## 1. Connection Pool Parameters (`SQLALCHEMY_ENGINE_OPTIONS`)

In high-concurrency production deployments (PostgreSQL, MySQL, Oracle), configure connection pool behavior via `SQLALCHEMY_ENGINE_OPTIONS`:

```python
app.config['SQLALCHEMY_ENGINE_OPTIONS'] = {
    'pool_size': 10,       # Number of permanent active database connections kept open in pool
    'max_overflow': 20,    # Max extra temporary connections created under heavy traffic spikes
    'pool_recycle': 1800,  # Recycle stale idle connections older than 1800 seconds (30 mins)
    'pool_timeout': 30     # Seconds to wait for an available connection before raising TimeoutError
}
```

## 2. SQLAlchemy Connection Pool Implementations

SQLAlchemy selects an appropriate pooling strategy based on the database engine dialect:

```
+──────────────────────────┬─────────────────────────────────────────────────────────────+
| Pool Class               | Description & Default Use Case                              |
+──────────────────────────┼─────────────────────────────────────────────────────────────+
| QueuePool (Default)      | Standard thread-safe connection pool with fixed size        |
|                          | and overflow bounds. Used for PostgreSQL/MySQL.             |
+──────────────────────────┼─────────────────────────────────────────────────────────────+
| NullPool                 | Disables connection pooling completely! Every query opens   |
|                          | and immediately closes a new DB connection.                 |
|                          | (Essential for Serverless / AWS Lambda deployments!).       |
+──────────────────────────┼─────────────────────────────────────────────────────────────+
| SingletonThreadPool      | Maintains a single open connection per active thread.       |
|                          | (Default pool used by SQLite).                              |
+──────────────────────────┴─────────────────────────────────────────────────────────────+
```

## 3. Session Scopes & Preventing Connection Leaks

In Flask, `db.session` is scoped to the current HTTP Request context. When a request ends, Flask automatically cleans up the session using **`teardown_appcontext`**, which calls `db.session.remove()`.

If you write background tasks or CLI scripts outside an HTTP request, you must manage session cleanup manually to prevent **Connection Leaks**:

```python
from sqlalchemy.exc import SQLAlchemyError

def execute_background_job():
    try:
        stmt = text("UPDATE users SET is_active = TRUE WHERE last_login > :cutoff")
        db.session.execute(stmt, {"cutoff": "2026-01-01"})
        db.session.commit()
    except SQLAlchemyError as e:
        db.session.rollback()
        print(f"Error in job: {e}")
    finally:
        # Return connection back to the connection pool!
        db.session.remove()
```
