# Day 10: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from multi-database concepts up to raw SQL security and connection pool tuning.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: Why would a real-world web application use more than one database?
**Answer**:
Real-world applications split data across multiple databases to separate high-frequency background logs (analytics, clickstreams, audit logs) from core business data (users, financial orders). This prevents heavy logging queries from slowing down core user transactions.

---

### Q2: What is a Database Bind in Flask-SQLAlchemy?
**Answer**:
A Database Bind is a named connection URI defined in `app.config['SQLALCHEMY_BINDS']` that allows Flask-SQLAlchemy to route specific ORM models to secondary databases.

---

### Q3: What is Raw SQL and when would you use it instead of ORM models?
**Answer**:
Raw SQL refers to writing native SQL string statements (`SELECT ... FROM ...`) directly. It is used when executing complex multi-table analytical reporting queries, database maintenance scripts, or legacy SQL procedures that are difficult to express in standard ORM syntax.

---

### Q4: What is Connection Pooling in simple terms?
**Answer**:
Connection Pooling is keeping a pre-opened fleet of database network connections ready in memory. Instead of wasting time opening and authenticating a new database connection for every incoming HTTP request, Flask reuses an open connection from the pool.

---

### Q5: How do you assign an ORM model class to a secondary database bind?
**Answer**:
Set the `__bind_key__` class attribute on the model:
```python
class SystemLog(db.Model):
    __bind_key__ = 'analytics'
    id = db.Column(db.Integer, primary_key=True)
```

---

## 🟡 Level 2: Intermediate Questions

### Q6: How do you safely execute raw SQL queries in Flask-SQLAlchemy to prevent SQL Injection?
**Answer**:
Wrap the SQL string in `sqlalchemy.text()` and pass query parameters as a dictionary to `db.session.execute()`:

```python
from sqlalchemy import text

stmt = text("SELECT * FROM users WHERE email = :user_email")
result = db.session.execute(stmt, {"user_email": input_val}).fetchall()
```

Never concatenate user input directly into SQL strings!

---

### Q7: What does `db.create_all()` do when multiple database binds are configured?
**Answer**:
`db.create_all()` inspects the `__bind_key__` attribute on every registered model class, connects to each respective database engine defined in `SQLALCHEMY_BINDS` (as well as `SQLALCHEMY_DATABASE_URI`), and creates the appropriate tables inside each database.

---

### Q8: What is the difference between `fetchone()`, `fetchall()`, and `scalar()` on a raw SQL result object?
**Answer**:
*   `fetchone()`: Returns the next single `Row` tuple object from the result set (or `None`).
*   `fetchall()`: Returns a list of all remaining `Row` tuple objects in the result set.
*   `scalar()`: Returns the first column value of the first row (ideal for `COUNT(*)` or `SUM()` queries).

---

### Q9: How do you retrieve the underlying SQLAlchemy `Engine` for a specific database bind?
**Answer**:
Use `db.get_engine(app, bind='bind_name')`:

```python
audit_engine = db.get_engine(app, bind='audit')
```

---

### Q10: What happens if a raw SQL query raises a database error during a transaction?
**Answer**:
The database session enters a failed state. You must call `db.session.rollback()` inside an exception handler block to clear pending failed queries and restore the session to a clean state.

---

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Can a single `db.session.commit()` perform an atomic two-phase commit across multiple database binds?
**Answer**:
No. By default, `db.session.commit()` issues separate `COMMIT` statements to each engine sequentially. If the second database commit fails after the first database commit succeeds, the first database changes remain committed. For true cross-database atomic transactions, you must configure **Two-Phase Commit (2PC)** support on underlying database drivers (like PostgreSQL XA transactions).

---

### Q12: Explain `pool_size` and `max_overflow` in `SQLALCHEMY_ENGINE_OPTIONS`.
**Answer**:
*   `pool_size`: The baseline number of permanent database connections kept open continuously in memory.
*   `max_overflow`: The maximum number of extra temporary connections allowed to open above `pool_size` during unexpected traffic spikes. Once peak traffic subsides, overflow connections are closed automatically.

---

### Q13: Why is `NullPool` recommended for Serverless environments (like AWS Lambda or Google Cloud Functions)?
**Answer**:
Serverless functions scale rapidly by spinning up hundreds of short-lived container instances. Maintaining traditional connection pools across hundreds of transient containers quickly exhausts database connection limits. `NullPool` disables connection pooling, ensuring each short-lived lambda execution opens and closes its connection cleanly.

---

### Q14: How do you prevent Connection Leaks in long-running background tasks or standalone CLI scripts?
**Answer**:
Always wrap database operations in a `try/except/finally` block and call **`db.session.remove()`** inside `finally:`. This releases the scoped session and returns the active database connection back to the engine pool.

---

### Q15: How do you configure Flask-Migrate when using multiple database binds?
**Answer**:
Pass `binds="__all__"` to `Migrate(app, db, binds="__all__")`. Alembic will create migration repositories and version tracking for all secondary database binds defined in `SQLALCHEMY_BINDS`.
