# Day 22: Practice & Technical Interview Questions

---

### Q1: What is the difference between Virtual Machines (VMs) and Docker Containers?
**Answer**:
- **Virtual Machines**: Virtualize physical hardware. Each VM runs a full guest operating system (OS kernel, system binaries, libraries), resulting in high RAM overhead, multi-gigabyte image sizes, and slow boot times (minutes).
- **Docker Containers**: Virtualize the operating system level. Containers share the host Linux kernel while isolating application processes in user-space, resulting in minimal RAM footprint, tiny megabyte-scale images, and sub-second boot times.

---

### Q2: How does Docker Layer Caching work and how do you optimize `Dockerfile` instruction ordering?
**Answer**:
Every `Dockerfile` instruction (`FROM`, `RUN`, `COPY`) creates a read-only filesystem layer. During builds, Docker checks if previous layers remain unchanged in cache. If an instruction invalidates a layer (e.g. modifying source code in `COPY . .`), all subsequent layers must be rebuilt from scratch.

To optimize caching, place static or rarely changing dependencies (`COPY requirements.txt` and `RUN pip install`) before frequently modified application source code (`COPY . .`).

### Q3: Why are Multi-Stage Docker builds beneficial for production deployment?
**Answer**:
Multi-stage builds allow separating build-time tools (C compilers, `gcc`, header files, `pip` caches) from the final production runtime image. 

By copying only installed Python packages and application code into a fresh runtime base image (`python:3.11-slim`), production images are reduced from ~1GB down to ~150MB, significantly reducing attack surface and container vulnerability risks.

---

### Q4: Why should Docker containers NOT run as the `root` user in production?
**Answer**:
By default, processes inside a container run as `root` (UID 0). If an attacker exploits a remote code execution vulnerability inside the container and breaks out via a kernel privilege escalation flaw, they gain full root control over the host server! 

Creating and running as a unprivileged user (`USER appuser`) limits potential exploit damage.

### Q5: How does DNS service discovery work in Docker Compose networks?
**Answer**:
Docker Compose creates an isolated user-defined bridge network. It provides an embedded DNS server that automatically registers service names defined in `docker-compose.yml` (e.g. `db`, `redis`, `web`). Containers resolve those service names directly to their internal container IP addresses.

---

### Q6: What is the purpose of `.dockerignore`?
**Answer**:
`.dockerignore` prevents copying unwanted files (such as local `.venv` virtual environments, `.git` histories, SQLite `.db` databases, and secret `.env` files) into the Docker build context. This speeds up build context transfer times and prevents leaking secrets into image layers.

---

### Q7: How do `depends_on` and health checks interact in `docker-compose.yml`?
**Answer**:
By default, `depends_on` only waits for a dependency container to *start*, not for its database server to be *ready* to accept socket connections. Combining `depends_on` with `condition: service_healthy` ensures the `web` container waits until PostgreSQL passes its `pg_isready` health check before launching Flask:

```yaml
depends_on:
  db:
    condition: service_healthy
```

---

### Q8: What is the difference between persistent Volumes and Bind Mounts in Docker?
**Answer**:
- **Volumes**: Managed entirely by Docker inside the host storage area (`/var/lib/docker/volumes/`). Ideal for database data persistence (`db_data:/var/lib/postgresql/data`).
- **Bind Mounts**: Mounts a specific host directory directly into the container (`./src:/app/src`). Ideal for local development live-reloading.

---

### Q9: How do `ENV` and `ARG` differ in a `Dockerfile`?
**Answer**:
- `ARG`: Build-time variables accessible only during `docker build`. Not available when the container is running.
- `ENV`: Environment variables persisted inside the image and available during runtime execution.

---

### Q10: What does `EXPOSE 5000` in a `Dockerfile` do?
**Answer**:
`EXPOSE 5000` is documentation indicating which network port the application listens on inside the container. It does **NOT** publish the port to the host system. To expose the port to external host traffic, use `-p 5000:5000` in `docker run` or `ports:` in `docker-compose.yml`.
