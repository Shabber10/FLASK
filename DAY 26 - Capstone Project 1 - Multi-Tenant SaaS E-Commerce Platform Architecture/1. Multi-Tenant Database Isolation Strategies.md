## 1. What is Multi-Tenancy?

In Software-as-a-Service (SaaS) applications, **Multi-Tenancy** is an architectural model where a single running application deployment serves multiple distinct customer organizations (called **Tenants**), ensuring strict data isolation so no tenant can ever view or modify another tenant's data:

```
Tenant A (Acme Corp)        Tenant B (Globex Inc)        Tenant C (Umbrella Corp)
[ acme.saas.com ]          [ globex.saas.com ]          [ umbrella.saas.com ]
        |                            |                            |
        +----------------------------+----------------------------+
                                     |
                                     v
                  +--------------------------------------+
                  | Shared Flask SaaS Application Engine |
                  +--------------------------------------+
                                     |
                                     v
                  +--------------------------------------+
                  | Multi-Tenant Data Isolation Storage  |
                  +--------------------------------------+
```

## 2. Multi-Tenant Database Isolation Models

Selecting a database isolation strategy balances operational cost, hardware overhead, and security isolation:

```
+-----------------------------------------------------------------------------------+
| 1. Discriminator Column (Shared DB, Shared Schema)                                 |
|    - Table: `orders` -> Columns: [id, tenant_id, item, amount]                    |
+-----------------------------------------------------------------------------------+
| 2. PostgreSQL Schemas (Shared DB, Separate Schemas)                                |
|    - Schema: `acme_schema.orders`  |  Schema: `globex_schema.orders`             |
+-----------------------------------------------------------------------------------+
| 3. Database-per-Tenant (Isolated DB Instances)                                    |
|    - DB 1: `acme_production_db`    |  DB 2: `globex_production_db`               |
+-----------------------------------------------------------------------------------+
```

| Isolation Model | Data Isolation | Operational Cost | Schema Migration Complexity |
| :--- | :--- | :--- | :--- |
| **Discriminator Column** | Logical (Filter by `tenant_id`) | Lowest (1 DB instance) | Lowest (Standard Alembic) |
| **PostgreSQL Schemas** | Logical/Structural (Postgres `search_path`)| Low/Medium | Medium (Migrate $N$ schemas) |
| **Database-per-Tenant**| Physical (Separate DB servers) | Highest | Highest |

## 3. Discriminator Column vs. PostgreSQL Schemas

### Model 1: Discriminator Column Pattern
Every database table includes a mandatory `tenant_id` foreign key. All queries MUST append `.filter_by(tenant_id=g.tenant.id)`:

```python
class Order(db.Model):
    __tablename__ = 'orders'
    id = db.Column(db.Integer, primary_key=True)
    tenant_id = db.Column(db.Integer, db.ForeignKey('tenants.id'), nullable=False, index=True)
    amount = db.Column(db.Float, nullable=False)
```

> ⚠️ **SECURITY RISK**: If a developer forgets to append `.filter_by(tenant_id=g.tenant.id)` in a single query, data leaks across tenants!

### Model 2: PostgreSQL Schemas (`search_path`)
Each tenant is assigned an isolated PostgreSQL schema. Upon receiving a request, Flask sets the database session search path dynamically:

```python
# Switch active PostgreSQL schema for current request thread
db.session.execute(text(f"SET search_path TO tenant_{tenant_slug}, public"))
```
