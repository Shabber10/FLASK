# Day 26: Practice & Technical Interview Questions

---

### Q1: What is Multi-Tenancy in SaaS software architecture?
**Answer**:
Multi-tenancy is an architectural model where a single running instance of a software application serves multiple distinct client organizations (tenants). The application guarantees logical or physical data isolation, ensuring no tenant can access or view another tenant's data.

---

### Q2: Compare Discriminator Column vs PostgreSQL Schemas vs Database-per-Tenant models.
**Answer**:
- **Discriminator Column**: Single shared database and schema. Every table includes `tenant_id`. Lowest operational cost, but highest security risk if a query misses the `tenant_id` filter.
- **PostgreSQL Schemas**: Single database instance with separate schemas per tenant. Good isolation, moderate cost, and schema switching via `SET search_path`.
- **Database-per-Tenant**: Dedicated database server per tenant. Maximum security and isolation, but highest infrastructure and migration cost.

---

### Q3: How does Flask resolve tenant identity dynamically per incoming HTTP request?
**Answer**:
Flask uses `@app.before_request` middleware to extract the tenant slug from:
1. Subdomain in Host header (`acme.saas.com`).
2. Custom HTTP Header (`X-Tenant-ID: acme`).
3. JWT token claim.

The resolved `Tenant` model object is injected into Flask's thread-local `g.tenant` proxy for access throughout the request lifecycle.

---

### Q4: What is the primary security vulnerability in Discriminator Column multi-tenancy?
**Answer**:
**Cross-Tenant Data Leakage**. If a developer writes a database query and forgets to append `.where(Model.tenant_id == g.tenant.id)`, the database returns records belonging to all tenants in the system.

---

### Q5: How do you prevent cross-tenant data leakage automatically in SQLAlchemy?
**Answer**:
Use SQLAlchemy ORM event listeners (`do_orm_execute`) to intercept all SELECT queries dynamically and automatically append `where(Model.tenant_id == g.tenant.id)` before query compilation.

---

### Q6: How do database migrations (Alembic) work in a PostgreSQL Schema-per-Tenant architecture?
**Answer**:
Alembic migrations must loop through every tenant schema in the database and execute `SET search_path TO schema_name` before applying migration DDL statements:

```python
for schema in tenant_schemas:
    connection.execute(text(f"SET search_path TO {schema}"))
    context.run_migrations()
```

---

### Q7: What is `g` in Flask and why is it used for tenant context?
**Answer**:
`g` is Flask's thread-local global context object reset on every HTTP request. Storing `g.tenant` ensures tenant metadata is isolated to the active request thread and accessible in any view function or extension without global variable conflicts.

---

### Q8: How does subdomain routing work in Flask?
**Answer**:
Set `SERVER_NAME = 'saasapp.com:5000'` in `app.config`. Routes can then match subdomains using blueprint host parameters or inspect `request.host` inside `@app.before_request`.

---

### Q9: How do you handle background Celery tasks in a Multi-Tenant application?
**Answer**:
Celery workers run outside HTTP request contexts. Celery tasks must explicitly receive `tenant_id` as a task argument (e.g. `generate_report.delay(tenant_id=5, report_id=12)`), allowing the worker function to query and set the tenant context manually inside `with app.app_context():`.

---

### Q10: How do cross-tenant analytics or global admin reports work in Multi-Tenant architectures?
**Answer**:
A dedicated Global Admin service or Data Warehouse (Snowflake, BigQuery) aggregates data across all tenant schemas/databases via background ETL jobs, granting superadmins cross-tenant analytics without weakening tenant runtime API isolation.
