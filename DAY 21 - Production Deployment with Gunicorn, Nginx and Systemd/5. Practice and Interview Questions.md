# Day 21: Practice & Technical Interview Questions

---

### Q1: Why should you NEVER use `flask run` or `app.run()` in a production deployment?
**Answer**:
Werkzeug's built-in development server (`flask run`) is single-threaded, unbuffered, and lacks worker process supervision or Slowloris attack protection. A single slow or hanging request blocks all other incoming user traffic. In production, applications require a dedicated pre-fork WSGI server like **Gunicorn** or **uWSGI** coupled with an Nginx reverse proxy.

---

### Q2: How do you calculate the optimal number of Gunicorn worker processes for a server?
**Answer**:
Follow the standard Gunicorn formula:

$$\text{Workers} = (2 \times \text{CPU Cores}) + 1$$

This formula allows workers to handle incoming requests while other worker processes wait for disk I/O or network database queries without causing CPU context-switching overhead.

---

### Q3: Why is Nginx placed in front of Gunicorn instead of exposing Gunicorn directly to the internet?
**Answer**:
1. **Static File Offloading**: Nginx serves static assets (CSS, JS, images) directly from disk at near-zero CPU cost, bypassing Gunicorn Python workers entirely.
2. **TLS/SSL Termination**: Manages HTTPS certificates and HTTP/2 protocol negotiation.
3. **Slow Client Protection**: Buffers slow incoming requests and responses, preventing Slowloris DoS attacks from holding Gunicorn workers hostage.
4. **Load Balancing & Failover**: Distributes traffic across multiple backend Gunicorn instances.

---

### Q4: What is the performance difference between a Unix Domain Socket and a TCP Loopback Socket?
**Answer**:
- **TCP Loopback (`127.0.0.1:8000`)**: Traverses the local operating system network stack, incurring TCP packet framing, checksums, and port binding overhead.
- **Unix Domain Socket (`unix:/tmp/gunicorn.sock`)**: Inter-process communication (IPC) managed directly in kernel memory filesystem space. It is **20% to 30% faster** with lower latency than TCP loopback.

---

### Q5: What are the differences between `sync`, `gthread`, and `gevent` Gunicorn worker models?
**Answer**:
- **`sync`**: Default pre-fork synchronous workers. Each worker process handles 1 request at a time.
- **`gthread`**: Multi-threaded worker processes. Each process manages multiple OS threads for I/O concurrency.
- **`gevent`**: Asynchronous coroutine workers (greenlets). Uses cooperative multitasking to handle thousands of concurrent I/O connections per worker process.

### Q6: What is the role of `ProxyFix` middleware when running Flask behind Nginx?
**Answer**:
Because Nginx terminates external client connections and forwards traffic over internal HTTP to Gunicorn, Flask sees `request.remote_addr` as the Nginx proxy IP and `request.is_secure` as `False`. `ProxyFix` parses `X-Forwarded-For` and `X-Forwarded-Proto` headers set by Nginx, restoring the real client IP and HTTPS protocol state in Flask.

---

### Q7: What is Systemd and why is it used for Gunicorn process management?
**Answer**:
Systemd is the init system and service manager for Linux operating systems. 

It acts as a process supervisor for Gunicorn:
- Starts Gunicorn automatically on system boot.
- Restarts Gunicorn immediately if a worker or master process crashes (`Restart=always`).
- Captures stdout/stderr logs into `journalctl`.

### Q8: What does `location /static/` in Nginx do?
**Answer**:

```nginx
location /static/ {
    alias /var/www/flaskapp/static/;
    expires 30d;
}
```

It instructs Nginx to intercept any request starting with `/static/` and serve the file directly from the filesystem path `/var/www/flaskapp/static/`, completely bypassing Gunicorn and Python processing.

---

### Q9: How do you gracefully reload Gunicorn worker processes after updating application code without dropping active connections?
**Answer**:
Send a `SIGHUP` signal to the Gunicorn Master Process ID (PID):

```bash
# Graceful Reload Signal
kill -HUP <gunicorn_master_pid>
# Or via Systemd:
sudo systemctl reload flaskapp
```

The master process spawns new worker processes running the updated code while allowing old workers to finish processing active requests before shutting them down.

---

### Q10: What does `keepalive 5` do in Gunicorn configuration?
**Answer**:
`keepalive 5` instructs Gunicorn to keep persistent HTTP connections open for 5 seconds waiting for subsequent requests from the Nginx proxy, reducing TCP handshake overhead between Nginx and Gunicorn.
