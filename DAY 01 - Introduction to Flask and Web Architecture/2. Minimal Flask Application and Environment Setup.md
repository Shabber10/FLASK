# Day 01: Minimal Flask Application & Environment Setup

In this section, we examine the inner workings of the `Flask` application instance, `__name__` import path resolution, application and request contexts, environment configuration management, and custom WSGI middleware.

---

## 1. The `Flask` Application Class & `__name__`

### Creating the Application Instance
Every Flask application begins by instantiating the `Flask` class:

```python
from flask import Flask

app = Flask(__name__)
```

### Why Pass `__name__`?
The `import_name` parameter passed to `Flask(import_name)` is crucial. Flask uses `__name__` to determine the root path of the application package or module. This root path is used to locate:
- `static` directory for CSS, JS, and image assets.
- `templates` directory for Jinja2 template files.
- `instance` folder for local configuration and SQLite databases.

#### Path Resolution Example
When `app = Flask(__name__)` executes inside a file at `/home/user/project/app.py`:
- `app.root_path` becomes `/home/user/project`
- `app.static_folder` defaults to `/home/user/project/static`
- `app.template_folder` defaults to `/home/user/project/templates`
- `app.instance_path` defaults to `/home/user/project/instance`

## 2. Application Context vs. Request Context

Flask relies on two types of context objects to make global proxies accessible per thread/coroutine:

```
                  +--------------------------------+
                  |     Application Context        |
                  |  (`current_app`, `g` object)   |
                  +---------------+----------------+
                                  |
                                  v
                  +---------------+----------------+
                  |       Request Context          |
                  |  (`request`, `session` object) |
                  +--------------------------------+
```

### 1. Application Context (`app_context`)
- **Bound Proxies**: `current_app`, `g`
- **Lifetime**: Pushed when handling a request or running CLI commands; destroyed when request finishes.
- **Use Case**: Holds application-level configuration, database connections, and temporary request-scoped global data stored on `g`.

### 2. Request Context (`request_context`)
- **Bound Proxies**: `request`, `session`
- **Lifetime**: Pushed when an HTTP request arrives; destroyed when response is sent.
- **Use Case**: Encapsulates incoming HTTP headers, parameters, form data, cookies, and session state.

#### Accessing Contexts Outside HTTP Requests
To access database objects or `current_app` inside CLI scripts or interactive Python shells, explicitly push the application context:

```python
with app.app_context():
    print(current_app.name)
    # Database queries can execute safely here
```

## 3. Environment Configurations (`.env` and `.flaskenv`)

Flask 3.x natively integrates `python-dotenv` to load environment variables automatically when running `flask run`.

### Configuration Files Breakdown

Create `.flaskenv` for non-sensitive development settings:

```ini
# .flaskenv (Committed to Git)
FLASK_APP=app.py
FLASK_DEBUG=1
FLASK_RUN_PORT=5000
FLASK_RUN_HOST=127.0.0.1
```

Create `.env` for secret credentials (Never commit to Git! Add to `.gitignore`):

```ini
# .env (Ignored by Git)
SECRET_KEY=super-secret-cryptographic-key-30-days
DATABASE_URL=postgresql://postgres:secretpassword@localhost:5432/app_db
```

## 4. Writing Custom WSGI Middleware

Because `app` is a standard WSGI application callable, you can wrap `app.wsgi_app` with custom WSGI middleware to intercept requests before Flask processes them.

### Custom HTTP Header Injection Middleware Example

```python
class HeaderInjectionMiddleware:
    def __init__(self, wsgi_app):
        self.wsgi_app = wsgi_app

    def __call__(self, environ, start_response):
        def custom_start_response(status, headers, exc_info=None):
            # Inject custom server timing / security headers into every response
            headers.append(('X-WSGI-Middleware', 'Active-Layer-1'))
            return start_response(status, headers, exc_info)

        return self.wsgi_app(environ, custom_start_response)

# Apply Middleware to Flask Application
app.wsgi_app = HeaderInjectionMiddleware(app.wsgi_app)
```

## 5. Flask Development Server vs. Production WSGI Servers

| Environment | Server Engine | Command | Capabilities |
| :--- | :--- | :--- | :--- |
| **Development** | Werkzeug Built-in Server | `flask run` | Auto-reloader, interactive debugger, single-threaded |
| **Production** | Gunicorn / uWSGI | `gunicorn -w 4 app:app` | Multi-process worker pool, high concurrency, non-blocking |
