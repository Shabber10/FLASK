## 1. Web Architecture & The WSGI Standard (PEP 3333)

### What is Flask?
Flask is a lightweight, extensible **WSGI web application framework** created by Armin Ronacher. Unlike monolithic frameworks like Django that prescribe specific database ORMs or form packages, Flask follows a **micro-framework design philosophy**. It supplies the bare minimum required to build web applications:
- **Routing & HTTP Handling** (via Werkzeug)
- **Templating** (via Jinja2)
- **CLI Commands** (via Click)

---

### The Web Request Pipeline Architecture

When a client (browser, mobile app, or cURL request) makes an HTTP call to a Flask app, it flows through a multi-layered pipeline:

```
+-------------------+
|    HTTP Client    |  Sends HTTP Request (GET /user/10)
|  (Browser/cURL)   |
+---------+---------+
          |
          v
+---------+---------+
|   Web Server      |  Handles TLS/SSL Termination, Static Files & Reverse Proxying
|  (Nginx / Apache) |
+---------+---------+
          | Passes request via Unix Domain Socket / TCP
          v
+---------+---------+
|   WSGI Server     |  Translates HTTP request into WSGI `environ` dictionary
| (Gunicorn/uWSGI)  |  Calls WSGI application callable: `app(environ, start_response)`
+---------+---------+
          |
          v
+---------+---------+
|  WSGI Middleware  |  Intercepts request (Logging, Auth, Header Modifications)
+---------+---------+
          |
          v
+---------+---------+
| Flask Application |  Pushes Application & Request Contexts
|  (App Instance)   |  Matches URL Rule in `app.url_map` & executes View Function
+---------+---------+
          |
          v
+---------+---------+
|   View Function   |  Executes business logic, queries DB, returns string/response object
+-------------------+
```

## 2. Low-Level WSGI Specification Mechanics

The **Web Server Gateway Interface (WSGI)** defined in **PEP 3333** is a simple specification that decouples web servers from Python web applications.

### The WSGI Application Interface
A WSGI application must be a **callable object** (a function, method, or class with a `__call__` method) that accepts exactly two arguments:

1. `environ`: A Python dictionary containing all HTTP headers, request variables, server metadata, and WSGI input streams.
2. `start_response`: A callable supplied by the WSGI server used to set the HTTP status code and response headers.

### Raw Pure-Python WSGI Application Example
Below is a fully functional WSGI application written without any frameworks:

```python
def raw_wsgi_app(environ, start_response):
    # 1. Parse HTTP Request details from WSGI environ dictionary
    request_method = environ.get('REQUEST_METHOD', 'GET')
    path_info = environ.get('PATH_INFO', '/')
    
    # 2. Define HTTP Response Status and Headers
    status = '200 OK'
    headers = [
        ('Content-Type', 'text/html; charset=utf-8'),
        ('X-Powered-By', 'Pure-Python-WSGI')
    ]
    
    # 3. Call start_response to send status & headers to server
    start_response(status, headers)
    
    # 4. Return iterable containing response body bytes
    body = f"<h1>Raw WSGI Server</h1><p>Method: {request_method}</p><p>Path: {path_info}</p>"
    return [body.encode('utf-8')]
```

### Anatomy of the `environ` Dictionary

The WSGI `environ` dictionary contains standardized CGI keys alongside WSGI-specific extensions:

| Key | Description | Example |
| :--- | :--- | :--- |
| `REQUEST_METHOD` | HTTP verb used for the request | `'GET'`, `'POST'`, `'PUT'` |
| `PATH_INFO` | URL path requested by client | `'/api/v1/users'` |
| `QUERY_STRING` | Raw unparsed URL query parameters | `'page=2&sort=desc'` |
| `CONTENT_TYPE` | MIME type of request body | `'application/json'` |
| `HTTP_AUTHORIZATION` | Raw HTTP Authorization header | `'Bearer <token>'` |
| `wsgi.input` | Input stream to read raw request body bytes | File-like object (`io.BytesIO`) |
| `wsgi.multithread` | `True` if app can be invoked concurrently by threads | `True` |
| `wsgi.multiprocess` | `True` if app can be invoked concurrently by processes | `True` |

## 3. Werkzeug Engine & Flask Core Architecture

Flask delegates request parsing, response construction, and URL routing to **Werkzeug**.

### Werkzeug Core Components

1. **Request & Response Wrappers**:
   Werkzeug wraps the raw `environ` dictionary into a clean, object-oriented `Request` object (`request.args`, `request.form`, `request.json`) and handles byte serialization in `Response` objects.

2. **Routing System (`Routing Map` & `Rules`)**:
   URL matching is handled by Werkzeug's `Map` and `Rule` objects using high-performance regular expression matching.

3. **Thread-Local / Context-Local Proxies**:
   Flask uses Werkzeug proxies (`LocalProxy` backed by Python's `contextvars` module) to ensure request data is thread-safe and isolated across concurrent requests without explicit parameter passing.

## 4. Framework Comparison: WSGI vs ASGI

| Feature | WSGI (Flask 3.x) | ASGI (FastAPI / Quart) | Monolith (Django WSGI) |
| :--- | :--- | :--- | :--- |
| **Concurrency Model** | Synchronous (Thread/Process Pools) | Asynchronous Event Loop (`async`/`await`) | Synchronous (Multi-threaded) |
| **Protocol Support** | HTTP 1.1 | HTTP 1.1, HTTP/2, WebSockets | HTTP 1.1 |
| **Flexibility** | Ultra-High (Micro-framework) | High (Micro-framework) | Opinionated (Batteries-Included) |
| **Execution Engine** | Werkzeug + Gunicorn | Uvicorn + Starlette | Django WSGI Handler |
