## 1. The Concurrency Problem & `LocalProxy`

When a web server (like Gunicorn or Werkzeug) processes HTTP requests, it uses **threads**, **coroutines**, or **worker processes** to execute requests concurrently.

If Flask used standard global variables, concurrent threads would overwrite each other's data (Race Conditions). Conversely, requiring developers to pass `request` and `app` as arguments into every single helper function would pollute function signatures.

Flask solves this using **Context Locals** powered by Werkzeug's `LocalProxy` and Python's `contextvars` module.

```python
from flask import request, current_app

# When you call `request.method`, Werkzeug inspects Python's `contextvars` 
# for the active thread/coroutine -> resolves the correct Request object dynamically!
method = request.method
```

## 2. Dual-Layer Context Architecture

Flask maintains two distinct context layers:

```
+-----------------------------------------------------------------------+
|                         APPLICATION CONTEXT                           |
|  - Lifetime: Duration of HTTP Request or explicit CLI / Script block |
|  - Global Proxies: `current_app`, `g`                                 |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
|                           REQUEST CONTEXT                             |
|  - Lifetime: Pushed when HTTP Request arrives, popped when sent       |
|  - Global Proxies: `request`, `session`                               |
+-----------------------------------------------------------------------+
```

### 1. Application Context (`app_context`)
Pushed when an application handles an HTTP request, runs CLI commands, or executes background scripts:
*   **`current_app`**: A proxy pointing to the active `Flask` application instance.
*   **`g`**: An empty object provided by the application context to store temporary request-scoped data (e.g., database connections, authenticated user instances, start timestamps).

### 2. Request Context (`request_context`)
Pushed immediately after the application context when an HTTP request arrives:
*   **`request`**: A proxy pointing to incoming HTTP request details (headers, query args, POST body).
*   **`session`**: A proxy pointing to the signed user session dictionary.

## 3. Manually Pushing Contexts (CLI Scripts & Testing)

If you attempt to access `current_app` or `request` outside an active HTTP request (for example, in a standalone database script or unit test), Flask raises an error:

> `RuntimeError: Working outside of application context.`

To fix this in scripts or unit tests, **manually push the context** using context managers:

### 1. Pushing Application Context (`app.app_context()`)
```python
from flask import Flask, current_app, g

app = Flask(__name__)
app.config['DB_NAME'] = 'production_db'

# Push application context manually for standalone scripts
with app.app_context():
    print(f"Active App Config: {current_app.config['DB_NAME']}")
    g.temp_value = 42
```

### 2. Pushing Request Context (`app.test_request_context()`)
```python
# Simulate an incoming HTTP request for unit testing
with app.test_request_context('/search?q=flask', method='GET'):
    from flask import request
    print(f"Simulated Path: {request.path}")     # Output: "/search"
    print(f"Simulated Query: {request.args['q']}") # Output: "flask"
```

## 4. In-Memory `g` vs. Cookie `session`

| Feature | `g` (Application Context Store) | `session` (Request Context Store) |
| :--- | :--- | :--- |
| **Lifetime** | Single HTTP Request only | Multiple HTTP Requests across user visits |
| **Location** | Server RAM memory | Cryptographically signed client browser cookie |
| **Data Types** | Complex Python objects (DB connections, sockets) | JSON-serializable primitives (strings, ints, dicts) |
| **Security** | Completely private to server process | Visible (signed, but unencrypted) to client browser |
