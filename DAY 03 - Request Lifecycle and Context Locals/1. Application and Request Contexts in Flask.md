# Day 03: Application & Request Contexts in Flask

Welcome to **Day 03** of the 30-Day Enterprise Flask Masterclass! Today, we explore Flask's internal context management system, Werkzeug `LocalProxy` objects, Python `contextvars`, and the dual-layer context architecture (`app_context` and `request_context`).

---

## 1. The Multi-Threading & Concurrency Problem

Web applications process multiple incoming HTTP requests concurrently using threads, greenlets, or coroutines. 

If Flask stored request data in standard global variables, concurrent requests would overwrite each other's data (Race Conditions). Conversely, passing `request` and `app` as explicit parameters through every function signature creates verbose, unmaintainable code.

Flask solves this using **Context Locals** backed by Python's native `contextvars` module and Werkzeug's `LocalProxy`.

---

## 2. Dual-Layer Context Architecture

Flask maintains two distinct context layers:

```
+-----------------------------------------------------------------------+
|                         APPLICATION CONTEXT                           |
|  - Lifetime: Duration of HTTP Request or explicit CLI / Script block |
|  - Global Proxies: `current_app`, `g`                                 |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
|                           REQUEST CONTEXT                             |
|  - Lifetime: Pushed when HTTP Request arrives, popped when sent       |
|  - Global Proxies: `request`, `session`                               |
+-----------------------------------------------------------------------+
```

### 1. Application Context Layer
Pushed when an application handles an HTTP request, runs CLI commands, or executes background scripts:
- **`current_app`**: A `LocalProxy` pointing to the active `Flask` application instance handling the current thread/task.
- **`g`**: An object provided by the application context to store arbitrary request-scoped data (e.g. database connections, authenticated user instances, start timestamps).

### 2. Request Context Layer
Pushed immediately after the application context when an HTTP request arrives:
- **`request`**: A `LocalProxy` to the incoming `Request` object (headers, query args, body payload).
- **`session`**: A `LocalProxy` to the signed user session dictionary.

## 3. How `LocalProxy` Works Under the Hood

When you access `request.method` or `current_app.config`, you are interacting with a **`LocalProxy`** instance.

```python
from werkzeug.local import LocalProxy
from flask import current_app

# `g` and `request` are dynamic proxies that resolve their target at runtime
user_ip = request.remote_addr 
# Werkzeug inspects `contextvars` for current thread/async task -> retrieves actual Request instance -> gets `.remote_addr`
```

### Benefits of `LocalProxy`
- Allows global imports (`from flask import request, g`) while remaining thread-safe and coroutine-safe.
- Always resolves to the active request instance of the executing thread.

## 4. Manually Pushing Contexts (CLI Scripts & Tests)

Attempting to access `current_app` or `request` outside an active HTTP request raises a `RuntimeError: Working outside of application context` or `RuntimeError: Working outside of request context`.

### 1. Manually Pushing Application Context
```python
from flask import Flask, current_app, g

app = Flask(__name__)
app.config['DB_NAME'] = 'production_db'

# Use `app.app_context()` context manager
with app.app_context():
    print(current_app.config['DB_NAME'])
    g.temp_val = 100
```

### 2. Manually Pushing Request Context (Testing)
```python
# Use `app.test_request_context()` for simulating HTTP requests
with app.test_request_context('/search?q=flask', method='GET'):
    from flask import request
    print(request.args.get('q')) # Outputs: "flask"
```

## 5. Storage Patterns with `g` vs. `session`

| Feature | `g` (Application Context Store) | `session` (Request Context Store) |
| :--- | :--- | :--- |
| **Persistence** | Single HTTP Request lifetime only | Multi-request (Stored in HTTP Cookie/Redis) |
| **Location** | In-Memory on Server | Cryptographically Signed Client Cookie |
| **Data Types** | Complex Python objects (DB connections, sockets) | JSON-serializable primitives (strings, ints, dicts) |
| **Security** | Private to server process | Visible (though signed) to client browser |
