## 1. What does "Context" mean in Plain English?

In everyday English, **"Context"** means the background information or environment surrounding a situation. 

> **Example**: If someone says *"Pass me that key"*, the meaning depends entirely on the context:
> *   Inside a car repair shop 🚗 -> Car ignition key.
> *   Inside a piano studio 🎹 -> A musical key (C-Major).
> *   Inside a database office 💾 -> Primary database key.

In Flask, **Context** refers to the temporary background data surrounding an active HTTP request (like *"Which user sent this request?"*, *"What form parameters were submitted?"*, or *"Which database is active?"*).

## 2. The Danger of Standard Global Variables in Web Apps

In normal Python desktop scripts, you can use global variables freely:

```python
# Standard Python script (ONLY 1 USER RUNS THIS AT A TIME)
user_name = "Alice"

def print_user():
    print(f"User is {user_name}")
```

### Why Global Variables Fail in Web Applications 🚨

A web server handles **thousands of users at the exact same time**. Imagine what happens if 2 users visit your website at the same second:

1.  **User A (Alice)** logs in. The server sets `global_user = "Alice"`.
2.  **User B (Bob)** logs in 1 millisecond later. The server sets `global_user = "Bob"`.
3.  **User A** clicks "View Profile". Because `global_user` was overwritten by Bob, **Alice sees Bob's personal bank account!** 😱

This catastrophe is called a **Race Condition**.

---

## 3. How Flask Solves Concurrency: Context Locals (`g` & `request`)

Flask prevents users from overwriting each other's data by introducing **Context Local Objects**:

```
USER A (Alice) Request ───> Thread 1 ───> Has its own isolated `request` & `g`
USER B (Bob) Request   ───> Thread 2 ───> Has its own isolated `request` & `g`
```

*   Even though you write `from flask import request, g` at the top of your script like a global variable, **Flask dynamically isolates `g` and `request` for each thread or user request!**
*   **`g` (Global Request Backpack)**: An empty container created at the start of a request where you can safely store temporary data (like database connections or logged-in user details). It is wiped clean as soon as the request finishes.

---

## 4. What is the Request Lifecycle?

When a user clicks a button on your site, their request goes through a multi-step journey (the **Request Lifecycle**):

```
1. Request Arrives from Browser
              │
              ▼
2. Flask Pushes App & Request Contexts (Prepares `g` and `request`)
              │
              ▼
3. Runs `@app.before_request` Hooks (Check logins, start timers)
              │
              ▼
4. Executes your View Function (`def profile():`)
              │
              ▼
5. Runs `@app.after_request` Hooks (Add security headers)
              │
              ▼
6. Runs `@app.teardown_request` Hooks (Close database connections)
              │
              ▼
7. Response Sent to Browser & Contexts Destroyed
```

---

## 5. What are Lifecycle Hooks?

Think of **Lifecycle Hooks** as automatic event triggers. Instead of adding database connection code or timing code inside *every single view function*, you register hooks:

*   **`@app.before_request`**: *"Hey Flask, run this code right BEFORE processing any request!"* (Great for security checks or starting timers).
*   **`@app.after_request`**: *"Hey Flask, run this code right AFTER creating the response!"* (Great for adding security headers).
*   **`@app.teardown_request`**: *"Hey Flask, run this code at the VERY END, even if my code crashes!"* (Great for closing database connections safely).
