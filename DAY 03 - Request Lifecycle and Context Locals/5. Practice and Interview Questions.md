# Day 03: Practice & Technical Interview Questions

### Q1: What is a `LocalProxy` in Flask and how does it prevent race conditions in multi-threaded web servers?
**Answer**:
`LocalProxy` is a proxy object provided by Werkzeug that forwards all attribute accesses and method calls to an underlying object bound to the current thread or coroutine (using Python's `contextvars`).

In a multi-threaded server (e.g. Gunicorn with thread workers), multiple requests execute concurrently in parallel threads. `LocalProxy` ensures `from flask import request` resolves dynamically to the specific `Request` object created for the calling thread, eliminating race conditions without passing `request` explicitly through view functions.

### Q2: What is the difference between `g` and `session` in Flask?
**Answer**:
- **`g`**: In-memory, request-scoped temporary storage bound to the application context. Destroyed automatically when the request ends. Used for database connections, current user objects, or request start times.
- **`session`**: Multi-request persistent storage serialized into a cryptographically signed HTTP cookie (or server-side Redis store). Persists across multiple HTTP requests from the same user browser.

### Q3: Explain what happens if `@app.before_request` returns a response object instead of `None`.
**Answer**:
If a function decorated with `@app.before_request` returns a value other than `None` (e.g. a `Response` object, tuple, or `redirect()`), Flask performs **request short-circuiting**:
1. Execution of any remaining `@app.before_request` functions is skipped.
2. The view function matching the route is **never executed**.
3. Execution skips directly to `@app.after_request` hooks and returns the short-circuited response.

This is commonly used for authentication/authorization middleware and rate limit checks.

### Q4: Compare `@app.after_request` and `@app.teardown_request`. When would you use each?
**Answer**:
- **`@app.after_request`**: Executes after the view function succeeds. Must accept and return a `Response` object. **Skipped** if an unhandled exception occurs during request execution. Use it to modify response headers, set cookies, or compress response bodies.
- **`@app.teardown_request`**: Executes at the very end of request teardown. Receives an optional exception argument. **Guaranteed to execute** even if unhandled errors or exceptions occur. Use it to close database connections, release mutex locks, or delete temporary files.

### Q5: How do you access `current_app` or database models inside a background CLI script or standalone unit test?
**Answer**:
Wrap the script execution inside `with app.app_context():`:

```python
from app import create_app, db
from flask import current_app

app = create_app()

with app.app_context():
    print(f"Active DB: {current_app.config['SQLALCHEMY_DATABASE_URI']}")
    # Execute database queries safely
```

### Q6: What is a `@app.context_processor` and how does it benefit Jinja2 template rendering?
**Answer**:
A context processor is a function that returns a dictionary of keys and values. Flask automatically merges these key-value pairs into the Jinja2 template context for every `render_template()` call across the app. It eliminates the need to manually pass common global variables (e.g. site logo, current year, user settings) in every view function.

### Q7: What error is raised when accessing `request.args` outside an active HTTP request, and how do you fix it in unit tests?
**Answer**:
It raises `RuntimeError: Working outside of request context`. 

In unit tests or scripts, fix it by pushing a temporary request context using `app.test_request_context()`:

```python
with app.test_request_context('/search?q=flask', method='GET'):
    assert request.args.get('q') == 'flask'
```

### Q8: Can multiple `@app.before_request` functions be registered, and in what order do they execute?
**Answer**:
Yes. Multiple `@app.before_request` functions execute in the exact order they were registered. If any hook returns a non-None response, execution short-circuits immediately.

---

### Q9: Why shouldn't heavy database connections or socket objects be stored inside the `session` object?
**Answer**:
`session` data is serialized into a client-side HTTP cookie (or JSON-serialized into Redis). Complex Python objects like socket handles, thread locks, or database connections cannot be JSON/pickle-serialized safely into HTTP headers. Complex objects should be stored on `g`.

---

### Q10: How does Flask 3.x handle context isolation in asynchronous (`async`/`await`) routes?
**Answer**:
Flask 3.x utilizes Python 3.7+'s native `contextvars` module under the hood instead of `thread.local`. `contextvars` automatically preserves and isolates context state across asynchronous task boundaries, coroutines, and event loops.
