# Day 29: Practice & Technical Interview Questions

---

### Q1: Why do individual SQL `INSERT` statements fail under high write volume (10,000+ RPS)?
**Answer**:
Every individual SQL `INSERT` statement requires opening a database transaction, acquiring table/page locks, writing to the Write-Ahead Log (WAL), updating indexes, and awaiting TCP acknowledgement. 

Executing thousands of individual `INSERT` calls per second causes database lock contention, connection pool exhaustion, and server crashes. High-throughput ingestion requires **buffering messages in Kafka** and executing **bulk batch insertions**.

---

### Q2: Why does a high-throughput ingestion API return HTTP status `202 Accepted` instead of `201 Created`?
**Answer**:
- `201 Created`: Implies the resource has already been created and committed synchronously to the database.
- `202 Accepted`: Indicates the server received and validated the event payload, queuing it in a message broker (Kafka/Redis) for asynchronous batch insertion later. It allows the API gateway to return responses in under 2ms.

---

### Q3: What is the performance difference between `db.session.add()` and `db.session.bulk_insert_mappings()` in SQLAlchemy?
**Answer**:
- `db.session.add()`: Instantiates full ORM model Python objects, tracks unit-of-work state changes, and generates individual SQL `INSERT` statements.
- `db.session.bulk_insert_mappings()`: Accepts raw Python dictionaries and bypasses ORM object instantiation and unit-of-work overhead, generating a single multi-row SQL `INSERT INTO table VALUES (...), (...), (...)` query. It executes **up to 50x faster**.

---

### Q4: What is Backpressure in high-throughput event streaming architectures?
**Answer**:
Backpressure occurs when incoming event traffic rates exceed the processing capacity of downstream database consumers. 

Message brokers (Kafka or Redis Streams) buffer burst spikes safely on disk/RAM, allowing consumers to process events at a sustainable rate without dropping data or crashing servers.

---

### Q5: How do Kafka Topics, Partitions, and Consumer Groups interact to scale read throughput?
**Answer**:
Kafka divides Topics into parallel **Partitions**. A **Consumer Group** consists of worker processes assigned to specific partitions. Because each partition is consumed by a single worker in the group, adding partitions and consumer workers enables parallel linear scaling of read and write throughput across a cluster.

---

### Q6: What is the difference between Tumbling Time Windows and Sliding Time Windows in analytics aggregation?
**Answer**:
- **Tumbling Window**: Non-overlapping, contiguous fixed time intervals (e.g., 10:00-10:01, 10:01-10:02). Every event belongs to exactly one window.
- **Sliding Window**: Overlapping time intervals that advance continuously (e.g., Total events over the *past 5 minutes*, evaluated every second).

---

### Q7: What is TimescaleDB and why is it used for time-series analytics in PostgreSQL?
**Answer**:
TimescaleDB is a PostgreSQL extension that partitions large time-series tables into automatic, smaller time-based chunks called **Hypertables**. It improves write performance for timestamped data and supplies built-in functions like `time_bucket()` for high-speed time-window aggregations.

---

### Q8: How do you handle idempotency during bulk batch processing?
**Answer**:
If a batch flusher crashes after writing rows to PostgreSQL but before committing its Kafka consumer offset, the batch may be re-delivered. 

Idempotency is enforced using `INSERT INTO ... ON CONFLICT (event_uuid) DO NOTHING`, ensuring duplicate re-delivered events are silently ignored by the database.

---

### Q9: Why is `producer.poll(0)` used in `confluent-kafka` Python producers?
**Answer**:
`producer.produce()` queues messages into memory without blocking the Flask thread. Calling `producer.poll(0)` serves delivery report callbacks in the background without blocking the HTTP request thread.

---

### Q10: How do you monitor pipeline health in high-throughput event systems?
**Answer**:
Monitor two key metrics:
1. **Ingestion Latency**: P99 HTTP response latency on the API gateway.
2. **Consumer Lag**: The delta between the latest message offset in Kafka partitions and the current read offset of consumer workers. High consumer lag alerts engineers that consumers are falling behind incoming traffic.
