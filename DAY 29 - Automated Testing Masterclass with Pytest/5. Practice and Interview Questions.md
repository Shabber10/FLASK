# Day 29: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from automated testing basics up to Pytest fixtures, Flask `test_client()`, database mocking, code coverage, and GitHub Actions CI pipelines.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is Automated Testing and why is it essential for software development?
**Answer**:
Automated Testing involves writing code to execute your application features automatically. It eliminates manual browser testing, catches regressions instantly, and allows developers to deploy code updates with confidence.

---

### Q2: What is `Pytest`?
**Answer**:
`Pytest` is the standard Python testing framework that automatically discovers test files (`test_*.py`), executes test functions (`def test_*()`), and evaluates assertions using plain Python `assert` statements.

---

### Q3: What is Flask's `test_client()`?
**Answer**:
Flask's `test_client()` is a built-in virtual HTTP client (`app.test_client()`) that allows developers to simulate HTTP GET, POST, PUT, and DELETE requests against Flask routes in-memory without launching a live server.

---

### Q4: What is a Pytest Fixture?
**Answer**:
A Pytest Fixture (`@pytest.fixture`) is a reusable helper function that sets up test prerequisites (such as initializing an in-memory test database or generating authentication headers) before a test runs.

---

### Q5: What is Code Coverage?
**Answer**:
Code Coverage is a metric (measured by tools like `pytest-cov`) indicating the percentage of your application's source code lines that were executed during test runs.

---

## 🟡 Level 2: Intermediate Questions

### Q6: Why should `TESTING = True` be set in Flask test configurations?
**Answer**:
Setting `TESTING = True` disables Flask's built-in error trapping middleware, allowing exceptions to propagate directly to the Pytest runner so developers get clear, detailed tracebacks when tests fail.

---

### Q7: How does fixture teardown work using the `yield` keyword in Pytest?
**Answer**:
Code before the `yield` statement executes during test setup. When Pytest reaches `yield`, it pauses the fixture and executes the test function. Once the test function completes, Pytest resumes the fixture to execute cleanup code after `yield` (e.g. `db.drop_all()`).

---

### Q8: What are the different Fixture Scopes in Pytest?
**Answer**:
*   `function` (Default): Fixture runs once per test function.
*   `class`: Fixture runs once per test class.
*   `module`: Fixture runs once per test `.py` file module.
*   `session`: Fixture runs once for the entire Pytest test run session.

---

### Q9: Why use `sqlite:///:memory:` for database integration tests?
**Answer**:
`sqlite:///:memory:` creates an ephemeral in-memory database in RAM. It executes SQL statements extremely fast and automatically disappears when the test process ends, guaranteeing total database isolation.

---

### Q10: How do you check JSON response data in Pytest assertions?
**Answer**:
Use `response.get_json()` or `response.json`:

```python
assert response.status_code == 200
assert response.get_json()['username'] == 'alice'
```

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Why should external third-party API calls (e.g. Stripe, SendGrid) be mocked during automated tests, and how do you mock them?
**Answer**:
Calling real external APIs during tests makes tests slow, network-dependent, flaky, and expensive. Use `mocker.patch('module.function_name', return_value=fake_response)` to intercept outgoing HTTP calls and return predictable mock data instantly.

---

### Q12: How do `@pytest.mark.parametrize` decorators reduce test code duplication?
**Answer**:
`@pytest.mark.parametrize` allows running a single test function multiple times with different sets of input arguments and expected output assertions:

```python
@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (10, -5, 5),
    (0, 0, 0)
])
def test_add(a, b, expected):
    assert a + b == expected
```

---

### Q13: How do you achieve database transaction rollback per test to speed up test suites?
**Answer**:
Instead of re-creating database tables (`db.create_all()` / `db.drop_all()`) between every test, wrap each test function in a nested SQLAlchemy database transaction (`db.session.begin_nested()`). After the test finishes, issue a `transaction.rollback()`, resetting DB state instantly without expensive DDL table creation overhead.

---

### Q14: How does a Continuous Integration (CI) pipeline work in GitHub Actions for Flask?
**Answer**:
GitHub Actions runs a virtual machine on every `git push` defined in `.github/workflows/ci.yml`. It checks out the code, installs Python and dependencies from `requirements.txt`, provisions background services (like Redis or PostgreSQL), executes `pytest --cov=.`, and blocks Pull Requests if tests fail or coverage drops below a minimum threshold (`--cov-fail-under=80`).

---

### Q15: What is the difference between Fakes, Mocks, and Stubs in automated testing?
**Answer**:
*   **Stub**: Provides canned hardcoded answers to calls made during the test.
*   **Mock**: Objects pre-programmed with expectations about calls they should receive (asserting `mock.assert_called_once_with(...)`).
*   **Fake**: A working implementation (like an in-memory SQLite database or in-memory dictionary cache) that takes shortcuts unsuitable for production.
