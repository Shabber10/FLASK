# Day 20: Practice & Technical Interview Questions

---

### Q1: What is the difference between `@cache.cached()` and `@cache.memoize()` in Flask-Caching?
**Answer**:
- **`@cache.cached()`**: Operates on Flask view functions to cache complete HTTP responses (status codes, headers, response body strings). It evaluates the incoming request URI (and optional query string) to generate cache keys.
- **`@cache.memoize()`**: Operates on arbitrary Python functions (views or utility functions). It caches function return values using the function's name and arguments as the cache key.

---

### Q2: Why should `SimpleCache` NOT be used in multi-process production environments like Gunicorn?
**Answer**:
`SimpleCache` stores cached items inside a Python `dict` in the memory of the active worker process. 

When deploying Gunicorn with multiple worker processes (e.g. 4 workers), each worker process maintains its own independent, un-synchronized dictionary. A cache update on Worker #1 is invisible to Workers #2, #3, and #4, leading to inconsistent stale responses. Enterprise production environments require a centralized, shared in-memory cache like **Redis**.

### Q3: What is the Thundering Herd Problem (Cache Stampede) and how do you prevent it?
**Answer**:
The Thundering Herd problem occurs when a heavily accessed cache key (receiving thousands of requests per second) expires. All incoming requests encounter a **Cache Miss** at the same millisecond and simultaneously query the database to re-compute the value, overloading the database server.

Mitigations:
1. **Mutex Locks**: The first request to hit a cache miss acquires a lock to recompute the value, while subsequent requests wait or receive stale data until the lock releases.
2. **Probabilistic Early Expiration**: Background worker tasks re-compute cache keys shortly before the TTL expires.

### Q4: Why is `query_string=True` critical when applying `@cache.cached()` to REST API endpoints?
**Answer**:
Without `query_string=True`, Flask-Caching uses only the URL path (e.g. `/api/products`) as the cache key, ignoring GET parameters. Requests for `/api/products?page=1` and `/api/products?page=2` would return the exact same cached response payload! Setting `query_string=True` includes query parameters in the cache key generation.

### Q5: How do you invalidate a specific memoized function cache when database records update?
**Answer**:
Use `cache.delete_memoized(function_name, *args)`:

```python
@cache.memoize(timeout=600)
def get_user_profile(user_id):
    return User.query.get(user_id)

# Invalidate when profile is updated
@app.route('/users/<int:user_id>/update', methods=['POST'])
def update_profile(user_id):
    # Update DB...
    cache.delete_memoized(get_user_profile, user_id)
```

### Q6: How do Redis and Memcached differ as cache backends for Flask applications?
**Answer**:
- **Memcached**: Extremely simple, high-speed pure in-memory key-value store. Best suited for simple string/object caching without persistence needs.
- **Redis**: Feature-rich in-memory data store supporting advanced data structures (Lists, Hashes, Sets), pub/sub messaging, disk persistence, and atomic operations. Preferred for enterprise applications needing caching, Celery task brokers, and WebSockets.

---

### Q7: What is the difference between `Cache-Control` HTTP headers and server-side caching?
**Answer**:
- **`Cache-Control` Headers**: Instruct the **client browser** or CDN edge proxies (Cloudflare) to store responses locally. Server load is eliminated completely for repeated requests.
- **Server-Side Caching (Flask-Caching)**: Stores data in Redis on the application server. The browser still sends HTTP requests to Flask, but Flask responds in microseconds by skipping database queries.

---

### Q8: What does `cache.clear()` do?
**Answer**:
`cache.clear()` flushes and deletes **all** keys stored inside the cache backend. In production environments sharing a Redis instance, `cache.clear()` should be used with extreme caution to avoid accidentally wiping non-Flask Redis keys.

---

### Q9: How do you set a default global timeout for all Flask-Caching decorators?
**Answer**:
Set `CACHE_DEFAULT_TIMEOUT` in Flask configuration:

```python
app.config['CACHE_DEFAULT_TIMEOUT'] = 300 # 300 seconds (5 minutes)
```

---

### Q10: How can you bypass caching during unit testing?
**Answer**:
Set `CACHE_TYPE = 'NullCache'` in `TestingConfig`. `NullCache` always returns a cache miss (`None`), ensuring tests execute view logic and database queries directly without caching side effects.
