## 1. Why Caching Matters

In high-throughput enterprise web applications, executing expensive database queries, rendering complex Jinja2 templates, or calling external APIs on every single HTTP request degrades performance and scales costs.

**Caching** stores pre-computed result representations in high-speed, in-memory data structures (such as Redis or RAM), serving subsequent requests in microseconds:

```
Without Cache: 250ms per request (High Database CPU & I/O Load)
Browser ---> [ GET /api/analytics ] ---> [ Complex SQL Joins + Aggregations (250ms) ] ---> DB

With Cache: 1.5ms per request (Sub-millisecond latency!)
Browser ---> [ GET /api/analytics ] ---> [ Cache Hit in Redis (1.5ms) ] (Bypasses DB completely!)
```

## 2. Flask-Caching Storage Backends

`Flask-Caching` supports multiple storage backends depending on the deployment environment:

| Cache Type (`CACHE_TYPE`) | Description | Production Ready? |
| :--- | :--- | :--- |
| **`SimpleCache`** | In-memory dictionary on the active Python process | ❌ No (Single process only; fails across Gunicorn workers) |
| **`NullCache`** | Disables caching entirely (always cache miss) | 🧪 Testing / Development |
| **`FileSystemCache`** | Stores cached payloads as files on disk | ⚠️ Small apps |
| **`RedisCache`** | In-memory distributed key-value store (Redis) | ✅ **Enterprise Production Standard** |
| **`MemcachedCache`** | High-speed distributed memory object cache | ✅ Production Standard |

## 3. Cache Invalidation Strategies

Caching introduces a fundamental computer science challenge: **Cache Invalidation** ("Ensuring stale data is updated when underlying database records change").

### 1. Time-To-Live (TTL) Expiration
Every cached item is assigned a `timeout` in seconds. When the TTL expires, the cache automatically purges the item, forcing the next request to re-query the database.

### 2. Event-Driven Explicit Invalidation
When a database update occurs (`POST`, `PUT`, `DELETE`), the view function explicitly invalidates the associated cache keys immediately:

```python
# Clear explicit cache key
cache.delete('popular_products_list')

# Clear memoized function cache for specific argument
cache.delete_memoized(get_user_profile, user_id)
```

## 4. The Thundering Herd Problem (Cache Stampede)

The **Thundering Herd Problem** (or Cache Stampede) occurs when a heavily accessed cache key (e.g. homepage data receiving 10,000 requests/sec) expires. 

Simultaneously, thousands of concurrent requests encounter a **Cache Miss**, causing all requests to hammer the database with expensive queries at the exact same millisecond, crashing the database server!

### Mitigations for Cache Stampedes
1. **Mutex Lock / Probabilistic Early Expiration**: Re-compute cache keys in background before TTL expires.
2. **Stale-While-Revalidate**: Serve stale cached data for a few seconds while 1 background worker updates the cache.
