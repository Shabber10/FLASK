# Day 19: Practice & Technical Interview Questions

This question bank is organized into **3 difficulty tiers**, providing crystal-clear definitions, concrete code examples, and production trade-off analyses.

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is a JSON Web Token (JWT) and what are its 3 components?
**Answer**:
A JSON Web Token (JWT) is an open standard (RFC 7519) defining a compact, self-contained method for securely transmitting information between parties as a JSON object.

A JWT consists of 3 dot-separated Base64Url-encoded strings:
1.  **Header**: Specifies algorithm (`alg: "HS256"`) and token type (`typ: "JWT"`).
2.  **Payload (Claims)**: JSON statements about user identity (`sub`, `exp`, `role`, `jti`).
3.  **Signature**: Cryptographic hash computed over `Base64(Header) + "." + Base64(Payload)` using `JWT_SECRET_KEY`.

---

### Q2: Why are JWTs preferred over browser cookies for mobile and microservice APIs?
**Answer**:
*   **Mobile Clients (iOS / Android)**: Mobile HTTP clients do not automatically handle browser cookie jars. JWTs sent in standard `Authorization: Bearer <token>` headers work universally across all platforms.
*   **CORS Separation**: Avoids cross-domain browser cookie restrictions when SPAs (`app.company.com`) communicate with backend APIs (`api.company.com`).
*   **Horizontal Scalability**: Stateless JWTs require zero server-side session lookups, allowing any server in a cluster to verify tokens independently.

---

### Q3: What is the difference between an Access Token and a Refresh Token?
**Answer**:
*   **Access Token**: Short-lived (e.g. 15 minutes), sent on every API request in the `Authorization: Bearer` header.
*   **Refresh Token**: Long-lived (e.g. 7 days), kept securely and used exclusively at `/api/v1/auth/refresh` to mint new token pairs without requiring the user to re-enter their password.

---

### Q4: Are claims in a JWT payload encrypted?
**Answer**:
No. By default, JWT claims in the payload are **Base64Url encoded and digitally signed**, but **NOT encrypted**. Anyone with access to the token string can decode the Base64 payload. Never store sensitive credentials (passwords, credit cards, SSNs) in a JWT payload.

---

### Q5: What is the purpose of the `sub` and `exp` claims in a JWT?
**Answer**:
*   **`sub` (Subject)**: Identifies the principal user or entity (e.g. `"sub": "101"`).
*   **`exp` (Expiration Time)**: A Unix epoch timestamp after which the token is automatically rejected by the server.

## 🟡 Level 2: Intermediate Questions

### Q6: What is a `jti` (JWT ID) and why is it essential for Token Revocation?
**Answer**:
A `jti` is a unique 128-bit UUID string assigned to every generated token payload. Because JWTs are stateless, the server cannot cancel a token directly. Instead, upon logout, the server extracts the token's `jti` and saves it in a fast Redis cache with a TTL matching the token's expiration. On incoming requests, `@jwt.token_in_blocklist_loader` checks if the `jti` is revoked.

```python
# Extract JTI and store in Redis with TTL
jti = get_jwt()['jti']
ttl = max(int(get_jwt()['exp'] - datetime.now(timezone.utc).timestamp()), 1)
redis_client.setex(f"jwt:revoked:{jti}", ttl, "true")
```

---

### Q7: Why do In-Memory sets (`jwt_blocklist = set()`) fail in production Gunicorn environments?
**Answer**:
In production, Flask runs across multiple worker processes (e.g. Gunicorn with 4 workers). Each worker has its own isolated OS memory space. Logging out on Worker #1 adds the `jti` only to Worker #1's memory. When the next request hits Worker #2, Worker #2's set is empty, and the revoked token is incorrectly accepted. Redis provides centralized, shared memory accessible to all worker processes.

### Q8: How does `@jwt.user_lookup_loader` simplify route handlers in `Flask-JWT-Extended`?
**Answer**:
It registers a callback executed on every `@jwt_required()` request that queries the database using `jwt_data["sub"]` and populates `flask_jwt_extended.current_user`:

```python
@jwt.user_lookup_loader
def user_lookup_callback(_jwt_header, jwt_data):
    return db.session.get(User, int(jwt_data["sub"]))

# In view function:
@app.route('/profile')
@jwt_required()
def profile():
    return jsonify({"username": current_user.username})
```

### Q9: How should an API handle clock drift between different server nodes?
**Answer**:
Configure `JWT_DECODE_LEEWAY`. This adds a small margin of tolerance (e.g. 10 seconds) when evaluating the `exp` claim, preventing valid requests from being rejected due to minor server clock synchronization discrepancies:
```python
app.config['JWT_DECODE_LEEWAY'] = timedelta(seconds=10)
```

### Q10: How do you implement custom JSON error handlers for expired tokens in Flask?
**Answer**:
Use the `@jwt.expired_token_loader` decorator:
```python
@jwt.expired_token_loader
def expired_token_callback(jwt_header, jwt_payload):
    return jsonify({
        "error": {
            "code": 401,
            "type": "TOKEN_EXPIRED",
            "message": "Access token has expired. Please refresh via /api/v1/auth/refresh."
        }
    }), 401
```

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: What is Single-Use Refresh Token Rotation and what attack does it mitigate?
**Answer**:
**Refresh Token Rotation** is a security pattern where using a Refresh Token to get a new Access Token immediately invalidates the used Refresh Token and mints a brand-new Refresh Token.
*   **Attack Mitigated**: Mitigates **Token Replay Attacks**. If an attacker intercepts a Refresh Token, as soon as the legitimate user rotates it, the stolen token's `jti` is revoked. If the attacker later attempts to use the stolen token, the server detects token reuse and can invalidate the entire user session.

---

### Q12: Compare Symmetric (`HS256`) vs. Asymmetric (`RS256`) JWT Signing.
**Answer**:
*   **Symmetric (`HS256`)**: Uses a single shared secret key (`JWT_SECRET_KEY`) for both signing and verifying tokens. Ideal for single monolithic applications.
*   **Asymmetric (`RS256`)**: Uses a **Private Key** (kept only on the Authentication Server) to sign tokens, and a **Public Key** (distributed to downstream microservices) to verify tokens. Downstream services can verify signatures without possessing the ability to forge tokens.

---

### Q13: What are the security tradeoffs between storing JWTs in `localStorage` vs. `httpOnly` Cookies?
**Answer**:
*   **`localStorage`**:
    *   *Pros*: Easy to send in `Authorization: Bearer` headers; immune to CSRF.
    *   *Cons*: Vulnerable to **XSS (Cross-Site Scripting)**. Any injected script can read `localStorage.getItem('token')`.
*   **`httpOnly; Secure; SameSite=Lax` Cookies**:
    *   *Pros*: Immune to JavaScript XSS theft (`document.cookie` is blocked).
    *   *Cons*: Vulnerable to **CSRF**. Requires double-submit CSRF tokens (`JWT_COOKIE_CSRF_PROTECT = True`).

---

### Q14: How does JWT compare to OAuth2 and OpenID Connect (OIDC)?
**Answer**:
*   **JWT**: The *token format standard* (RFC 7519) defining how claims are structured and signed.
*   **OAuth2**: An *authorization framework* (RFC 6749) allowing third-party applications to access user resources without passwords (e.g. "Login with Google"). OAuth2 authorization servers often issue JWTs as access tokens.
*   **OpenID Connect (OIDC)**: An *identity protocol* built on top of OAuth2 that standardizes authentication and introduces an `id_token` JWT containing user profile data.
