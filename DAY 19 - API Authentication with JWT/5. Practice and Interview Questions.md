# Day 19: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from JWT token basics up to token pair refresh flows, JTI blacklisting, and asymmetric RSA token signing.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is a JSON Web Token (JWT)?
**Answer**:
A JSON Web Token (JWT) is a compact, self-contained digital passport used for stateless authentication between a client and a server. It contains cryptographically signed JSON data encoding user identity and permissions.

---

### Q2: Why are JWTs preferred over browser cookie sessions when building mobile app APIs?
**Answer**:
Native mobile applications (iOS and Android) and decoupled frontend applications (React, Angular) do not automatically handle browser cookie jars. JWTs are sent in standard HTTP headers (`Authorization: Bearer <token>`), making them platform-independent and free from cross-domain cookie restrictions.

---

### Q3: What is the format of an Authorization header carrying a JWT?
**Answer**:
```http
Authorization: Bearer <your_jwt_token_string>
```

---

### Q4: Are data claims inside a JWT payload encrypted?
**Answer**:
No. By default, JWT claims in the payload are **Base64 encoded and digitally signed**, but **NOT encrypted**. Anyone can decode the Base64 string to read payload claims. Never store confidential secrets (like raw passwords or credit card numbers) inside a JWT payload.

---

### Q5: What is the difference between an Access Token and a Refresh Token?
**Answer**:
*   **Access Token**: Short-lived (e.g. 15 minutes), sent in API requests to access protected resources.
*   **Refresh Token**: Long-lived (e.g. 7 days), used exclusively at `/auth/refresh` to obtain a fresh access token without forcing the user to re-enter their password.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What are the 3 parts of a JWT string?
**Answer**:
1.  **Header**: Defines the algorithm (`HS256`) and token type (`JWT`).
2.  **Payload**: Contains user claims (`sub`, `exp`, `jti`, `role`).
3.  **Signature**: Cryptographic hash computed over `Base64(Header) + "." + Base64(Payload)` using `JWT_SECRET_KEY`.

---

### Q7: What is a JTI (JWT ID) and why is it used?
**Answer**:
A `jti` is a unique UUID string assigned to every generated JWT token. It allows servers to track individual tokens and blacklist specific revoked tokens on logout before their natural expiration date.

---

### Q8: How does `@jwt.token_in_blocklist_loader` work in `Flask-JWT-Extended`?
**Answer**:
It registers a callback function that `Flask-JWT-Extended` runs automatically on every request. It receives the incoming token's payload, extracts its `jti`, and checks if `jti` exists in a blocklist set or Redis cache. If it returns `True`, the request is rejected with HTTP 401.

---

### Q9: How do you extract custom claims embedded in a JWT during a request?
**Answer**:
Use `get_jwt()` inside a `@jwt_required()` protected view function:
```python
claims = get_jwt()
user_role = claims.get('role')
```

---

### Q10: How do you handle expired tokens gracefully in `Flask-JWT-Extended`?
**Answer**:
Register an `@jwt.expired_token_loader` callback returning a custom JSON error payload and HTTP 401 status code:

```python
@jwt.expired_token_loader
def expired_token_callback(header, payload):
    return jsonify({"error": "Access token expired"}), 401
```

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: What is the fundamental architectural trade-off between Stateless JWTs and Immediate Revocation?
**Answer**:
Pure JWT authentication is **Stateless** (servers do not query a database to validate tokens, achieving massive scalability). However, immediate revocation requires checking a central blocklist (like Redis), re-introducing a small server-side state check. Using short-lived access tokens (15 mins) minimizes the window of risk if blocklist checks are omitted.

---

### Q12: Where should JWTs be stored in client-side Single Page Applications (SPAs) to prevent XSS vs CSRF attacks?
**Answer**:
*   **LocalStorage / SessionStorage**: Immune to CSRF, but vulnerable to XSS script theft if an attacker injects malicious JavaScript.
*   **HttpOnly SameSite Cookies**: Immune to XSS theft, but vulnerable to CSRF if `SameSite` flags and CSRF tokens are not configured properly.
*   **In-Memory (Best Practice)**: Store Access Tokens in JavaScript memory and Refresh Tokens in `HttpOnly SameSite` cookies.

---

### Q13: How does Symmetric (HS256) signing differ from Asymmetric (RS256) signing for JWTs?
**Answer**:
*   **Symmetric (HS256)**: Uses a single shared secret key (`JWT_SECRET_KEY`) for both signing and verifying tokens. Suitable for single monolithic APIs.
*   **Asymmetric (RS256)**: Uses a Private Key to sign tokens on the auth server, and a Public Key to verify tokens across multiple independent microservices.

---

### Q14: What is Token Side-Loading / Custom Claims Injection?
**Answer**:
Injecting extra context attributes into the JWT payload during generation (`@jwt.additional_claims_loader`) so downstream microservices can perform authorization without querying a central database.

---

### Q15: How can an API handle Refresh Token Rotation for enhanced security?
**Answer**:
During each `/auth/refresh` request, invalidate the old Refresh Token and issue a brand-new Refresh Token alongside the Access Token. If an old revoked Refresh Token is ever reused, revoke the entire token family immediately as a potential breach.
