## 1. Why Cookie Sessions Fail for APIs

In [Day 14](file:///c:/Users/SHABBER%20HUSSAIN/Desktop/FLASK/DAY%2014%20-%20Session%20Management%20and%20Cookie%20Security/0.%20Sessions%20and%20Cookie%20Security%20Fundamentals%20for%20Beginners.md), we used browser cookies for sessions. However, browser cookies fail when building modern decoupled APIs:
1.  **Mobile Apps (iOS / Android)**: Native mobile applications do not automatically manage browser cookie jars.
2.  **Cross-Origin (CORS) Restrictions**: Modern single-page web apps (React, Vue) hosted on different domains (`app.company.com`) face browser CORS restrictions when attempting to send cookies to `api.company.com`.
3.  **Stateless Microservices**: Storing session IDs on a server breaks the statelessness required by modern cloud microservices.

To solve this, APIs use **JSON Web Tokens (JWT)**!

---

## 2. What is a JWT (JSON Web Token)?

A **JWT (JSON Web Token)** is a compact, self-contained digital passport. When a user logs in, the API server issues a cryptographically signed JWT string back to the client.

The client stores this token and sends it in the HTTP header of every subsequent request:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

---

## 3. The 3 Parts of a JWT (`Header.Payload.Signature`)

A JWT is a single string separated by two dots (`.`):

```
eyJhbGciOiJIUzI1... . eyJzdWIiOiIxMjM0... . SflKxwRJSMeKKF...
[ 1. HEADER ]      . [ 2. PAYLOAD ]    . [ 3. SIGNATURE ]
```

1.  **Header**: Specifies the hashing algorithm used (e.g. `HS256`).
2.  **Payload (Claims)**: Contains user identity attributes (e.g. `user_id = 42`, `role = "Admin"`, `exp = 1750000000`).
3.  **Signature**: A cryptographic hash computed using the server's secret key (`JWT_SECRET_KEY`). If anyone alters the payload, the signature check fails!

> ⚠️ **Key Rule**: Like Flask session cookies, JWT payloads are Base64 readable, but tamper-proof! **Never put raw passwords inside a JWT payload!**

---

## 4. Access Tokens vs. Refresh Tokens

To balance security and user convenience, modern APIs issue a **Token Pair**:

*   **Access Token**: Short-lived (e.g., 15 minutes). Used to access protected API endpoints. If stolen, it expires quickly!
*   **Refresh Token**: Long-lived (e.g., 7 days). Used exclusively at `/auth/refresh` to request a new access token without requiring the user to re-type their password.

---

## 5. Token Revocation & Blacklisting

Because JWTs are stateless, the server does not store active tokens in a database. But what if a user clicks "Logout" or their laptop is stolen?

To revoke a JWT before its expiration date, servers store the token's unique ID (**JTI - JWT ID**) inside a fast cache (like **Redis**). This is called **Token Blacklisting**!
