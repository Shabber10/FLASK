## 1. Extension Configuration & Initialization

### 📖 Definitions of Configuration Settings

| Config Key | Definition | Default | Production Value Example |
| :--- | :--- | :--- | :--- |
| **`JWT_SECRET_KEY`** | The symmetric secret string used to compute and verify HMAC-SHA256 signatures. | `None` (Required) | `os.environ.get("JWT_SECRET_KEY")` (32+ bytes) |
| **`JWT_ACCESS_TOKEN_EXPIRES`** | The duration a generated Access Token remains valid before expiring. | `timedelta(minutes=15)` | `timedelta(minutes=15)` |
| **`JWT_REFRESH_TOKEN_EXPIRES`** | The duration a generated Refresh Token remains valid. | `timedelta(days=30)` | `timedelta(days=7)` |
| **`JWT_DECODE_LEEWAY`** | Time window (in seconds) allowed for server clock drift when evaluating `exp`. | `0` seconds | `timedelta(seconds=10)` |
| **`JWT_ALGORITHM`** | Cryptographic algorithm used for signing tokens (`HS256`, `RS256`, `ES256`). | `"HS256"` | `"HS256"` (Monolith) / `"RS256"` (Microservices) |

---

### 💻 Code Example: Initializing `Flask-JWT-Extended`

```python
import os
from datetime import timedelta
from flask import Flask
from flask_jwt_extended import JWTManager

app = Flask(__name__)

# 1. Load cryptographic signing secret from environment (Day 12 pattern)
app.config['JWT_SECRET_KEY'] = os.environ.get(
    'JWT_SECRET_KEY', 
    'dev-fallback-secret-key-replace-in-production-12345678'
)

# 2. Configure Token Lifespans
app.config['JWT_ACCESS_TOKEN_EXPIRES'] = timedelta(minutes=15)
app.config['JWT_REFRESH_TOKEN_EXPIRES'] = timedelta(days=7)

# 3. Configure Clock-Skew Leeway (Handles minor timestamp mismatch across cluster nodes)
app.config['JWT_DECODE_LEEWAY'] = timedelta(seconds=10)

# 4. Initialize Extension Instance
jwt = JWTManager(app)
```

## 2. Generating Tokens: `create_access_token` & `create_refresh_token`

### 📖 Definitions:
*   **`create_access_token(identity, additional_claims=None, expires_delta=None)`**: Generates a signed Access Token containing the subject `sub=identity` and optional custom claims.
*   **`create_refresh_token(identity, additional_claims=None, expires_delta=None)`**: Generates a signed long-lived Refresh Token containing `type="refresh"`.

### 💻 Code Example: Login Endpoint Issuing Token Pairs

```python
from flask import request, jsonify
from flask_jwt_extended import create_access_token, create_refresh_token
from werkzeug.security import check_password_hash

# Mock user database
users_db = {
    "alice_dev": {"id": 101, "password_hash": "...", "role": "Developer", "email": "alice@company.com"}
}

@app.route('/api/v1/auth/login', methods=['POST'])
def login():
    data = request.get_json() or {}
    username = data.get('username')
    password = data.get('password')

    user = users_db.get(username)
    if not user or not check_password_hash(user['password_hash'], password):
        return jsonify({"error": "Unauthorized", "message": "Invalid username or password"}), 401

    # IMPORTANT: Identity MUST be a string in Flask-JWT-Extended v4.4+
    user_id_str = str(user['id'])

    # Issue token pair embedding custom role claims
    access_token = create_access_token(
        identity=user_id_str,
        additional_claims={
            "role": user['role'],
            "email": user['email']
        }
    )
    refresh_token = create_refresh_token(identity=user_id_str)

    return jsonify({
        "status": "success",
        "access_token": access_token,
        "refresh_token": refresh_token,
        "token_type": "Bearer",
        "expires_in_seconds": 900
    }), 200
```

## 3. Resolving Users with Identity & Lookup Loaders

### 📖 Definitions:
*   **`@jwt.user_identity_loader`**: Defines how to serialize a user object into the JWT `sub` claim string.
*   **`@jwt.user_lookup_loader`**: A callback executed automatically on every `@jwt_required()` request that queries the database and populates `flask_jwt_extended.current_user`.

### 💻 Code Example:

```python
from flask_jwt_extended import current_user

@jwt.user_identity_loader
def user_identity_lookup(user):
    """Extract user ID as string for JWT 'sub' claim."""
    return str(user.id if hasattr(user, 'id') else user)


@jwt.user_lookup_loader
def user_lookup_callback(_jwt_header, jwt_data):
    """
    Called on every @jwt_required() request.
    jwt_data['sub'] holds the user ID string.
    Returns the user model instance or None.
    """
    user_id = int(jwt_data["sub"])
    return users_db.get(user_id)  # Or User.query.get(user_id)
```

## 4. Protecting Routes with `@jwt_required`

### 📖 Definitions of Decorator Parameters:

| Decorator | Meaning | Use Case |
| :--- | :--- | :--- |
| **`@jwt_required()`** | Requires a valid, unexpired, non-revoked **Access Token**. | Protecting standard API endpoints (e.g. `/profile`, `/orders`). |
| **`@jwt_required(refresh=True)`** | Requires a valid **Refresh Token**. | The `/auth/refresh` endpoint exclusively. |
| **`@jwt_required(optional=True)`** | Allows requests without tokens, but parses claims if a token is present. | Public feeds with personalized features for logged-in users. |
| **`@jwt_required(fresh=True)`** | Requires a "fresh" token generated via recent password entry. | High-security actions (e.g. changing passwords, deleting accounts). |

---

### 💻 Code Example: Protected Profile & Admin Route

```python
from flask_jwt_extended import jwt_required, get_jwt, get_jwt_identity, current_user

@app.route('/api/v1/profile', methods=['GET'])
@jwt_required()
def get_user_profile():
    """Returns profile data for the authenticated user."""
    # Method 1: Use current_user populated by user_lookup_loader
    # Method 2: Extract custom claims from get_jwt()
    claims = get_jwt()
    
    return jsonify({
        "user_id": current_user['id'],
        "username": current_user['username'],
        "role": claims.get('role'),
        "token_jti": claims.get('jti')
    }), 200


@app.route('/api/v1/admin/dashboard', methods=['GET'])
@jwt_required()
def admin_dashboard():
    """RBAC Role Check inside view."""
    claims = get_jwt()
    if claims.get('role') != "Admin":
        return jsonify({"error": "Forbidden", "message": "Admin privileges required"}), 403

    return jsonify({"message": "Welcome to the Admin Command Center"}), 200
```

## 5. Symmetric (HS256) vs. Asymmetric (RS256) Key Signing

### 📖 Definitions:
*   **Symmetric Signing (`HS256`)**: Both the token creator and token verifier share the exact same secret key (`JWT_SECRET_KEY`).
*   **Asymmetric Signing (`RS256`)**: The Auth Server uses an **RSA Private Key** to sign tokens. Downstream microservices only possess the **RSA Public Key** to verify signatures.

```
┌────────────────────────────────┐                 ┌────────────────────────────────┐
│   Auth Microservice (Issuer)   │                 │ Resource Microservice (Reader) │
│   - Holds RSA Private Key      │ ──[ JWT Token ]─>│ - Holds RSA Public Key ONLY    │
│   - Signs Tokens               │                 │ - Verifies Signatures          │
│   - CANNOT BE FORGED!          │                 │ - CANNOT FORGE TOKENS!         │
└────────────────────────────────┘                 └────────────────────────────────┘
```

---

### 💻 Code Example: Configuring RS256 in Flask

```python
# Generate RSA Keys with OpenSSL:
# openssl genrsa -out jwt_private.pem 2048
# openssl rsa -in jwt_private.pem -pubout -out jwt_public.pem

with open("jwt_private.pem", "r") as f:
    app.config["JWT_PRIVATE_KEY"] = f.read()

with open("jwt_public.pem", "r") as f:
    app.config["JWT_PUBLIC_KEY"] = f.read()

app.config["JWT_ALGORITHM"] = "RS256"
```
