# Day 27: Practice & Technical Interview Questions

---

### Q1: Why are WebSockets mandatory for financial trading applications instead of standard HTTP Polling?
**Answer**:
High-frequency financial trading requires sub-50ms market price updates. 

HTTP short polling introduces HTTP request/response header overhead, high latency, and severe server CPU load. WebSockets maintain a persistent, full-duplex TCP socket, allowing the server to push price ticks to thousands of connected clients instantly with zero header overhead per message.

---

### Q2: What is the role of Redis Pub/Sub in a multi-process real-time WebSocket cluster?
**Answer**:
In production, Flask applications run across multiple Gunicorn worker processes. If Worker #1 receives a new market tick from an exchange API, clients connected to Worker #2 would not receive the update. 

Redis Pub/Sub acts as a central message backplane. Worker #1 publishes the tick to a Redis channel, and Redis instantly broadcasts the message to all Gunicorn worker processes so their WebSocket clients receive the update.

### Q3: How do `socketio.start_background_task()` and `time.sleep()` interact in Flask-SocketIO?
**Answer**:
Standard `time.sleep()` blocks the entire operating system thread. In cooperative async WSGI servers (Eventlet/Gevent), standard `time.sleep()` freezes all active WebSocket connections. 

`socketio.start_background_task()` spawns a cooperative greenlet, and `socketio.sleep()` yields execution back to the event loop without blocking other WebSockets.

### Q4: How do room subscriptions (`join_room`) optimize network bandwidth in financial streaming apps?
**Answer**:
A trading platform may track 10,000 stock ticker symbols. Broadcasting every tick to all 50,000 connected users would crash client browsers and exhaust network bandwidth. 

Calling `join_room('AAPL')` subscribes traders strictly to the symbols in their portfolio. Emitting events with `to='AAPL'` delivers ticks *only* to interested clients.

### Q5: What happens if a WebSocket client experiences temporary network degradation (Event Backpressure)?
**Answer**:
If a client connection stalls, WebSocket buffers on the server fill up rapidly. Server engines implement buffer drop policies or rate throttlers to drop stale ticks for slow clients rather than exhausting server RAM.

### Q6: How do you handle client authentication during WebSocket connection handshakes in Flask-SocketIO?
**Answer**:
Authenticate clients inside the `@socketio.on('connect')` event handler by verifying JWT bearer tokens passed in the query string or `auth` payload:

```python
@socketio.on('connect')
def connect_handler(auth):
    token = auth.get('token') if auth else None
    user = verify_jwt_token(token)
    if not user:
        return False # Rejects connection
```

### Q7: What is the difference between `socketio.emit()` and `emit()` in Flask-SocketIO?
**Answer**:
- `emit()`: Used inside active socket event handlers (e.g. `@socketio.on('subscribe')`). It automatically infers the current client's session ID (`request.sid`).
- `socketio.emit()`: Used outside request contexts (e.g. inside background threads or Celery tasks) where no active HTTP/Socket request context exists. Requires explicitly specifying `to=room_name`.

### Q8: How do you ensure high-performance rendering of live price updates in the browser DOM?
**Answer**:
Avoid expensive DOM re-paints. Modify existing DOM element text nodes directly (`element.innerText = price`) or use HTML5 Canvas / WebGL charting libraries (TradingView, Lightweight Charts) rather than re-rendering HTML template strings on every tick.

---

### Q9: What happens if a Gunicorn worker process executing a background stream crashes?
**Answer**:
Process supervisors (Systemd / Docker) automatically restart the crashed worker process. Additionally, using standalone worker daemons or Celery for ticker ingestion prevents background worker crashes from interrupting WSGI web servers.

---

### Q10: How do you protect financial order placement WebSocket events against replay attacks?
**Answer**:
Order placement payloads must include short-lived timestamps and unique nonces. The server validates that the timestamp falls within a strict 5-second window and ensures the nonce has not been previously processed.
