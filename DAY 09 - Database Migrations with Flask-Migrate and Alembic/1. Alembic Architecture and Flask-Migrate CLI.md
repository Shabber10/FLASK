# Day 09: Alembic Architecture & Flask-Migrate CLI

Welcome to **Day 09** of the 30-Day Enterprise Flask Masterclass! Today, we examine database schema evolution, Alembic migration architecture, `Flask-Migrate` integration, and CLI migration management workflows.

---

## 1. Why `db.create_all()` is Not Enough

In initial development, `db.create_all()` creates missing database tables defined in SQLAlchemy models. However, `db.create_all()` has a major limitation:

> **`db.create_all()` NEVER alters existing tables.** If you add a new column, change a column type, or drop a constraint on an existing model, `db.create_all()` ignores the change!

In production software development, dropping and recreating tables destroys production data. Enterprise applications rely on **Database Schema Migrations** to apply incremental, version-controlled schema transformations.

---

## 2. Alembic & Flask-Migrate Architecture

**Alembic** is the lightweight database migration tool written for SQLAlchemy. **Flask-Migrate** wraps Alembic, exposing migration commands directly through the `flask db` CLI interface.

```
+-------------------+      Generates Revision Script      +---------------------------------+
|  Flask-SQLAlchemy | --------------------------------->  |   migrations/versions/          |
|    Model Definition|  `flask db migrate -m "add_bio"`   |   a1b2c3d4_add_bio.py           |
+-------------------+                                     +----------------+----------------+
                                                                           |
                                                           Executes SQL    | `flask db upgrade`
                                                           Transformation  v
                                                          +---------------------------------+
                                                          | Target Database (SQLite/PG/MySQL)|
                                                          | Table: `alembic_version`        |
                                                          +---------------------------------+
```

---

## 3. The `migrations/` Directory Structure

Executing `flask db init` generates a `migrations/` repository in your project root:

```
migrations/
├── env.py              # Configuration script executed during migration commands
├── README              # Documentation file
├── script.py.mako      # Mako template used to generate new revision files
└── versions/           # Folder containing version-controlled Python migration scripts
    ├── 1a2b3c4d_initial_migration.py
    └── 5e6f7g8h_add_profile_bio.py
```

---

## 4. The Four Core `flask db` CLI Commands

### 1. `flask db init`
Initializes a new `migrations/` directory in the project root. Runs once per application lifecycle.

### 2. `flask db migrate -m "Description of changes"`
Compares active `Flask-SQLAlchemy` models against the target database schema, generating an autogenerated Python migration revision script in `migrations/versions/`.

### 3. `flask db upgrade [revision]`
Applies pending migration revision scripts to the database engine, advancing the schema to the target version and updating the `alembic_version` table.

### 4. `flask db downgrade [revision]`
Rolls back the database schema to a specified prior revision head, executing `downgrade()` functions inside revision scripts.

---

## 5. Helpful Migration Inspection Commands

- `flask db current`: Displays the current revision hash recorded in the database's `alembic_version` table.
- `flask db heads`: Displays the latest revision hash available in `migrations/versions/`.
- `flask db history`: Displays a chronological list of all migration revisions.
- `flask db stamp <revision>`: Sets the `alembic_version` table value to a specific revision hash without executing any migration scripts (useful for resolving out-of-sync environments).
