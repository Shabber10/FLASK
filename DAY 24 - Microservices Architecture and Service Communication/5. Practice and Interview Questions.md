# Day 24: Practice & Technical Interview Questions

---

### Q1: What are the main trade-offs between a Monolithic Architecture and a Microservices Architecture?
**Answer**:
- **Monolith**: Simple single codebase, easy deployment, local in-memory function calls, and single ACID database transactions. However, as the app grows, code becomes tightly coupled, independent domain scaling is impossible, and a single bug can bring down the entire system.
- **Microservices**: Independent deployment, independent domain scaling, polyglot technology stacks, and failure isolation. However, it introduces network latency overhead, distributed data consistency challenges, complex deployment orchestration, and distributed tracing requirements.

---

### Q2: What is the Database-per-Service pattern and why is direct cross-service database access prohibited?
**Answer**:
In the Database-per-Service pattern, each microservice owns its private database tables. Direct SQL joins or queries across another microservice's database are strictly prohibited. 

This guarantees strict domain encapsulation, allowing team owners to alter database schemas or migrate storage engines (e.g. Postgres to MongoDB) without breaking external services.

---

### Q3: What is the API Gateway pattern and what responsibilities does it handle?
**Answer**:
An API Gateway is a reverse proxy entry point that sits between external clients and internal microservices. 

Responsibilities include:
1. **Request Routing**: Forwarding API calls (`/api/v1/users`) to specific microservice instances.
2. **Cross-Cutting Concerns**: Authentication/JWT verification, SSL termination, and rate limiting.
3. **Response Aggregation**: Combining data from multiple internal microservices into a single JSON payload.

---

### Q4: How does gRPC differ from standard REST APIs and why is it faster for internal microservice calls?
**Answer**:
- **REST**: Uses plaintext JSON payloads over HTTP/1.1. Incurs string serialization/deserialization CPU overhead and HTTP/1.1 head-of-line blocking.
- **gRPC**: Uses strongly typed binary **Protocol Buffers (`.proto`)** over HTTP/2 multiplexed streams. Binary serialization is **7x to 10x faster** than JSON with significantly smaller network payload sizes.

---

### Q5: What is the Circuit Breaker Pattern and how does it prevent Cascading Failures?
**Answer**:
If Microservice A synchronously calls Microservice B, and Microservice B experiences an outage or hangs, Microservice A worker threads become blocked waiting for network timeouts, leading to resource exhaustion across the entire cluster (a **Cascading Failure**).

A Circuit Breaker monitors call failure rates. When failures exceed a threshold, the breaker trips to **`OPEN`**, immediately failing subsequent requests (HTTP 503) without attempting the downstream network call, shielding worker threads and giving the failing service time to recover.

---

### Q6: What are the three states of a Circuit Breaker?
**Answer**:
1. **`CLOSED`**: Normal state. All requests pass through to the downstream service.
2. **`OPEN`**: Failure threshold exceeded. All requests fail fast immediately without making downstream network calls.
3. **`HALF-OPEN`**: After a timeout interval, the breaker allows a limited number of trial requests through. If successful, it resets to `CLOSED`; if failures persist, it returns to `OPEN`.

---

### Q7: How do distributed transactions work in microservices without traditional ACID database transactions?
**Answer**:
Because microservices use independent databases, cross-service ACID transactions are impossible. Microservices handle distributed consistency using the **Saga Pattern**:
- **Choreography / Orchestration**: A sequence of local database transactions. If one step fails (e.g. payment declined), compensating transactions are triggered backwards to undo previous steps (e.g. release reserved inventory).

---

### Q8: Why is setting explicit HTTP timeouts mandatory for inter-service communication?
**Answer**:
Without timeouts (e.g. calling `requests.get(url)` without `timeout=2.0`), a network request can hang indefinitely if the target server drops packets or deadlocks. This holds the caller's worker thread open indefinitely, rapidly consuming all available web server processes.

---

### Q9: What is Distributed Tracing and how do Correlation IDs work?
**Answer**:
Distributed Tracing tracks request execution flows across multiple microservices. When a request enters the API Gateway, the gateway generates a unique **Trace ID / Correlation ID** (e.g. `X-Correlation-ID: uuid`). 

Every microservice forwards this header in subsequent downstream HTTP or gRPC calls, allowing log aggregation tools (Jaeger, Zipkin, Datadog) to visualize the entire distributed request lifecycle.

---

### Q10: What is Service Discovery and why is it required in container environments?
**Answer**:
In containerized environments (Kubernetes, Docker Swarm), container IP addresses are dynamic and ephemeral. **Service Discovery** registries maintain a live mapping of service names to active container IP addresses and ports, routing requests dynamically.
