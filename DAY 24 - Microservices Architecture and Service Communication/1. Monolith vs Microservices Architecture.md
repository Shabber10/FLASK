# Day 24: Monolith vs. Microservices Architecture

Welcome to **Day 24** of the 30-Day Enterprise Flask Masterclass! Today, we explore distributed systems architecture, Monolithic vs Microservices trade-offs, Database-per-Service patterns, API Gateways, and service discovery.

---

## 1. Monolith vs. Microservices Comparison

As enterprise applications expand in feature complexity and engineering team size, monolithic codebases present scaling challenges:

```
Monolithic Architecture:
+-------------------------------------------------------------+
| Single Flask Application (Auth + Orders + Payments + Search) |
+-------------------------------------------------------------+
                              |
                              v
                  Single Shared Database (RDBMS)

Microservices Architecture:
                    API Gateway (Port 80)
                              |
       +----------------------+----------------------+
       |                      |                      |
       v                      v                      v
+--------------+       +--------------+       +--------------+
| User Service |       |Order Service |       |Payment Server|
| (Flask API)  |       | (Flask API)  |       | (Flask API)  |
+--------------+       +--------------+       +--------------+
       |                      |                      |
       v                      v                      v
User Database          Order Database         Payment Database
```

| Feature | Monolithic Architecture | Microservices Architecture |
| :--- | :--- | :--- |
| **Codebase** | Single repository containing all domains | Decoupled, independent repositories per domain |
| **Database** | Shared relational database | **Database-per-Service** (Private data stores) |
| **Scaling** | Scale entire application monolith together | Scale individual bottleneck services independently |
| **Tech Stack** | Unified language and frameworks | Polyglot (Python, Go, Node.js per service) |
| **Complexity**| Low deployment complexity; high code coupling | High network complexity; distributed tracing required |

## 2. Core Microservices Design Patterns

### 1. API Gateway Pattern
An **API Gateway** acts as the single reverse proxy entry point for external clients. It routes incoming client requests to internal microservices, handles cross-cutting concerns (Authentication, JWT validation, Rate Limiting, TLS termination), and aggregates responses.

### 2. Database-per-Service Pattern
Each microservice **must own its private database**. Direct SQL queries into another microservice's database tables are strictly forbidden! All cross-domain data interactions must occur via public API endpoints or async domain events.

### 3. Service Discovery
Microservice IP addresses change dynamically in container environments (Kubernetes, AWS ECS). Service discovery registries (Consul, Eureka, CoreDNS) dynamically resolve service names (e.g. `http://user-service:5000`) to healthy instances.
