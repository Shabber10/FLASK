# Day 30: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from deployment basics up to Gunicorn worker math, Nginx reverse proxying, Docker containerization, and enterprise cloud architecture.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: Why should Flask's built-in development server (`flask run`) never be used in production?
**Answer**:
The built-in Werkzeug development server is single-threaded by default, lacks process management, crashes under load, lacks SSL HTTPS termination, and lacks DDoS protections required for high-concurrency production web traffic.

---

### Q2: What is Gunicorn and what role does it play in Flask deployments?
**Answer**:
Gunicorn is a UNIX WSGI HTTP application server. It sits between Nginx and Flask, spawning and managing a pool of parallel Python worker processes to handle multiple concurrent HTTP requests.

---

### Q3: What is Nginx and why is it placed in front of Gunicorn?
**Answer**:
Nginx is a high-performance reverse proxy server. It handles public SSL/TLS HTTPS encryption, serves static files (images, CSS, JS) directly at lightning speed, protects against slowloris/DDoS attacks, and proxies application API requests to Gunicorn.

---

### Q4: What is Docker and why is containerization useful?
**Answer**:
Docker packages application source code, Python libraries, environment configurations, and operating system binaries into an isolated, portable container. It ensures the application runs identically across development laptops, staging environments, and production cloud servers.

---

### Q5: What is the difference between `/healthz` and `/readyz` endpoints?
**Answer**:
*   `/healthz` (Liveness Probe): Checks if the Flask web server process is alive.
*   `/readyz` (Readiness Probe): Checks if the Flask app AND backing services (PostgreSQL & Redis) are ready to accept user traffic.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the recommended formula for calculating Gunicorn worker processes?
**Answer**:
$$\text{Workers} = (2 \times \text{CPU Cores}) + 1$$
This formula balances CPU utilization and I/O wait times, preventing thread starvation while avoiding excessive process context switching.

---

### Q7: What are the key rules of the 12-Factor App methodology for Flask applications?
**Answer**:
1. Store all secret configurations (DB URLs, API keys) in environment variables.
2. Treat backing services (PostgreSQL, Redis) as attached network resources.
3. Keep Flask application processes completely stateless.
4. Stream logs directly to `sys.stdout` as JSON event streams.

---

### Q8: Why should Docker containers run under a non-root system user (`USER appuser`)?
**Answer**:
Running a container as `root` creates a severe security risk. If an attacker exploits an application vulnerability inside the container, running as non-root prevents them from gaining root privileges on the underlying host operating system.

---

### Q9: What does `docker-compose` do?
**Answer**:
`docker-compose` is a tool for defining and orchestrating multi-container Docker applications (e.g. launching Flask API, PostgreSQL, Redis, Celery Worker, and Nginx together with shared virtual networks and persistent volumes via `docker-compose.yml`).

---

### Q10: How do you handle database migrations during automated production deployments?
**Answer**:
Execute `flask db upgrade` in automated CI/CD deployment pipeline hooks before launching new application containers, ensuring the database schema matches new code requirements without dropping data.

---

## 🔴 Level 3: Advanced & Enterprise Capstone Architect Questions

### Q11: How do Blue-Green Deployments achieve zero-downtime production updates?
**Answer**:
Blue-Green Deployment maintains two identical production environments:
*   **Blue (Live)**: Currently receiving 100% of user traffic via the router/Nginx.
*   **Green (Idle)**: New application version is deployed and tested.
Once Green passes readiness tests, Nginx instantly switches traffic to Green with zero downtime!

---

### Q12: How does Nginx perform SSL/TLS Termination?
**Answer**:
SSL Termination occurs when Nginx handles the heavy CPU operations of decrypting incoming HTTPS requests on Port 443 and encrypting outgoing HTTPS responses. Requests passed from Nginx to Gunicorn over local loopback (`127.0.0.1:8000`) use plain HTTP, freeing Flask from SSL computation overhead.

---

### Q13: What happens when a Gunicorn worker process crashes due to an out-of-memory (OOM) exception?
**Answer**:
Gunicorn's master process monitors worker process health. If a worker process dies, the master process immediately spawns a fresh worker process to replace it, ensuring continuous service availability.

---

### Q14: How do you prevent database connection pool exhaustion when scaling Gunicorn across multiple Docker container replicas?
**Answer**:
Use a database connection proxy like **PgBouncer** in front of PostgreSQL. PgBouncer multiplexes thousands of incoming Gunicorn worker pool connections down to a small, fixed number of active PostgreSQL database server connections.

---

### Q15: Looking back across all 30 Days of the Flask Masterclass, what are the 5 pillars of Enterprise Flask Application Architecture?
**Answer**:
1. **Modular Architecture**: Application Factory (`create_app()`) + Blueprints + Environment Configs.
2. **Data & Storage**: SQLAlchemy ORM + Migrations (Flask-Migrate) + Marshmallow Serialization + Redis Caching.
3. **Security & Access**: Passlib/Bcrypt + JWT Authentication + RBAC + CORS + Flask-Talisman HTTP Headers.
4. **Asynchronous Processing**: Celery Background Workers + Redis Broker + WebSockets (Flask-SocketIO) + `async`/`await`.
5. **Production Readiness**: Pytest Test Suites + Structured JSON Logging + Correlation IDs + Docker + Nginx + Gunicorn.
