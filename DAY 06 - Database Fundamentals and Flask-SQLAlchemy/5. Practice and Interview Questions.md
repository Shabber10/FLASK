### Q1: What is the difference between legacy `Model.query.all()` and SQLAlchemy 2.0 `db.select()` syntax?
**Answer**:
- `Model.query`: Implicit legacy query syntax specific to Flask-SQLAlchemy 1.x/2.x. It binds queries directly to model classes, making raw SQL composition and multi-table joins less transparent.
- `db.select(Model)`: The modern 2.0+ standard across all SQLAlchemy frameworks. It explicitly constructs select statement AST objects that are executed against `db.session.execute()`, ensuring consistent, type-safe query building and better async support.

```python
# Modern 2.0 Standard
stmt = db.select(User).where(User.is_active == True)
users = db.session.execute(stmt).scalars().all()
```

### Q2: Explain the Unit of Work pattern in Flask-SQLAlchemy (`db.session`).
**Answer**:
The Unit of Work pattern maintains a list of objects affected by a business transaction. Instead of executing SQL queries immediately upon object modification, `db.session` tracks object states (Transient, Pending, Persistent, Deleted) in memory and flushes changes to the database in a single optimized SQL transaction batch when `db.session.commit()` is called.

---

### Q3: What is the difference between `db.session.flush()` and `db.session.commit()`?
**Answer**:
- `db.session.flush()`: Issues SQL statements (`INSERT`, `UPDATE`, `DELETE`) to the database transaction buffer. Primary key IDs are generated and accessible, but changes are **not yet permanently committed** to disk and can be rolled back.
- `db.session.commit()`: Calls `flush()` if needed, permanently commits the open database transaction to disk, and closes the transaction block.

---

### Q4: Why is `db.session.rollback()` critical inside exception blocks during database operations?
**Answer**:
If an exception occurs during a database transaction (e.g. unique constraint violation or connection error), `db.session` transitions into an invalid/failed state. Any subsequent database operations attempted on the un-rolledback session raise `InvalidRequestError: This Session's transaction has been rolled back due to a previous exception`. Calling `db.session.rollback()` clears pending failed SQL operations and restores the session to a clean state.

### Q5: How do `server_default` and `default` differ in Flask-SQLAlchemy column definitions?
**Answer**:
- `default`: Evaluates the default value **in Python code** at the application layer before sending the INSERT statement (e.g. `default=datetime.utcnow`).
- `server_default`: Configures a default value constraint **inside the database DDL schema** itself (e.g. `server_default=db.func.now()` or `server_default='0'`). If a raw SQL query or external tool inserts a row directly into the database, `server_default` still executes.

### Q6: What does `db.session.get(Model, pk_val)` do, and why is it preferred over `db.select(Model).where(Model.id == pk_val)`?
**Answer**:
`db.session.get(Model, pk_val)` looks up an entity by primary key. It first checks the `db.session` **identity map** (in-memory cache). If the object with that primary key is already loaded in the active session, `get()` returns it immediately **without issuing an SQL query to the database server**, making it faster than constructing a full `db.select()` statement.

### Q7: Explain the five object lifecycle states in SQLAlchemy.
**Answer**:
1. **Transient**: Created in Python (`user = User()`), not added to session.
2. **Pending**: Added to session via `db.session.add(user)`, awaiting flush/commit.
3. **Persistent**: Exists in session and has a corresponding row in the database table with a primary key.
4. **Deleted**: Marked for deletion inside session, SQL `DELETE` executed upon commit.
5. **Detached**: Session closed or expunged; object contains data but is disconnected from active DB session updates.

### Q8: What does `SQLALCHEMY_TRACK_MODIFICATIONS = False` do and why should it always be disabled?
**Answer**:
`SQLALCHEMY_TRACK_MODIFICATIONS` was an early Flask-SQLAlchemy event tracking system that monitored object modifications and emitted signals on every change. It consumes significant extra memory overhead. Setting it to `False` disables this legacy signal system, improving application performance.

### Q9: How do `db.Numeric(precision, scale)` and `db.Float` differ for storing financial transactions?
**Answer**:
- `db.Float`: Uses binary floating-point representation (`IEEE 754`). It suffers from rounding inaccuracies (e.g. `0.1 + 0.2 != 0.3`), making it unsuitable for financial data.
- `db.Numeric(precision, scale)` (or `db.Decimal`): Uses exact decimal representation in the database and maps to Python's `decimal.Decimal` class, ensuring exact currency calculations without rounding errors.

### Q10: How do you configure SQLAlchemy engine connection pooling for high-concurrency production deployments?
**Answer**:
Pass `SQLALCHEMY_ENGINE_OPTIONS` in application configuration:

```python
app.config['SQLALCHEMY_ENGINE_OPTIONS'] = {
    'pool_size': 15,       # Permanent active database connections in pool
    'max_overflow': 30,    # Temporary connections allowed above pool_size under heavy load
    'pool_recycle': 1800,  # Recycle stale idle connections every 30 minutes
    'pool_timeout': 30     # Seconds to wait for an available pool connection before error
}
```
