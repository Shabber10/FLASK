# Day 06: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from absolute database fundamentals up to SQLAlchemy 2.0 query patterns and transaction safety.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is a Database and why can't we just store data in Python variables?
**Answer**:
A Database is software designed to store, search, and manage data permanently on a computer's hard drive. Standard Python variables exist only in RAM memory and are completely wiped clean whenever the Python process finishes or restarts.

---

### Q2: What is a Relational Database (SQL) and what are Tables, Columns, and Rows?
**Answer**:
A Relational Database organizes data into grid structures called **Tables** (like Excel spreadsheets):
*   **Table**: Grid holding related records (e.g. `users`).
*   **Column**: A specific attribute field across all records (e.g. `email`).
*   **Row**: A single item in the table containing values for each column.

---

### Q3: What is a Primary Key and why does every table need one?
**Answer**:
A Primary Key is a unique identifier assigned to every single row in a table (like an ID number or passport number). It ensures that every record can be individually located, updated, or deleted without accidentally modifying other rows.

---

### Q4: What is an ORM (Object-Relational Mapper) and what does Flask-SQLAlchemy do?
**Answer**:
An ORM is a translator connecting Python classes to SQL database tables. Flask-SQLAlchemy allows developers to define models as Python classes (`class User(db.Model)`) and perform database operations in pure Python without writing raw SQL query strings.

---

### Q5: What is SQLite and why is it used in Flask development?
**Answer**:
SQLite is a lightweight, zero-configuration database engine that stores an entire database inside a single local file (`app.db`). It requires no background server setup, making it ideal for rapid local development and testing.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the difference between legacy `Model.query.all()` and SQLAlchemy 2.0 `db.select()` syntax?
**Answer**:
*   `Model.query`: Legacy query syntax specific to older Flask-SQLAlchemy releases. It binds queries directly to model classes, making multi-table joins less explicit.
*   `db.select(Model)`: The modern 2.0+ standard across all SQLAlchemy frameworks. It explicitly constructs select statement AST objects that are executed against `db.session.execute()`, ensuring consistent, type-safe query building.

```python
# Modern 2.0 Standard
stmt = db.select(User).where(User.is_active == True)
users = db.session.execute(stmt).scalars().all()
```

---

### Q7: What does `db.session.get(Model, pk_val)` do, and why is it preferred over `db.select(Model).where(Model.id == pk_val)`?
**Answer**:
`db.session.get(Model, pk_val)` looks up an entity by primary key. It first checks the `db.session` **identity map** (in-memory cache). If the object with that primary key is already loaded in the active session, `get()` returns it immediately **without issuing an SQL query to the database server**, making it faster.

---

### Q8: What is the difference between `db.session.flush()` and `db.session.commit()`?
**Answer**:
*   `db.session.flush()`: Issues pending SQL statements (`INSERT`, `UPDATE`, `DELETE`) to the database transaction buffer. Primary key IDs are generated, but changes are **not yet saved permanently to disk** and can be rolled back.
*   `db.session.commit()`: Flushes pending SQL statements and **permanently commits** the transaction to disk.

---

### Q9: Why is `db.session.rollback()` critical inside exception blocks during database operations?
**Answer**:
If an exception occurs during a database transaction (e.g. unique constraint violation), `db.session` enters a poisoned/failed state. Any subsequent database operations attempted on the session raise `InvalidRequestError`. Calling `db.session.rollback()` clears pending failed SQL queries and restores the session to a clean state.

---

### Q10: How do `default` and `server_default` differ in Flask-SQLAlchemy column definitions?
**Answer**:
*   `default`: Evaluates the default value **in Python code** before sending the INSERT statement (e.g. `default=datetime.utcnow`).
*   `server_default`: Configures a default value constraint **inside the database DDL schema** itself (e.g. `server_default=db.func.now()`). If an external tool inserts a row directly into the database, `server_default` still executes.

---

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Explain the Unit of Work pattern in Flask-SQLAlchemy (`db.session`).
**Answer**:
The Unit of Work pattern maintains a list of objects affected by a business transaction. Instead of executing SQL queries immediately upon object modification, `db.session` tracks object states (Transient, Pending, Persistent, Deleted) in memory and flushes changes to the database in a single optimized SQL transaction batch when `db.session.commit()` is called.

---

### Q12: Explain the five object lifecycle states in SQLAlchemy.
**Answer**:
1.  **Transient**: Created in Python (`user = User()`), not added to session.
2.  **Pending**: Added to session via `db.session.add(user)`, awaiting flush/commit.
3.  **Persistent**: Exists in session and has a corresponding row in the database table with a primary key.
4.  **Deleted**: Marked for deletion inside session, SQL `DELETE` executed upon commit.
5.  **Detached**: Session closed or expunged; object contains data but is disconnected from active DB session updates.

---

### Q13: How do `db.Numeric(precision, scale)` and `db.Float` differ for storing financial transactions?
**Answer**:
*   `db.Float`: Uses binary floating-point representation (`IEEE 754`). It suffers from rounding inaccuracies (e.g. `0.1 + 0.2 != 0.3`), making it unsuitable for financial data.
*   `db.Numeric(precision, scale)`: Uses exact decimal representation in the database and maps to Python's `decimal.Decimal` class, ensuring exact currency calculations without rounding errors.

---

### Q14: What does `SQLALCHEMY_TRACK_MODIFICATIONS = False` do and why should it always be disabled?
**Answer**:
`SQLALCHEMY_TRACK_MODIFICATIONS` was an early Flask-SQLAlchemy event tracking system that monitored object modifications and emitted signals on every change. It consumes significant extra memory overhead. Setting it to `False` disables this legacy signal system, improving application performance.

---

### Q15: How do you configure SQLAlchemy engine connection pooling for high-concurrency production deployments?
**Answer**:
Pass `SQLALCHEMY_ENGINE_OPTIONS` in application configuration:

```python
app.config['SQLALCHEMY_ENGINE_OPTIONS'] = {
    'pool_size': 15,       # Permanent active database connections in pool
    'max_overflow': 30,    # Temporary connections allowed above pool_size under heavy load
    'pool_recycle': 1800,  # Recycle stale idle connections every 30 minutes
    'pool_timeout': 30     # Seconds to wait for an available pool connection before error
}
```
