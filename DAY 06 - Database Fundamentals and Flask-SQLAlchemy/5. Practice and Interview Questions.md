## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is an ORM (Object-Relational Mapping) and why is it used in Flask?
**Answer**:
An **ORM (Object-Relational Mapping)** is a programming library that translates relational database tables into object-oriented Python classes (`db.Model`). It allows developers to perform database operations (querying, inserting, updating, deleting) using standard Python syntax without writing raw SQL strings, significantly improving developer productivity, type safety, and maintainability.

---

### Q2: What is the purpose of `db.session.commit()` vs `db.session.add()`?
**Answer**:
*   `db.session.add(obj)`: Stages an object in memory within the current transaction (Unit of Work). It does NOT write to the database yet.
*   `db.session.commit()`: Flushes all staged changes to the database and executes an atomic SQL transaction (`COMMIT`), persisting data permanently to disk.

---

### Q3: What is a Database URI and what are the standard formats for SQLite and PostgreSQL?
**Answer**:
A **Database URI** is a standardized connection string describing the driver, dialect, credentials, and host of the database.
*   **SQLite**: `sqlite:///app.db` (Relative file) or `sqlite:////absolute/path/app.db`
*   **PostgreSQL**: `postgresql+psycopg2://username:password@localhost:5432/database_name`

## 🟡 Level 2: Intermediate Questions

### Q4: How does Flask-SQLAlchemy prevent SQL Injection attacks automatically?
**Answer**:
`Flask-SQLAlchemy` generates parameterized SQL queries under the hood. When values are passed into methods like `db.session.get()`, `filter_by()`, or `where()`, SQLAlchemy separates the SQL statement structure from the user data parameters, ensuring user inputs cannot escape their data literal boundaries or execute unauthorized SQL statements.

---

### Q5: Why is `with app.app_context(): db.create_all()` required in Flask 3.x?
**Answer**:
In Flask 3.x, database operations must run within an active **Application Context** so `Flask-SQLAlchemy` can access `current_app.config['SQLALCHEMY_DATABASE_URI']` and the database connection engine. Running `db.create_all()` inside `with app.app_context():` ensures the extension has access to the application's configuration.

## 🔴 Level 3: Advanced & Enterprise Questions

### Q6: What is the Unit of Work pattern in `Flask-SQLAlchemy` and how does `db.session.rollback()` protect data integrity?
**Answer**:
The **Unit of Work** pattern maintains a list of objects affected by a business transaction and coordinates writing out changes. If multiple database operations are staged and one encounters an error (e.g. unique constraint violation), calling `db.session.rollback()` clears all uncommitted staged operations, leaving the database in a clean, consistent state.

```python
try:
    db.session.add(user)
    db.session.add(profile)
    db.session.commit()
except Exception as e:
    db.session.rollback()  # Aborts both operations atomically!
    raise e
```

### Q7: Compare classic `db.Column()` syntax with modern SQLAlchemy 2.0 `Mapped[]` and `mapped_column()`.
**Answer**:
*   **Classic (SQLAlchemy 1.x)**: Uses runtime column definitions: `name = db.Column(db.String(100), nullable=False)`. It lacks static typing metadata.
*   **Modern (SQLAlchemy 2.0)**: Uses Python type annotations: `name: Mapped[str] = mapped_column(String(100), nullable=False)`. This enables IDE type-checking, MyPy validation, and cleaner dataclass-style syntax.
