# Day 06 - Module 2: CRUD Operations & Session Lifecycle

Welcome to **Module 2** of Day 06! Now that we know how to define database models, let's learn how to perform **CRUD** operations (**C**reate, **R**ead, **U**pdate, **D**elete) and manage database transactions using `db.session`!

---

## 1. The 5 Object Lifecycle States in `db.session`

SQLAlchemy tracks model objects using a Unit of Work pattern through 5 distinct lifecycle states:

```
+------------------+
|    Transient     |  Object created in Python (`emp = Employee()`), not added to session
+--------+---------+
         | db.session.add(emp)
         v
+--------+---------+
|     Pending      |  Attached to session, SQL INSERT statements not yet executed
+--------+---------+
         | db.session.commit() / flush()
         v
+--------+---------+
|    Persistent    |  Has a primary key ID and corresponds to an active row in the database
+--------+---------+
         | db.session.delete(emp)
         v
+--------+---------+
|     Deleted      |  Marked for deletion in session, SQL DELETE pending commit
+--------+---------+
         | db.session.commit()
         v
+--------+---------+
|    Detached      |  Session closed; object exists in Python memory but disconnected from DB
+------------------+
```

---

## 2. Standard CRUD Operations (SQLAlchemy 2.0 Syntax)

In modern SQLAlchemy 2.0+ (used in Flask 3.x), queries use explicit **`db.select()`** statements instead of legacy `Model.query` calls.

#### ⚖️ Legacy SQLAlchemy 1.x (`Model.query`) vs Modern 2.0 (`db.select()`)

| Operation | Legacy Syntax (1.x - Deprecated) | Modern Syntax (2.0+ - Best Practice) |
| :--- | :--- | :--- |
| **Lookup by Primary Key** | `Employee.query.get(1)` | `db.session.get(Employee, 1)` |
| **Fetch All Rows** | `Employee.query.all()` | `db.session.execute(db.select(Employee)).scalars().all()` |
| **Filter Single Row** | `Employee.query.filter_by(email=e).first()` | `db.session.execute(db.select(Employee).where(Employee.email == e)).scalar_one_or_none()` |
| **Filter Multiple Rows** | `Employee.query.filter(Employee.salary > 50000).all()` | `db.session.execute(db.select(Employee).where(Employee.salary > 50000)).scalars().all()` |

---

### 1. Create (Insert New Rows)
```python
# 1. Create transient object
new_emp = Employee(
    first_name="Alice",
    last_name="Smith",
    email="alice@example.com",
    salary=75000.00
)

# 2. Stage object in session (Pending state)
db.session.add(new_emp)

# 3. Commit transaction to database (Persistent state)
db.session.commit()
```

---

### 2. Read (Querying Data)

```python
# A. Fast Lookup by Primary Key ID
emp = db.session.get(Employee, 1)

# B. Fetch ALL Records Ordered by Last Name
stmt = db.select(Employee).order_by(Employee.last_name)
employees = db.session.execute(stmt).scalars().all()

# C. Fetch Single Matching Record or None
stmt = db.select(Employee).where(Employee.email == 'alice@example.com')
emp = db.session.execute(stmt).scalar_one_or_none()

# D. Filter Records by Condition (e.g. Salary > 70000)
stmt = db.select(Employee).where(Employee.salary > 70000.00)
high_earners = db.session.execute(stmt).scalars().all()
```

---

### 3. Update (Modify Existing Rows)
```python
# 1. Fetch persistent object
emp = db.session.get(Employee, 1)

if emp:
    # 2. Modify attributes directly
    emp.salary = 82000.00
    emp.department = "Engineering"
    
    # 3. Commit changes (SQL UPDATE statement executed automatically)
    db.session.commit()
```

---

### 4. Delete (Remove Rows)
```python
emp = db.session.get(Employee, 1)

if emp:
    db.session.delete(emp)
    db.session.commit()
```

## 3. `db.session.flush()` vs. `db.session.commit()`

*   **`db.session.flush()`**: Issues pending SQL queries (`INSERT`, `UPDATE`, `DELETE`) to the database transaction buffer. Primary keys are generated, but changes are **not yet saved permanently to disk** and can be rolled back.
*   **`db.session.commit()`**: Flushes pending SQL statements and **permanently commits** the transaction to disk.

---

## 4. Transaction Safety & Error Rollback (`db.session.rollback()`)

Database operations should always be wrapped in exception handling blocks to prevent broken session states:

```python
from sqlalchemy.exc import SQLAlchemyError

def create_employee_safely(data):
    try:
        emp = Employee(name=data['name'], email=data['email'])
        db.session.add(emp)
        db.session.commit()
        return emp
    except SQLAlchemyError as e:
        # Rollback transaction on database error or duplicate constraint violation!
        db.session.rollback()
        print(f"[DB ERROR] Transaction rolled back safely: {e}")
        return None
```

> **Why `rollback()`?** If a query fails (e.g., duplicate email address), `db.session` enters a poisoned state. Calling `db.session.rollback()` clears pending failed SQL queries and restores the session to a clean state.
