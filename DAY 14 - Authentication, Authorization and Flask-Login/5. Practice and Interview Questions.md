### Q1: Why is raw MD5 or SHA-256 insufficient for password hashing, and how does PBKDF2 / Bcrypt fix it?
**Answer**:
Raw MD5 and SHA-256 are fast hash functions designed for throughput. Modern GPUs can calculate billions of raw SHA-256 hashes per second, making brute-force dictionary attacks fast and inexpensive. Furthermore, unsalted raw hashes are vulnerable to pre-computed Rainbow Table attacks.

PBKDF2 and Bcrypt resolve this by:
1. Generating a unique random **cryptographic salt** per password (preventing Rainbow Table lookups).
2. Implementing **Key Stretching** (executing 100,000+ iterations), deliberately making GPU brute-force attacks computationally expensive.

### Q2: What is a Timing Side-Channel Attack on password verification, and how does Werkzeug prevent it?
**Answer**:
Standard string comparisons (`if string_a == string_b:`) terminate execution immediately at the first non-matching character byte. Attackers measure microsecond execution latency differences across thousands of requests to deduce valid password/hash characters one byte at a time.

Werkzeug's `check_password_hash()` prevents timing attacks by utilizing `hmac.compare_digest()`, executing a **constant-time string comparison** that takes the exact same number of clock cycles regardless of where or whether characters match.

### Q3: What is the purpose of the `@login_manager.user_loader` callback in Flask-Login?
**Answer**:
HTTP is stateless. When a user logs in, Flask-Login serializes the user's primary key ID into a signed session cookie. 

On subsequent incoming HTTP requests, Flask-Login retrieves the user ID from the session cookie and invokes `@login_manager.user_loader(user_id)` to query the database and reload the active `User` model instance into `current_user`.

### Q4: What four methods does `UserMixin` supply for Flask-Login user models?
**Answer**:
1. `is_authenticated`: Returns `True` if the user instance represents an authenticated user.
2. `is_active`: Returns `True` if the account is active and not banned.
3. `is_anonymous`: Returns `True` if the user is an unauthenticated guest.
4. `get_id()``: Returns a unique string representation of the user's primary key ID.

### Q5: How does `remember=True` work in `login_user(user, remember=True)`?
**Answer**:
- `remember=False` (default): Sets a session cookie that expires when the browser window is closed.
- `remember=True`: Sets a persistent, cryptographically signed "Remember Me" cookie with a long expiration date (default 365 days). If the session cookie expires, Flask-Login uses the remember cookie to re-authenticate the user automatically.

### Q6: How do you implement a custom Role-Based Access Control (RBAC) decorator in Flask?
**Answer**:

```python
from functools import wraps
from flask_login import current_user
from flask import abort

def roles_required(*roles):
    def decorator(f):
        @wraps(f)
        def decorated_function(*args, **kwargs):
            if not current_user.is_authenticated or current_user.role not in roles:
                abort(403)
            return f(*args, **kwargs)
        return decorated_function
    return decorator
```

### Q7: What does `login_manager.login_view = 'auth.login'` do?
**Answer**:
It specifies the endpoint name of the login page. When an unauthenticated user attempts to access a route protected by `@login_required`, Flask-Login intercepts the request and automatically redirects the user to `auth.login`, appending the originally requested URL path as a `next` query string parameter (`/auth/login?next=/dashboard`).

---

### Q8: How should the `next` query parameter in login redirects be validated to prevent Open Redirect vulnerabilities?
**Answer**:
Using `redirect(request.args.get('next'))` without validation allows attackers to craft phishing links redirecting victims to malicious external domains (`/login?next=http://attacker.com`).

Validate that the `next` target URL is a relative path or shares the same host domain using `urllib.parse.urlsplit()` before calling `redirect()`.

### Q9: What is the difference between Session-Based Authentication and Token-Based (JWT) Authentication?
**Answer**:
- **Session-Based (Flask-Login)**: The server stores session state in memory/Redis or signed cookies. The client sends a session cookie with every request. Ideal for monolithic web applications with HTML templates.
- **JWT Authentication**: The server issues a signed JSON Web Token containing claims. The client stores the token in memory/localStorage and transmits it in an HTTP `Authorization: Bearer <token>` header. Ideal for SPA frontends (React/Vue) and mobile APIs.

### Q10: What happens when `logout_user()` is called?
**Answer**:
`logout_user()` clears the user ID from the active session, deletes the "Remember Me" cookie from the browser, and resets `current_user` to an `AnonymousUserMixin` instance.
