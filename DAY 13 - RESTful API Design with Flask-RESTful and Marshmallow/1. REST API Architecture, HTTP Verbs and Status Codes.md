# Day 13: REST API Architecture & HTTP Standards

Welcome to **Day 13** of the 30-Day Enterprise Flask Masterclass! Today, we explore **RESTful API Design**, architectural constraints, HTTP verb semantics, status codes, content negotiation, and API data serialization.

---

## 1. Core Principles of RESTful Architecture

**REST (Representational State Transfer)** is an architectural style for designing networked web APIs based on six core constraints:

1. **Statelessness**: Every HTTP request from a client must contain all necessary authentication and context data. The server stores no client session state between requests.
2. **Client-Server Separation**: The user interface (Client) and data storage/logic (Server) are completely decoupled.
3. **Uniform Interface**: Resources are identified by standard URIs (e.g. `/api/v1/users/5`), manipulated using standard HTTP verbs, and returned in self-describing representations (JSON/XML).
4. **Cacheability**: Responses must declare whether they are cacheable (`Cache-Control` headers) to reduce server load.
5. **Layered System**: Clients cannot tell whether they are connected directly to the end server or an intermediate proxy/load balancer.

## 2. HTTP Verbs & Idempotency Matrix

| HTTP Verb | Operation | Target URI Example | Safe? | Idempotent? |
| :--- | :--- | :--- | :--- | :--- |
| **`GET`** | Read resource representation | `/api/v1/articles/10` | ✅ Yes | ✅ Yes |
| **`POST`** | Create new resource | `/api/v1/articles` | ❌ No | ❌ No |
| **`PUT`** | Replace entire resource state | `/api/v1/articles/10` | ❌ No | ✅ Yes |
| **`PATCH`** | Apply partial resource update | `/api/v1/articles/10` | ❌ No | ❌ No |
| **`DELETE`** | Remove specified resource | `/api/v1/articles/10` | ❌ No | ✅ Yes |

> **Idempotency Rule**: An HTTP operation is **idempotent** if executing it once yields the exact same server state as executing it multiple times consecutively (e.g. `PUT` replacing a record vs `POST` creating new duplicate rows).

## 3. Standard HTTP Status Codes

REST APIs communicate outcome state through HTTP status codes:

### 2xx Success
- **`200 OK`**: General success for GET, PUT, PATCH requests.
- **`201 Created`**: Resource created successfully (used in POST responses; includes `Location` header).
- **`204 No Content`**: Operation succeeded with empty response body (used in DELETE requests).

### 4xx Client Errors
- **`400 Bad Request`**: Malformed payload, invalid JSON syntax, or missing mandatory fields.
- **`401 Unauthorized`**: Authentication missing or invalid token provided.
- **`403 Forbidden`**: Client is authenticated but lacks required permission scope.
- **`404 Not Found`**: Target URI or resource ID does not exist in database.
- **`409 Conflict`**: Operation conflicts with existing state (e.g. duplicate unique email).
- **`422 Unprocessable Entity`**: Payload JSON is well-formed, but fails validation rules.

### 5xx Server Errors
- **`500 Internal Server Error`**: Unhandled exception raised on server side.
- **`503 Service Unavailable`**: Database connection pool exhausted or upstream server down.
