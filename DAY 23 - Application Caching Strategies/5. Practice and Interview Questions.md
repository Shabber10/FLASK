# Day 23: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from application caching basics up to view caching, memoization, ORM cache invalidation triggers, and Cache Stampede mitigation.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is Application Caching?
**Answer**:
Application Caching is a technique of storing copies of frequently accessed data or expensive computation results in ultra-fast RAM memory (e.g., Redis or in-memory dicts) so future requests can be served instantly (< 1ms) without querying a slow database.

---

### Q2: What is the difference between a Cache Hit and a Cache Miss?
**Answer**:
*   **Cache Hit**: Requested data is found in RAM memory; returned immediately to the user.
*   **Cache Miss**: Requested data is NOT in RAM memory; fetched from the database, saved to RAM for next time, and returned to the user.

---

### Q3: What is Cache Invalidation?
**Answer**:
Cache Invalidation is the process of removing or purging stale cached data from RAM memory whenever database records are updated or deleted, ensuring users never see outdated information.

---

### Q4: What is `Flask-Caching`?
**Answer**:
`Flask-Caching` is the standard Flask extension providing caching utilities and decorators (like `@cache.cached()` and `@cache.memoize()`) supporting backends like Redis, Memcached, and SimpleCache.

---

### Q5: Why is querying RAM faster than querying a Relational Database?
**Answer**:
RAM operates electronically with near-zero latency (~0.5 microseconds), whereas Relational Databases must read data from disk/SSD storage, parse SQL queries, and construct table joins (~10 to 200 milliseconds).

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the difference between `@cache.cached()` and `@cache.memoize()`?
**Answer**:
*   `@cache.cached()`: Caches the complete HTTP view response payload (HTML or JSON) generated by a route function based on the request URL.
*   `@cache.memoize()`: Caches the return value of an internal Python function based on the specific positional and keyword arguments passed into it.

---

### Q7: What is the difference between `SimpleCache` and `RedisCache` in `Flask-Caching`?
**Answer**:
*   `SimpleCache`: In-memory Python dictionary backend. Suitable for local development; data is isolated per WSGI worker process and lost on server restart.
*   `RedisCache`: Shared Redis RAM server backend. Required for production multi-worker Gunicorn deployments so all workers share a unified cache.

---

### Q8: How do you invalidate a memoized function cache when a database record updates?
**Answer**:
Call `cache.delete_memoized(function_name, *args)` passing the function object and the exact argument values used when memoizing:

```python
cache.delete_memoized(calculate_product_discount, product_id)
```

---

### Q9: How can you generate custom cache keys incorporating request headers or API keys?
**Answer**:
Define a custom key function and pass it to `key_prefix`:

```python
def make_custom_key():
    return f"path:{request.path}_user:{request.headers.get('X-API-KEY')}"

@app.route('/data')
@cache.cached(timeout=60, key_prefix=make_custom_key)
def get_data():
    pass
```

---

### Q10: How does `CACHE_DEFAULT_TIMEOUT` work?
**Answer**:
It specifies the fallback expiration time in seconds (e.g. `CACHE_DEFAULT_TIMEOUT=300`) after which cached keys automatically expire and are purged from RAM.

---

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: What is a Cache Stampede (Thundering Herd) and how do you prevent it in high-traffic APIs?
**Answer**:
A **Cache Stampede** occurs when a high-traffic cache key (e.g. 10,000 req/sec) expires. Thousands of incoming requests discover a Cache Miss simultaneously and swarm the database at once, causing a severe database crash.

**Mitigation Strategies**:
1.  **Probabilistic Early Expiration (XFetch)**: Background workers recompute the cache before it expires.
2.  **Mutex Locking**: Uses a Redis lock so only 1 thread recomputes the cache while other threads wait for the lock to release.

---

### Q12: How can you automate cache invalidation using SQLAlchemy ORM Event Listeners?
**Answer**:
Attach `@listens_for(Model, 'after_update')` and `@listens_for(Model, 'after_delete')` decorators to models to automatically trigger `cache.delete()` or `cache.delete_memoized()` whenever an ORM model is updated or deleted anywhere in the application.

---

### Q13: What is Cache Penetration and how do you prevent it?
**Answer**:
**Cache Penetration** occurs when attackers deliberately request non-existent keys (e.g. `GET /products/99999999`). Since non-existent keys are never cached, every request hits the database.

**Mitigation**: Cache `null`/empty results with a short expiration timeout (e.g. 30 seconds) or use Bloom Filters.

---

### Q14: What is the difference between Write-Through, Write-Back, and Cache-Aside caching patterns?
**Answer**:
*   **Cache-Aside (Lazy Loading)**: Application checks cache first; on miss, loads from DB and populates cache. (Default web pattern).
*   **Write-Through**: Application writes data to cache and database simultaneously.
*   **Write-Back**: Application writes to cache immediately; background worker asynchronously writes batch updates to database.

---

### Q15: Why is configuring `CACHE_KEY_PREFIX` critical in microservices sharing a single Redis cluster?
**Answer**:
Without `CACHE_KEY_PREFIX`, different microservices using identical route paths (like `/api/v1/users`) will overwrite or read each other's cached data in Redis. Adding a unique prefix (like `CACHE_KEY_PREFIX="billing_service_"`) namespaces keys safely.
