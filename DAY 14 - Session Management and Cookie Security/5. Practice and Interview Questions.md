# Day 14: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from session fundamentals up to cookie security flags and Redis server-side session revocation.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is HTTP Statelessness in simple terms?
**Answer**:
HTTP Statelessness means that the web server treats every incoming HTTP request as completely independent. It has no built-in memory to recognize that two separate requests came from the exact same user.

---

### Q2: What is the difference between a Cookie and a Session?
**Answer**:
*   **Cookie**: A small text file stored inside the user's web browser and sent automatically to the server on every request.
*   **Session**: A server-side or signed data mechanism that uses the cookie to remember who the logged-in user is across multiple page visits.

---

### Q3: Is data inside Flask's default client-side session encrypted?
**Answer**:
No. Default Flask sessions are **signed (tamper-proof)** using HMAC with `SECRET_KEY`, but **NOT encrypted**. Anyone can decode the Base64 session string in browser tools to read payload contents. Never store raw passwords or sensitive credentials in `session`.

---

### Q4: What happens when a user calls `session.clear()`?
**Answer**:
`session.clear()` wipes all key-value pairs stored in the active session dictionary, logging the user out and resetting the session state.

---

### Q5: What is the default lifespan of a Flask session?
**Answer**:
If `session.permanent = True` is set, the default lifetime is 31 days (configurable via `PERMANENT_SESSION_LIFETIME`). If `session.permanent = False`, the cookie expires as soon as the user closes their browser window.

---

## 🟡 Level 2: Intermediate Questions

### Q6: How does `SESSION_COOKIE_HTTPONLY = True` protect against XSS attacks?
**Answer**:
The `HttpOnly` flag instructs the browser that the cookie must only be sent in HTTP headers and **cannot be accessed by client-side JavaScript** (`document.cookie`). If a hacker succeeds in injecting a malicious XSS script into your page, they cannot steal the session cookie.

---

### Q7: What does `SESSION_COOKIE_SECURE = True` do?
**Answer**:
It instructs the browser to send the session cookie **ONLY over encrypted `HTTPS://` connections**, preventing man-in-the-middle (MITM) network sniffers from intercepting cookies over unencrypted HTTP.

---

### Q8: What is `SESSION_COOKIE_SAMESITE = 'Lax'` and how does it prevent CSRF?
**Answer**:
`SameSite='Lax'` prevents the browser from sending the session cookie when a request originates from a third-party website (e.g. clicking a link on a malicious site pointing to your bank). This blocks Cross-Site Request Forgery (CSRF) attacks.

---

### Q9: How does Flask verify that a client-side session cookie hasn't been tampered with?
**Answer**:
Flask uses the `itsdangerous` library to compute an HMAC SHA-256 signature using `SECRET_KEY`. When the client sends the cookie back, Flask recomputes the signature. If a user modified the payload (e.g. changing `user_id`), the signature check fails and Flask discards the session.

---

### Q10: How do you configure a custom session expiration window of 7 days?
**Answer**:
```python
from datetime import timedelta

app.config['PERMANENT_SESSION_LIFETIME'] = timedelta(days=7)
session.permanent = True
```

---

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Why are Server-Side Sessions (using Redis) required for enterprise production systems?
**Answer**:
Enterprise systems require Server-Side Sessions because:
1.  Browser cookies have a strict **4KB size limit**, which overflows when storing large session objects.
2.  Client-side cookies cannot be **instantly revoked** by an administrator (e.g. forcing a global logout after a password reset). Redis allows instant deletion of session keys.
3.  Client-side session data is visible to users via Base64 decoding.

---

### Q12: How does `Flask-Session` store sessions in Redis under the hood?
**Answer**:
`Flask-Session` sends only a random UUID string as the browser cookie (`session=uuid-value`). In Redis, it creates a key `session:uuid-value` containing the serialized session dictionary and sets a Redis TTL (Time-To-Live) matching `PERMANENT_SESSION_LIFETIME`.

---

### Q13: How can an administrator implement instant single-user session revocation in Redis?
**Answer**:
Query Redis for the target user's session UUID key and delete it directly:
```python
redis_client = app.config['SESSION_REDIS']
redis_client.delete(f"session:{target_session_uuid}")
```
The next time the user makes an HTTP request, Flask looks up the UUID in Redis, finds no matching key, and treats the request as unauthenticated.

---

### Q14: What is Session Fixation and how do you prevent it in Flask?
**Answer**:
Session Fixation occurs when an attacker tricks a victim into using a known session ID prior to logging in. Prevent it by calling `session.clear()` or regenerating the session ID immediately upon successful authentication.

---

### Q15: What happens if `SECRET_KEY` is leaked or changed in a Flask application?
**Answer**:
*   If `SECRET_KEY` is changed or rotated, all existing active client-side signed session cookies fail HMAC signature verification, instantly logging out all current users across the platform.
*   If `SECRET_KEY` is leaked to hackers, attackers can forge valid HMAC signatures and impersonate any user on the platform.
