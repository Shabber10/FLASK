## 1. The 6 REST Architectural Constraints

To qualify as a true RESTful API (defined by Roy Fielding in 2000), an API must satisfy 6 core constraints:

1.  **Client-Server Separation**: Concerns are decoupled; user interface code stays on the client, data storage stays on the server.
2.  **Statelessness**: Every request from client to server must contain all necessary context (tokens, parameters). The server stores no client session context between requests.
3.  **Cacheability**: Server responses must define whether they are cacheable (`Cache-Control` headers) to optimize network speed.
4.  **Uniform Interface**: Standardized resource URLs (`/api/v1/users`), standard HTTP verbs (`GET`, `POST`, `DELETE`), and self-descriptive representations (JSON).
5.  **Layered System**: Clients cannot tell whether they are connected directly to an end server or an intermediate load balancer/API gateway.
6.  **Code on Demand (Optional)**: Servers can temporarily extend client functionality by transferring executable code (e.g. JavaScript scripts).

## 2. RESTful URL Naming Best Practices

Always use **plural nouns** for resource paths and avoid putting verbs in the URL path:

```
❌ BAD (RPC Style / Anti-Pattern):
POST /getUsers
POST /createNewProduct
GET  /deleteOrder?id=5

✅ GOOD (RESTful Pattern):
GET    /api/v1/users            --> Fetch list of users
POST   /api/v1/products         --> Create a product
GET    /api/v1/products/42      --> Fetch product #42
DELETE /api/v1/orders/5         --> Delete order #5
```

## 3. HTTP Method Idempotency

An HTTP method is **Idempotent** if making the exact same request 1 time or 100 times produces the exact same side-effect state on the server:

| HTTP Method | Safe? | Idempotent? | Explanation |
| :--- | :--- | :--- | :--- |
| **`GET`** | ✅ Yes | ✅ Yes | Reading data does not alter server state. |
| **`PUT`** | ❌ No | ✅ Yes | Replacing resource #5 with `{"name": "Laptop"}` 10 times yields the exact same state. |
| **`DELETE`** | ❌ No | ✅ Yes | Deleting resource #5 once removes it; subsequent deletes still leave it gone. |
| **`POST`** | ❌ No | ❌ **No** | Submitting `POST /api/v1/orders` 10 times creates 10 duplicate orders! |

## 4. HATEOAS (Hypermedia As The Engine Of Application State)

### 📖 What is HATEOAS?
**HATEOAS** (Richardson Maturity Model Level 3) is a REST architectural constraint where the server includes **navigational hypermedia links** in every response, informing the client which actions can be performed next.

### 💻 Code Example: JSON Response Envelope with HATEOAS Links

```python
from flask import Flask, jsonify, url_for

app = Flask(__name__)

@app.route('/api/v1/orders/<int:order_id>', methods=['GET'])
def get_order(order_id):
    order_data = {
        "id": order_id,
        "total_amount": 149.99,
        "status": "pending_payment",
        # HATEOAS Link Envelope (_links)
        "_links": {
            "self": {"href": f"/api/v1/orders/{order_id}", "method": "GET"},
            "pay": {"href": f"/api/v1/orders/{order_id}/pay", "method": "POST"},
            "cancel": {"href": f"/api/v1/orders/{order_id}", "method": "DELETE"},
            "customer": {"href": "/api/v1/customers/42", "method": "GET"}
        }
    }
    return jsonify(order_data), 200
```

## 5. Safe POST Retries with Idempotency Keys (`X-Idempotency-Key`)

### ❓ The Problem:
If a user submits an order (`POST /api/v1/orders`) and their mobile network drops before receiving the response, the client app retries. Without protection, the user is charged twice!

### 💻 Solution: Caching Idempotency Keys in Redis

```python
import redis
from flask import request, jsonify

redis_client = redis.Redis.from_url("redis://localhost:6379/0", decode_responses=True)

@app.route('/api/v1/orders', methods=['POST'])
def create_order():
    idempotency_key = request.headers.get('X-Idempotency-Key')
    
    if idempotency_key:
        cached_response = redis_client.get(f"idempotency:{idempotency_key}")
        if cached_response:
            # Return identical previous response without re-executing payment!
            return cached_response, 200

    # Execute business logic
    data = request.get_json() or {}
    order_id = execute_order_creation(data)
    
    response_payload = jsonify({"status": "created", "order_id": order_id}).get_data(as_text=True)
    
    if idempotency_key:
        # Cache response for 24 hours (86400s)
        redis_client.setex(f"idempotency:{idempotency_key}", 86400, response_payload)
        
    return response_payload, 201
```

## 6. Complete HTTP Status Code Directory

### 🟢 2xx Success Codes
*   **`200 OK`**: Request succeeded. Returns requested data payload.
*   **`201 Created`**: Resource created successfully (used after `POST`).
*   **`204 No Content`**: Request succeeded with no body returned (used after `DELETE`).

### 🔴 4xx Client Error Codes
*   **`400 Bad Request`**: Missing required JSON fields or malformed syntax.
*   **`401 Unauthorized`**: Authentication missing or invalid token.
*   **`403 Forbidden`**: Authenticated user lacks required permissions.
*   **`404 Not Found`**: Target URL resource endpoint or ID does not exist.
*   **`409 Conflict`**: Database constraint conflict (e.g. duplicate email).
*   **`422 Unprocessable Entity`**: Valid JSON, but semantic validation rules failed.
*   **`429 Too Many Requests`**: Rate limit quota exceeded.

### 💥 5xx Server Error Codes
*   **`500 Internal Server Error`**: Unexpected uncaught server exception or crash.
*   **`503 Service Unavailable`**: Server or dependency (DB/Redis) temporarily offline.
