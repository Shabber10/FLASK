## 1. What is the Difference Between API, REST API & RESTful API?

Many beginners get confused between these three terms. Let's make it crystal clear:

```
                  ┌─────────────────────────────────────────┐
                  │                   API                   │
                  │   (Any way two apps communicate)        │
                  │                                         │
                  │       ┌─────────────────────────┐       │
                  │       │        REST API         │       │
                  │       │  (Uses REST ideas/URLs) │       │
                  │       │                         │       │
                  │       │     ┌─────────────┐     │       │
                  │       │     │ RESTful API │     │       │
                  │       │     │(Follows ALL │     │       │
                  │       │     │ constraints)│     │       │
                  │       │     └─────────────┘     │       │
                  │       └─────────────────────────┘       │
                  └─────────────────────────────────────────┘
```

### 🏍️ The Sports Bike Analogy
*   **Every Sports Bike is a Bike.**
*   **But every Bike is NOT a Sports Bike.**
*   *Similarly:* **Every RESTful API is a REST API, but not every REST API is fully RESTful.**

### 👨‍🎓 The School Uniform / Rule-Following Analogy
Imagine a school with strict rules: Dress code, ID Card, Clean Shoes, and Punctuality.
*   **Student 1**: Wears dress code ✅, wears ID Card ✅, but arrives late ❌. He follows *most* rules, but not all.
*   **Student 2**: Follows dress code ✅, ID card ✅, shoes ✅, and arrives exactly on time ✅. He is a **100% Rule-Following Student**.

> In software:
> *   **REST API**: An API designed following general REST conventions (like using HTTP verbs and nouns).
> *   **RESTful API**: An API that strictly and consistently satisfies **all** official REST architectural principles.

## 2. Roy Fielding's 6 REST Architectural Constraints

In the year 2000, computer scientist **Roy Fielding** defined the 6 principles of REST:

1.  **Client-Server Separation**: The User Interface (Client) and the Database/Logic (Server) are independent. You can change your frontend (e.g. switch from HTML to React) without breaking the backend.
2.  **Statelessness**: Every request from client to server must contain all necessary information (e.g. auth tokens, parameters). The server does not remember past requests.
3.  **Cacheability**: Server responses must clearly declare whether they can be cached (saved in memory) to speed up performance.
4.  **Uniform Interface**: Resources have predictable, consistent naming (e.g. `/api/v1/students`), standard verbs (`GET`, `POST`), and standardized data formats (`application/json`).
5.  **Layered System**: The client doesn't need to know if it is talking directly to the main server, a proxy, a load balancer, or an API gateway.
6.  **Code on Demand (Optional)**: The server can temporarily send executable code (such as JavaScript) to the client.

## 3. Good vs. Bad URL Design

Always use **plural nouns** for resource paths and avoid putting action verbs in the URL path:

```
❌ BAD (RPC / Action-based URLs):
GET  /getAllStudents
POST /addNewStudent
POST /updateStudentData?id=101
GET  /deleteStudent/101

✅ GOOD (RESTful Resource URLs):
GET    /students          --> Get all students
POST   /students          --> Add a new student
GET    /students/101      --> Get student #101
PUT    /students/101      --> Replace student #101 completely
PATCH  /students/101      --> Update specific fields of student #101
DELETE /students/101      --> Delete student #101
```

## 4. The Complete HTTP Status Code Storybook 📖

When an API responds, the status code tells the client: *"Was your request successful or did something go wrong?"*

Here are the 12 most important HTTP Status Codes with real-life stories and Flask code:

---

### 1. `200 OK` (Success)
*   **Meaning**: The request was successful, and the server is returning the requested data.
*   **Real-Life Analogy**: You order food at a restaurant, the waiter brings the exact dish, and everything is fine.
*   **Flask Snippet**:
    ```python
    @app.route("/students", methods=["GET"])
    def get_students():
        return jsonify({"students": [{"id": 101, "name": "Rahul"}]}), 200
    ```

---

### 2. `201 Created` (Success - New Resource Created)
*   **Meaning**: A new resource has been created in the database (used with `POST`).
*   **Real-Life Analogy**: You fill out a registration form on Gmail, and Google says *"Account Created Successfully"*.
*   **Flask Snippet**:
    ```python
    @app.route("/students", methods=["POST"])
    def create_student():
        return jsonify({"message": "Student created successfully", "id": 103}), 201
    ```

---

### 3. `204 No Content` (Success - Empty Body)
*   **Meaning**: The request succeeded, but there is no data to return in the body (commonly used with `DELETE`).
*   **Real-Life Analogy**: You throw a piece of paper into a trash can. The task is completed; there is nothing to return.
*   **Flask Snippet**:
    ```python
    @app.route("/students/<int:student_id>", methods=["DELETE"])
    def delete_student(student_id):
        # Delete student from database...
        return "", 204
    ```

---

### 4. `400 Bad Request` (Client Error - Invalid Request)
*   **Meaning**: The client sent invalid, unparseable, or malformed data (such as broken JSON syntax).
*   **Real-Life Analogy**: In an application form where it asks for Age (numbers), you write `"Twenty"` instead of `20`. The form is rejected because the format is bad.
*   **Flask Snippet**:
    ```python
    @app.route("/students", methods=["POST"])
    def add_student():
        data = request.get_json()
        if not data:
            return jsonify({"error": "Bad Request", "message": "Malformed or missing JSON body"}), 400
    ```

---

### 5. `401 Unauthorized` (Client Error - Login Required)
*   **Meaning**: The client is **not authenticated** (missing or invalid credentials/token).
*   **Real-Life Analogy**: You try to enter Netflix without logging in. Netflix prompts: *"Please Login"*.
*   **Flask Snippet**:
    ```python
    @app.route("/profile")
    def profile():
        token = request.headers.get("Authorization")
        if not token:
            return jsonify({"error": "Unauthorized", "message": "Login required to access profile"}), 401
    ```

---

### 6. `403 Forbidden` (Client Error - Permission Denied)
*   **Meaning**: The client **is logged in**, but does not have permission/role rights to access this resource.
*   **Real-Life Analogy**: You work at a company and have an employee badge to enter the office building, but you are not allowed inside the CEO's private safe.
*   **Flask Snippet**:
    ```python
    @app.route("/admin/delete-database")
    def delete_db():
        if current_user.role != "ADMIN":
            return jsonify({"error": "Forbidden", "message": "Admin privileges required"}), 403
    ```

> 💡 **Interview Golden Distinction: 401 vs 403**
> *   **401 Unauthorized**: ❌ Not logged in / missing authentication.
> *   **403 Forbidden**: ✔️ Logged in, but ❌ No permission for this specific action.

---

### 7. `404 Not Found` (Client Error - Resource Doesn't Exist)
*   **Meaning**: The requested URL endpoint or resource ID was not found on the server.
*   **Real-Life Analogy**: You go to a library and ask for Book Number `999`. The librarian checks the shelf and says the book does not exist.
*   **Flask Snippet**:
    ```python
    @app.route("/students/<int:student_id>")
    def get_student(student_id):
        student = find_student(student_id)
        if not student:
            return jsonify({"error": "Not Found", "message": f"Student #{student_id} does not exist"}), 404
    ```

---

### 8. `405 Method Not Allowed` (Client Error - Wrong HTTP Verb)
*   **Meaning**: The URL exists, but the HTTP method used is not supported.
*   **Real-Life Analogy**: You walk into a restaurant and ask the waiter: *"Can I recharge my mobile phone here?"* The restaurant exists, but it does not provide mobile recharge services!
*   **Flask Snippet**: Flask raises this automatically if an endpoint is configured for `GET` only and a client sends a `POST` request.

---

### 9. `409 Conflict` (Client Error - Duplicate Data)
*   **Meaning**: The request conflicts with current server state (e.g. duplicate email, unique constraint violation).
*   **Real-Life Analogy**: A college tries to assign Roll Number `101` to a new student when `101` is already assigned to Rahul.
*   **Flask Snippet**:
    ```python
    if email_already_registered(data["email"]):
        return jsonify({"error": "Conflict", "message": "Email is already registered"}), 409
    ```

---

### 10. `422 Unprocessable Content` (Client Error - Validation Failed)
*   **Meaning**: The JSON syntax is valid, but the values fail semantic validation (e.g. empty string, negative age, invalid email format).
*   **Real-Life Analogy**: You filled out the form completely and in valid format, but entered your Age as `-5`.
*   **Flask Snippet**:
    ```python
    if data.get("age", 0) <= 0:
        return jsonify({"error": "Unprocessable Content", "message": "Age must be a positive integer"}), 422
    ```

> 💡 **Interview Golden Distinction: 400 vs 422**
> *   **400 Bad Request**: Malformed or unparseable request syntax (e.g. `{ "name": }`).
> *   **422 Unprocessable Content**: Valid syntax, but values fail business validation rules.

---

### 11. `500 Internal Server Error` (Server Error - Bug in Code)
*   **Meaning**: An unhandled exception or crash occurred in the server code (e.g. `ZeroDivisionError`, `NoneType` error).
*   **Real-Life Analogy**: The restaurant chef accidentally burns the kitchen food. It is a problem inside the kitchen, not the customer's fault!
*   **Flask Snippet**:
    ```python
    @app.errorhandler(500)
    def internal_error(e):
        return jsonify({"error": "Internal Server Error", "message": "An unexpected error occurred"}), 500
    ```

---

### 12. `503 Service Unavailable` (Server Error - Downtime / Maintenance)
*   **Meaning**: The server is temporarily unable to handle requests due to maintenance or database overload.
*   **Real-Life Analogy**: A bank website displays: *"Online banking is under scheduled maintenance from 2 AM to 4 AM"*.

## 5. HTTP Method to Status Code Quick Mapping Table

| HTTP Method | Primary Success Code | Alternative Success | Common Error Codes |
| :--- | :---: | :---: | :---: |
| **`GET`** | `200 OK` | — | `404 Not Found`, `401`, `403` |
| **`POST`** | `201 Created` | `200 OK` | `400 Bad Request`, `409 Conflict`, `422 Unprocessable` |
| **`PUT`** | `200 OK` | `204 No Content` | `400`, `404 Not Found`, `422 Unprocessable` |
| **`PATCH`** | `200 OK` | `204 No Content` | `400`, `404 Not Found`, `422 Unprocessable` |
| **`DELETE`** | `204 No Content` | `200 OK` | `404 Not Found`, `401`, `403` |

## 6. Advanced REST Concepts: HATEOAS & Idempotency

### HTTP Method Idempotency
An operation is **Idempotent** if performing it once or 100 times produces the exact same server state:
*   `GET`: Idempotent (Read-only, state never changes).
*   `PUT`: Idempotent (Setting resource #101 name to "Rahul" 10 times results in name being "Rahul").
*   `DELETE`: Idempotent (Deleting resource #101 once deletes it; running it again still leaves it deleted).
*   `POST`: **NOT Idempotent** (Calling `POST /students` 10 times creates 10 duplicate students!).

### HATEOAS (Hypermedia Links)
Providing navigational links inside the JSON response so the client knows what actions are possible next:

```json
{
  "id": 101,
  "name": "Rahul",
  "_links": {
    "self": { "href": "/api/v1/students/101", "method": "GET" },
    "update": { "href": "/api/v1/students/101", "method": "PUT" },
    "delete": { "href": "/api/v1/students/101", "method": "DELETE" }
  }
}
```
