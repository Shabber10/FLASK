# Day 15: Practice & Technical Interview Questions

---

### Q1: What are the three structural parts of a JSON Web Token (JWT) and how is the signature created?
**Answer**:
A JWT consists of three Base64URL-encoded strings separated by dots (`.`):
1. **Header**: Declares algorithm (`alg`) and token type (`typ`).
2. **Payload**: Contains standard claims (`sub`, `exp`, `jti`) and custom claims (`role`).
3. **Signature**: Created by taking the Base64URL encoded header and payload, joining them with a dot, and hashing them with the server's `SECRET_KEY` using HMAC-SHA256:

$$\text{Signature} = \text{HMAC-SHA256}(\text{Header} + "." + \text{Payload}, \text{SECRET\_KEY})$$

---

### Q2: Are JSON Web Tokens encrypted by default? Can an attacker read JWT payload contents?
**Answer**:
No! Standard JWTs (JSON Web Signature / JWS) are **signed and encoded, NOT encrypted**. Anyone who intercepts a JWT can decode the Base64URL payload string and view all claims in plaintext. 

The signature only guarantees **integrity** (that the payload has not been modified). Never store sensitive data (passwords, social security numbers) inside a standard JWT payload.

---

### Q3: Why is a Dual-Token strategy (Access Token + Refresh Token) recommended for REST APIs?
**Answer**:
- **Access Tokens** are short-lived (e.g. 15 minutes). If stolen via XSS or network interception, the attacker's window of access is minimal.
- **Refresh Tokens** are long-lived (e.g. 30 days) and restricted to the `/api/refresh` endpoint. They allow users to obtain new Access Tokens seamlessly without re-entering passwords.

---

### Q4: How do you revoke a stateless JWT before its expiration timestamp (`exp`)?
**Answer**:
Because JWT verification is stateless, the server cannot "delete" a token client-side. 

To revoke a JWT prematurely (e.g. on user logout), the server stores the token's unique ID (`jti`) in a **Token Denylist (Blocklist)** (in Redis or a database). Flask-JWT-Extended uses `@jwt.token_in_blocklist_loader` to check whether the incoming request's `jti` exists in the blocklist.

---

### Q5: What is the difference between `get_jwt_identity()` and `get_jwt()` in Flask-JWT-Extended?
**Answer**:
- `get_jwt_identity()`: Returns the subject claim (`sub`) of the active JWT (usually the user ID or username).
- `get_jwt()`: Returns the complete decoded dictionary of all claims inside the JWT payload (including `exp`, `jti`, `iat`, and custom claims like `role`).

---

### Q6: How do `@jwt_required()` and `@jwt_required(refresh=True)` differ?
**Answer**:
- `@jwt_required()`: Requires a valid **Access Token** in the `Authorization: Bearer <token>` header. Rejects Refresh Tokens.
- `@jwt_required(refresh=True)`: Requires a valid **Refresh Token**. Rejects Access Tokens. Used exclusively on token renewal endpoints (e.g. `/api/refresh`).

---

### Q7: What is the `jti` claim in a JWT and why is it important?
**Answer**:
`jti` stands for **JWT ID**. It is a unique UUID string generated for every issued token. It allows servers to identify individual tokens uniquely, enabling token revocation blocklisting and preventing replay attacks.

---

### Q8: How should clients transmit JWTs to Flask APIs securely?
**Answer**:
Clients should transmit JWTs in the HTTP `Authorization` header using the `Bearer` scheme:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

---

### Q9: What happens if an attacker modifies a claim (e.g. changes `"role": "member"` to `"role": "admin"`) in a JWT payload?
**Answer**:
When the modified JWT arrives at the server, Flask-JWT-Extended re-computes the HMAC-SHA256 signature using the server's secret key. Because the payload changed, the calculated signature will not match the signature attached to the token. Flask-JWT-Extended rejects the token as invalid (`401 Unauthorized`).

---

### Q10: What are custom claims in Flask-JWT-Extended and how are they added?
**Answer**:
Custom claims allow embedding additional metadata (such as user roles or permissions) directly inside the token payload during creation:

```python
access_token = create_access_token(
    identity=str(user.id),
    additional_claims={"role": user.role, "tenant_id": user.tenant_id}
)
```
