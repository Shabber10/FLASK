# Day 15: JSON Web Token (JWT) Architecture

Welcome to **Day 15** of the 30-Day Enterprise Flask Masterclass! Today, we complete **Phase 3: Modular Architecture, Blueprints & REST APIs**. We explore stateless API security, JSON Web Token (JWT) specification (RFC 7519), cryptographic signatures, and access token vs refresh token lifecycles.

---

## 1. Session-Based vs. Token-Based Authentication

As web applications transition to Single Page Applications (React, Vue, Angular) and mobile clients (iOS/Android), traditional HTTP session cookies present limitations:

| Feature | Session-Based (Cookies) | Token-Based (JWT) |
| :--- | :--- | :--- |
| **State Storage** | Server-side (Memory/Redis DB) | **Stateless** (Client stores signed token) |
| **Cross-Domain Support** | Difficult (Cookie Same-Origin policies) | **Seamless** (Transmitted via Bearer headers) |
| **Mobile Client Support** | Poor (Native apps lack browser cookies) | **Native** (Stored in Secure Storage / Keychain) |
| **Horizontal Scalability**| Requires shared Redis session store | **Instant** (Any backend node verifies token signature) |

## 2. JWT Anatomy (RFC 7519)

A JSON Web Token consists of three distinct parts separated by dots (`.`):

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

+-----------------------+ . +-----------------------+ . +-----------------------+
|    Base64URL Header   |   |   Base64URL Payload   |   | HMAC-SHA256 Signature |
|  - Algorithm (HS256)  |   |  - Claims (sub, exp)  |   |  - Signed with        |
|  - Type (JWT)         |   |  - Custom Data (role) |   |    SECRET_KEY         |
+-----------------------+   +-----------------------+   +-----------------------+
```

### 1. Header
Declares the signing algorithm and token type:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 2. Payload (Claims)
Contains statement claims about the entity (user) and additional metadata:
- **`sub`** (Subject): Unique user ID string.
- **`exp`** (Expiration Time): Unix timestamp when token expires.
- **`iat`** (Issued At): Unix timestamp when token was created.
- **`jti`** (JWT ID): Unique UUID identifier for token revocation tracking.
- **Custom Claims**: e.g., `"role": "admin"`.

### 3. Signature
Cryptographic signature calculated by hashing the encoded header, payload, and server `SECRET_KEY`:

$$\text{Signature} = \text{HMAC-SHA256}(\text{Base64URL}(\text{Header}) + "." + \text{Base64URL}(\text{Payload}), \text{SECRET\_KEY})$$

---

## 3. Critical Security Concept: JWTs are SIGNED, Not Encrypted!

> ⚠️ **CRITICAL WARNING**: Base64URL encoding is **NOT** encryption! Anyone who intercepts a JWT can decode the payload string and read its contents. 
> 
> **Never store sensitive data (passwords, credit card numbers, SSNs) inside a JWT payload!** The signature only guarantees that the payload has not been modified or tampered with by an attacker.
