# Day 12: Practice & Technical Interview Questions

---

### Q1: What is the Application Factory pattern in Flask and why is it considered an industry best practice?
**Answer**:
The Application Factory pattern decouples application creation by encapsulating initialization inside a `create_app()` function instead of declaring a global top-level `app = Flask(__name__)` instance.

Best practice benefits:
1. **Testing Isolation**: Enables creating separate, isolated app instances with dedicated test configurations (e.g. in-memory SQLite) for every test case.
2. **Circular Import Elimination**: Extensions (`db`, `migrate`, `login_manager`) are instantiated unbound at module level, avoiding circular imports between models and views.
3. **Multi-Environment Support**: Dynamically loads `Dev`, `Testing`, or `Prod` settings based on environment flags.

---

### Q2: How does the Deferred Extension Initialization pattern (`ext.init_app(app)`) work?
**Answer**:
In `extensions.py`, extension objects are instantiated without passing a Flask `app` instance: `db = SQLAlchemy()`. 

When `create_app()` runs, the extension is bound to the specific Flask application instance created by the factory calling `db.init_app(app)`. This allows extensions to attach event handlers, CLI commands, and teardown hooks to that specific app instance.

### Q3: How do `app.config.from_object()` and `app.config.from_pyfile()` differ?
**Answer**:
- `app.config.from_object(ConfigClass)`: Imports configuration attributes from a Python class or module object (e.g. `DevelopmentConfig`).
- `app.config.from_pyfile('instance/config.py')`: Loads configuration settings from a separate relative file on disk (commonly used for secret local overrides).

---

### Q4: Why is the `instance/` folder useful and why should it be added to `.gitignore`?
**Answer**:
The `instance/` folder is designed for unversioned configuration files, database files (such as SQLite `.db` files), and local secret keys that reside outside the main application package.

Adding `instance/` to `.gitignore` prevents developers from accidentally committing sensitive credentials, API keys, or production secrets into remote Git repositories.

### Q5: How do `python-dotenv` and `.env` files integrate with Flask CLI commands?
**Answer**:
When `python-dotenv` is installed, running `flask run` or any `flask` CLI command automatically locates and parses `.env` and `.flaskenv` files in the project root, setting environment variables (`FLASK_APP`, `SECRET_KEY`, `DATABASE_URL`) before the application initializes.

### Q6: How do you configure a Pytest fixture to test a Flask app built with `create_app()`?
**Answer**:

```python
import pytest
from app import create_app, db

@pytest.fixture
def app():
    _app = create_app('testing')
    with _app.app_context():
        db.create_all()
        yield _app
        db.drop_all()

@pytest.fixture
def client(app):
    return app.test_client()
```

### Q7: What happens if `WTF_CSRF_ENABLED = False` is set in `TestingConfig`?
**Answer**:
Setting `WTF_CSRF_ENABLED = False` disables CSRF token verification during automated test execution. This allows test suites to post mock form data directly to endpoints without manually generating or parsing secret CSRF tokens in every unit test.

### Q8: How can you pass custom configuration overrides into `create_app()` at runtime?
**Answer**:
Accept an optional `config_name` or `config_override` dictionary:

```python
def create_app(config_name='development', config_override=None):
    app = Flask(__name__)
    app.config.from_object(config_map[config_name])
    
    if config_override:
        app.config.update(config_override)
        
    return app
```

### Q9: What is the difference between `FLASK_ENV` and `FLASK_DEBUG` in Flask 2.3+ / 3.x?
**Answer**:
In Flask 2.3+, `FLASK_ENV` was deprecated in favor of `FLASK_DEBUG`. Setting `FLASK_DEBUG=1` (or `True` in config) enables the interactive debugger, auto-reloader, and debug logging.

### Q10: How does `db.session` resolve the current application database connection when using `create_app()`?
**Answer**:
When `db = SQLAlchemy()` is initialized without an app, `db.session` uses Werkzeug's `LocalProxy` to inspect the active Application Context (`current_app`). When an HTTP request enters an app instance built by `create_app()`, `db.init_app(app)` binds `current_app` to the specific engine for that thread.
