# Day 25: Practice & Technical Interview Questions

---

### Q1: What is the difference between Continuous Integration (CI) and Continuous Deployment (CD)?
**Answer**:
- **Continuous Integration (CI)**: The automated practice of building code, running linters (`flake8`), executing static security analysis (`bandit`), and running test suites (`pytest`) whenever developers push code or open pull requests.
- **Continuous Deployment (CD)**: The automated practice of building production artifacts (e.g. Docker images) and releasing passing builds to staging or production infrastructure without manual human intervention.

---

### Q2: What is a GitHub Actions Build Matrix strategy and why is it used?
**Answer**:
A Build Matrix allows running parallel job instances across different combinations of operating systems and Python runtime versions (e.g. testing across Python 3.10, 3.11, and 3.12 simultaneously):

```yaml
strategy:
  matrix:
    python-version: ['3.10', '3.11', '3.12']
```

---

### Q3: How does `bandit` perform static application security testing (SAST) on Python codebases?
**Answer**:
`bandit` parses Python source code into an Abstract Syntax Tree (AST) and scans for common security vulnerabilities, such as hardcoded API secrets, insecure use of `eval()` or `exec()`, weak random number generators (`random` instead of `secrets`), and unsafe subprocess executions.

---

### Q4: What does `pip-audit` do in a CI pipeline?
**Answer**:
`pip-audit` scans installed third-party PyPI packages against vulnerability databases (like PyPA Advisory Database and OSV) to detect known Common Vulnerabilities and Exposures (CVEs) in dependency trees before code reaches production.

---

### Q5: How do GitHub Actions Secrets (`${{ secrets.SECRET_NAME }}`) protect sensitive credentials?
**Answer**:
GitHub Actions Secrets store encrypted environment credentials (API keys, Docker Registry passwords, SSH private keys) in the GitHub repository settings. Workflows access them securely at runtime without exposing credentials in plaintext YAML files or build logs.

---

### Q6: What is Blue-Green Deployment and how does it achieve zero downtime?
**Answer**:
Blue-Green Deployment maintains two identical production environments (**Blue** = Active Live, **Green** = Idle Staging). 

The new application release is deployed and tested on Green. Once verified, the load balancer or Nginx router instantly switches incoming live traffic from Blue to Green. If issues occur, traffic is instantly flipped back to Blue with zero downtime.

---

### Q7: What is the difference between `github.event_name == 'pull_request'` and `github.ref == 'refs/heads/main'` in GitHub Actions triggers?
**Answer**:
- `github.event_name == 'pull_request'`: Triggers CI jobs when a PR is created or updated. Used for testing code quality before merging.
- `github.ref == 'refs/heads/main'`: Triggers CD deployment jobs only when code has been merged directly into the `main` production branch.

---

### Q8: What does `actions/checkout@v4` do in a GitHub Actions step?
**Answer**:
`actions/checkout@v4` clones the GitHub repository into the virtual environment runner (`workspace`), making source code files accessible for subsequent steps (such as running `pip install` and `pytest`).

---

### Q9: Why is dependency caching (`actions/setup-python@v5` with `cache: 'pip'`) important in CI pipelines?
**Answer**:
Without caching, every CI pipeline run must download all third-party PyPI dependencies from scratch over the network. Caching `pip` packages speeds up pipeline execution times from minutes to seconds, reducing GitHub Actions runner billable minutes.

---

### Q10: How do you enforce a minimum test coverage threshold (e.g. 80%) in Pytest during CI execution?
**Answer**:
Pass `--cov-fail-under=80` to `pytest`:

```bash
pytest --cov=app --cov-fail-under=80
```

If test coverage drops below 80%, Pytest exits with status code 1, causing the CI pipeline to fail and blocking the Pull Request.
