# Day 21: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from foundational Python email sending (`smtplib`) and asynchronous processing basics up to Celery task idempotency, broker configuration, and background worker lifecycle.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is `smtplib` and what is its full form?
**Answer**:
*   **Full Form**: **S**imple **M**ail **T**ransfer **P**rotocol **Lib**rary.
*   **Definition**: It is a built-in Python module used to send emails over the internet using standard SMTP email protocols.

---

### Q2: What is `smtplib.SMTP_SSL(...)` and why is port 465 used?
**Answer**:
*   **Full Form**: SMTP over **Secure Sockets Layer**.
*   **Purpose**: It creates an encrypted SSL connection between your Python script and email servers (like `smtp.gmail.com` on port `465`), ensuring passwords and email content are protected from interception.

---

### Q3: Why is a Gmail "App Password" required instead of a regular account password?
**Answer**:
When 2-Step Verification (2FA) is enabled on a Google account, Google blocks direct third-party logins with your main password for security. An **App Password** is a 16-character application-specific token that grants secure SMTP access to your Python automation script without exposing your primary Google account password.

---

### Q4: Why shouldn't you send emails directly inside a standard synchronous Flask route?
**Answer**:
Connecting to external SMTP servers (e.g., Gmail) takes 2 to 5 seconds per request. If sent synchronously, the Flask web server thread freezes while waiting for network responses, leading to slow page loads, timeouts, and poor user experience under traffic.

---

### Q5: What is the difference between Synchronous and Asynchronous execution?
**Answer**:
*   **Synchronous**: The web server thread blocks and waits for a long task to finish before returning an HTTP response to the user.
*   **Asynchronous**: The web server offloads long tasks to a background queue (Redis), immediately returns a `202 Accepted` response or redirect, and lets background worker processes (Celery) execute the task concurrently.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the role of the Message Broker and Result Backend in Celery?
**Answer**:
*   **Message Broker (e.g., Redis)**: An in-memory queue that receives task invocations (`task.delay()`) from Flask and stores them until worker processes consume them.
*   **Result Backend (e.g., Redis or PostgreSQL)**: Stores task execution outcomes, return values, error tracebacks, and lifecycle states (`PENDING`, `STARTED`, `SUCCESS`, `FAILURE`).

---

### Q7: How do you trigger an asynchronous background task from Flask?
**Answer**:
By invoking the `.delay()` or `.apply_async()` method on the Celery task function:
```python
# Dispatches to Redis queue in ~1ms without blocking:
send_async_email.delay(recipient_email, subject, content)
```

---

### Q8: How can you schedule a Python email sender to run automatically at 10:00 AM daily?
**Answer**:
By pairing `smtplib` with the `schedule` library:
```python
import schedule, time

schedule.every().day.at("10:00").do(send_email)

while True:
    schedule.run_pending()
    time.sleep(60)
```

## 🔴 Level 3: Advanced & Enterprise Questions

### Q9: Why is Application Context binding critical when Celery tasks interact with Flask-SQLAlchemy?
**Answer**:
Flask-SQLAlchemy and Flask extensions rely on `current_app` and request/app contexts. Because Celery workers execute inside independent processes outside the HTTP lifecycle, tasks must wrap database queries inside `with app.app_context():` or use a custom `Task` subclass (like `celery_init_app`) to bind the context automatically.

---

### Q10: What is Task Idempotency in background processing and why is it important?
**Answer**:
An idempotent task produces the exact same result regardless of whether it executes once or multiple times (e.g., due to network retries). For email tasks, idempotency prevents sending duplicate emails to users by checking a unique token/flag in the database before dispatching.
