# Day 21: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from asynchronous processing basics up to Celery application context binding, task idempotency, and late worker acknowledgments.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is the difference between Synchronous and Asynchronous execution in web applications?
**Answer**:
*   **Synchronous**: The web server thread blocks and waits for a long task to finish before returning an HTTP response to the user.
*   **Asynchronous**: The web server offloads long tasks to a background queue, immediately returns a `202 Accepted` response to the user, and lets background worker processes execute the task concurrently.

---

### Q2: What is Celery?
**Answer**:
Celery is Python's standard asynchronous task queue system used to execute background jobs and scheduled tasks outside of the web request-response cycle.

---

### Q3: What is the role of the Message Broker in Celery?
**Answer**:
The Message Broker (e.g., Redis or RabbitMQ) acts as a temporary buffer/mailbox that receives queued task messages from Flask and holds them until a background Celery worker process picks them up for execution.

---

### Q4: What is a Celery Worker?
**Answer**:
A Celery Worker is an independent Python process running in the background terminal that continuously polls the Message Broker, executes queued tasks, and writes execution outputs to the Result Backend.

---

### Q5: What HTTP status code should an API return when a background job is successfully queued?
**Answer**:
`HTTP 202 Accepted`.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the difference between `CELERY_BROKER_URL` and `CELERY_RESULT_BACKEND`?
**Answer**:
*   `CELERY_BROKER_URL`: Specifies the connection string for the message queue (e.g. Redis) holding pending task messages.
*   `CELERY_RESULT_BACKEND`: Specifies the storage database (e.g. Redis or PostgreSQL) storing completed task status states (`SUCCESS`, `FAILURE`) and return values.

---

### Q7: What is the difference between `.delay()` and `.apply_async()` when calling a Celery task?
**Answer**:
*   `.delay(*args, **kwargs)`: Shorthand method to queue a task for immediate execution.
*   `.apply_async(args, kwargs, countdown=60, eta=...)`: Advanced method supporting execution countdowns, scheduled ETAs, and queue routing parameters.

---

### Q8: How do you poll the status of a queued task using Celery?
**Answer**:
Pass the `task_id` into `AsyncResult(task_id, app=celery_app)` and inspect `result.state` (`PENDING`, `STARTED`, `SUCCESS`, `FAILURE`) and `result.result`.

---

### Q9: How do you automatically retry a failing Celery task?
**Answer**:
Use `self.retry()` inside a task decorated with `bind=True`:

```python
@celery.task(bind=True, max_retries=3)
def send_email_task(self, recipient):
    try:
        connect_smtp(recipient)
    except Exception as exc:
        raise self.retry(exc=exc, countdown=10)
```

---

### Q10: How do you launch a Celery worker process from the command line?
**Answer**:
```bash
celery -A app.celery_app worker --loglevel=info
```

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Why is Flask Application Context binding necessary inside Celery tasks, and how is it implemented?
**Answer**:
Celery workers run in separate Python processes outside Flask's WSGI request cycle. To access SQLAlchemy database models or Flask configuration settings inside background tasks, implement the `celery_init_app()` factory wrapper using a custom `Task` subclass that executes `with app.app_context():` during task invocation.

---

### Q12: What is Task Idempotency and why is it critical in distributed Celery architectures?
**Answer**:
**Task Idempotency** guarantees that executing a task multiple times produces the exact same side-effect as executing it once. Because networks can fail or workers can crash before sending task acknowledgments, Celery may re-queue a message. Tasks like payment processing must be idempotent to prevent double-charging customers.

---

### Q13: What is the difference between Early Acknowledgment and Late Acknowledgment (`task_acks_late=True`) in Celery?
**Answer**:
*   **Early Acknowledgment (Default)**: Worker acknowledges and deletes the task message from Redis *before* executing it. If worker crashes mid-execution, the task is lost.
*   **Late Acknowledgment (`task_acks_late=True`)**: Worker acknowledges the task *after* execution succeeds. If worker crashes, another worker picks up the task to re-run it.

---

### Q14: How does Celery Beat handle recurring cron-like scheduled tasks?
**Answer**:
Celery Beat is a scheduler process that reads a periodic schedule (`CELERY_BEAT_SCHEDULE`) and sends task messages to the Redis broker at specified time intervals (e.g., running database cleanup every midnight).

---

### Q15: How can enterprise teams prevent Redis memory exhaustion from storing thousands of Celery task results?
**Answer**:
1. Enable `CELERY_TASK_IGNORE_RESULT = True` for tasks whose return values are not needed.
2. Configure `CELERY_RESULT_EXPIRES = 3600` so Redis automatically expires and deletes old task results after 1 hour.
