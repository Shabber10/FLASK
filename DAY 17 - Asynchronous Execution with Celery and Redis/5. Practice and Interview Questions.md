# Day 17: Practice & Technical Interview Questions

### Q1: Why should heavy operations (e.g. sending emails or generating PDFs) be offloaded to Celery background tasks?
**Answer**:
Flask WSGI worker threads process requests synchronously. If a view function performs a slow operation taking 5 seconds, that WSGI worker thread is blocked and unavailable to handle other incoming user traffic. If multiple users hit slow routes simultaneously, worker pools become exhausted, leading to server unresponsiveness and HTTP 504 Gateway Timeouts.

Offloading tasks to Celery dispatches a message to Redis in milliseconds, allowing the Flask view function to return an immediate response (`202 Accepted`) while background Celery worker processes execute the heavy job asynchronously.

### Q2: What is the difference between a Message Broker and a Result Backend in Celery?
**Answer**:
- **Message Broker** (e.g. Redis, RabbitMQ): Transport middleware responsible for receiving, queuing, and delivering task messages from Flask producers to Celery workers.
- **Result Backend** (e.g. Redis, PostgreSQL): Storage system where Celery workers save task status (`PENDING`, `SUCCESS`, `FAILURE`), execution metadata, and return values or error stack traces.

### Q3: How do `.delay()` and `.apply_async()` differ when dispatching Celery tasks?
**Answer**:
- `.delay(*args, **kwargs)`: Shortcut method for simple asynchronous task invocation.
- `.apply_async(args=[...], kwargs={...}, countdown=60, queue='high_priority')`: Advanced invocation method offering execution control parameters such as execution countdown delays, ETA execution timestamps, task expiry limits, and explicit routing to specific worker queues.

---

### Q4: Why is it critical to run Celery tasks within Flask's Application Context (`app_context()`)?
**Answer**:
Celery workers run in separate standalone Python processes outside the Flask web application process. If a Celery task interacts with Flask extensions (such as querying `db.session` via Flask-SQLAlchemy or sending email via Flask-Mail), it requires an active Flask application context (`current_app`). 

Wrapping tasks in `with app.app_context():` ensures database connections, configurations, and proxies resolve correctly inside worker threads.

### Q5: How do you implement automatic task retries with exponential backoff in Celery?
**Answer**:
Pass `bind=True` to the task decorator and invoke `self.retry()` inside exception handlers:

```python
@celery.task(bind=True, max_retries=5)
def send_webhook(self, url, payload):
    try:
        response = requests.post(url, json=payload, timeout=5)
        response.raise_for_status()
    except Exception as exc:
        # Exponential Backoff: 2s, 4s, 8s, 16s, 32s
        countdown = 2 ** self.request.retries
        raise self.retry(exc=exc, countdown=countdown)
```

### Q6: What is Celery Beat and how does it differ from standard Celery Workers?
**Answer**:
- **Celery Workers**: Reactive background processes that wait for task messages to arrive in queues and execute them immediately.
- **Celery Beat**: A single-instance scheduler daemon that reads a cron-like configuration schedule (`beat_schedule`) and dispatches task messages to the message broker at specified time intervals.

---

### Q7: Why must Celery task arguments be JSON-serializable by default?
**Answer**:
Celery serializes task arguments into strings (using JSON or Pickle) to transmit them across network sockets to the message broker. Complex Python objects (such as SQLAlchemy model instances or file handles) cannot be JSON-serialized. Tasks should accept primitive identifiers (e.g. `user_id=5`) and re-query database models inside the worker task body.

---

### Q8: What is Task Idempotency and why is it important in distributed systems?
**Answer**:
An idempotent task produces the exact same side effects regardless of whether it is executed once or multiple times. In distributed networks, message brokers may re-deliver a task message if a worker crashes before acknowledging completion. Designing idempotent tasks prevents duplicate charges or duplicate emails if a task is executed twice.

---

### Q9: What happens if a Celery worker process crashes while executing a task?
**Answer**:
If task acknowledgment (`acks_late=True`) is configured, the broker detects the worker disconnect and re-queues the unacknowledged task message for another available worker to pick up and re-execute.

### Q10: How do you check the real-time status of a task using its UUID `task_id`?
**Answer**:
Use `celery.result.AsyncResult(task_id)`:

```python
from celery.result import AsyncResult

res = AsyncResult(task_id)
print(res.state)   # PENDING, STARTED, SUCCESS, FAILURE
print(res.result)  # Return value or Exception instance
```
