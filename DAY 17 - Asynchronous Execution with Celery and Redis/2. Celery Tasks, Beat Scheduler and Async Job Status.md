# Day 17: Celery Tasks, Beat Scheduler & Job Polling

In this section, we examine declaring Celery tasks (`@shared_task`), `.delay()` vs `.apply_async()`, task status inspection via `AsyncResult`, error retries with exponential backoff, and periodic scheduling with Celery Beat.

---

## 1. Declaring & Dispatching Celery Tasks

Tasks are defined using `@shared_task` (or `@celery.task`):

```python
from celery import shared_task
import time

@shared_task
def add_numbers(x, y):
    """Simple Background Task."""
    return x + y

@shared_task(bind=True, max_retries=3)
def send_email_task(self, recipient, subject, body):
    """Task with Automatic Retry Logic."""
    try:
        # Simulate sending email
        time.sleep(2)
        print(f"Email sent to {recipient}")
        return {"status": "SUCCESS", "recipient": recipient}
    except Exception as exc:
        # Retry in 10 seconds if email server is temporarily down
        raise self.retry(exc=exc, countdown=10)
```

### Dispatching Tasks

```python
# 1. Simple Asynchronous Dispatch (.delay)
task_result = add_numbers.delay(10, 20)
print(task_result.id) # Unique Task UUID string

# 2. Advanced Dispatch (.apply_async) with Countdown and Queue Routing
send_email_task.apply_async(
    args=['user@example.com', 'Welcome!', 'Hello User'],
    countdown=60,            # Execute 60 seconds in future
    queue='high_priority'    # Route to high_priority worker queue
)
```

## 2. Polling Task Status & Results (`AsyncResult`)

Web clients poll task status using the task UUID returned during dispatch:

```python
from celery.result import AsyncResult
from flask import jsonify

@app.route('/api/tasks/<task_id>')
def get_task_status(task_id):
    result = AsyncResult(task_id)
    
    response = {
        "task_id": task_id,
        "state": result.state,  # PENDING, STARTED, SUCCESS, FAILURE, RETRY
    }
    
    if result.state == 'SUCCESS':
        response["result"] = result.result
    elif result.state == 'FAILURE':
        response["error"] = str(result.result)
        
    return jsonify(response)
```

### Celery Task Lifecycle States
- **`PENDING`**: Task is queued in broker, awaiting a worker.
- **`STARTED`**: Worker has picked up the task and execution is underway.
- **`SUCCESS`**: Task executed successfully without errors.
- **`FAILURE`**: Task raised an unhandled exception.
- **`RETRY`**: Task failed and is waiting to be retried.

## 3. Periodic Scheduled Jobs with Celery Beat

**Celery Beat** is a scheduler daemon that dispatches tasks at regular intervals (like a cron daemon):

```python
# In Celery Configuration
CELERY = {
    'broker_url': 'redis://localhost:6379/0',
    'result_backend': 'redis://localhost:6379/0',
    'beat_schedule': {
        'cleanup-expired-sessions-every-midnight': {
            'task': 'tasks.cleanup_sessions',
            'schedule': crontab(hour=0, minute=0), # Runs daily at midnight
        },
        'sync-inventory-every-5-mins': {
            'task': 'tasks.sync_inventory',
            'schedule': 300.0, # Runs every 300 seconds (5 minutes)
        }
    }
}
```

## 4. Starting Celery Processes via CLI

Run Celery worker and beat daemons in separate terminal windows:

```bash
# 1. Start Celery Worker Process
celery -A app.celery_app worker --loglevel=info

# 2. Start Celery Beat Scheduler Daemon
celery -A app.celery_app beat --loglevel=info
```
