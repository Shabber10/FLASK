## 1. What are Error Handling, Logging, and Observability?

Imagine an airplane flying through a storm:

*   **Error Handling**: The airplane's backup systems preventing the engine from stalling when a minor sensor glitch occurs. In Flask, error handling catches crashes gracefully so users see clean JSON error messages instead of ugly 500 HTML tracebacks!
*   **Logging**: The airplane's **Flight Data Recorder (Black Box)** recording timestamps, altitude, fuel levels, and pilot actions. In Flask, logging records every request, warning, and database error to a file.
*   **Observability**: The air traffic control radar tracking the exact flight path across multiple airports. In Flask, observability traces a single HTTP request across multiple microservices to find performance bottlenecks!

## 2. The 5 Python Logging Levels

Not all log messages have the same urgency. Python provides 5 standard log severity levels:

| Log Level | Severity | When to Use |
| :--- | :--- | :--- |
| **`DEBUG`** | 🔵 Low | Detailed diagnostic info (e.g., `Executing SQL query: SELECT...`). Enabled only in development. |
| **`INFO`** | 🟢 Normal | Confirmation that things are working normally (e.g., `User #42 logged in successfully`). |
| **`WARNING`** | 🟡 Attention | Indication that something unexpected happened (e.g., `Redis memory at 85% capacity`). |
| **`ERROR`** | 🔴 High | A serious issue occurred; application failed to complete a request (e.g., `Database connection lost`). |
| **`CRITICAL`** | 💥 Fatal | A catastrophic failure; application may crash completely (e.g., `Disk space 100% full`). |

## 3. Why Unstructured Text Logs Fail vs. Structured JSON Logging

In beginner tutorials, developers write plain text log messages:

```python
# ❌ Unstructured Text Log (Hard for machines to search!)
print("2026-08-10 10:00:00 - User 42 failed to purchase item 99 due to insufficient funds")
```

When managing 100 servers generating 50 million log lines per day, log aggregation systems (like ELK Stack, Datadog, or AWS CloudWatch) cannot search plain text efficiently.

Enterprise apps use **Structured JSON Logging**:

```json
{
  "timestamp": "2026-08-10T10:00:00Z",
  "level": "WARN",
  "event": "PAYMENT_FAILED",
  "user_id": 42,
  "item_id": 99,
  "reason": "INSUFFICIENT_FUNDS",
  "correlation_id": "req-uuid-987654"
}
```

Because JSON is structured key-value data, engineers can query `event == "PAYMENT_FAILED"` in Datadog instantly!

## 4. What is a Request Correlation ID (`X-Request-ID`)?

When a user clicks "Checkout", your web app might call the Auth API, Payment API, and Inventory API.

A **Request Correlation ID** is a unique UUID string (`req-uuid-987654`) generated when the HTTP request arrives at your server. It is injected into every log entry generated during that request, allowing you to trace the entire lifecycle of a single user action!
