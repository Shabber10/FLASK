# Day 08: Lazy Loading Strategies & Performance Tuning

In this section, we examine relationship loading strategies (`select`, `joined`, `subquery`, `selectin`, `dynamic`), the infamous **N+1 Query Problem**, benchmarking queries, and explicit eager loading using `options()`.

---

## 1. The N+1 Query Problem Explained

The **N+1 Query Problem** occurs when an application fetches $N$ parent records, and then accesses a lazily-loaded relationship attribute on each parent inside a loop, resulting in $1 + N$ separate database queries:

```python
# 1 Query to fetch 100 Posts
posts = db.session.execute(db.select(Post).limit(100)).scalars().all()

for post in posts:
    # Triggers 1 SEPARATE SELECT query per post to fetch author! (100 extra queries!)
    print(post.author.name)

# Total DB Queries Executed: 1 + 100 = 101 queries!
```

---

## 2. SQLAlchemy Lazy Loading Strategies

Change loading behavior globally on the `db.relationship(..., lazy=STRATEGY)` declaration or per-query using `options()`.

### Loading Strategies Comparison

| Loading Strategy | Generated SQL Pattern | Best Use Case |
| :--- | :--- | :--- |
| `lazy='select'` (Default) | Emits secondary `SELECT` on attribute access | Single object lookups where relationship is rarely accessed. |
| `lazy='joined'` | Performs SQL `LEFT OUTER JOIN` in primary query | One-to-One or Many-to-One scalar relationships. |
| `lazy='subquery'` | Issues 2nd `SELECT` using subquery of parent IDs | Legacy collections (Can be slow on large datasets). |
| `lazy='selectin'` | Issues 2nd `SELECT` using `WHERE parent_id IN (...)` | **One-to-Many collections (Best general performance!)** |
| `lazy='dynamic'` | Returns a `Query` object instead of loading collection | Very large collections requiring in-memory filtering/paging. |

## 3. Explicit Eager Loading with `selectinload()` & `joinedload()`

Override model-level loading defaults per-query using `sqlalchemy.orm` options:

```python
from sqlalchemy.orm import selectinload, joinedload

# 1. Eager Load Collection using selectinload (2 SQL queries total for 100 posts)
stmt = db.select(Post).options(selectinload(Post.comments)).limit(100)
posts = db.session.execute(stmt).scalars().all()

for p in posts:
    # Fast: Comments already pre-loaded into memory!
    print(len(p.comments))

# 2. Eager Load Scalar Relationship using joinedload (1 SQL JOIN query total)
stmt = db.select(Post).options(joinedload(Post.author)).where(Post.id == 1)
post = db.session.execute(stmt).scalar_one()
```

## 4. Using Dynamic Loading (`lazy='dynamic'`)

When a relationship contains thousands of records (e.g. `user.followers`), loading all items into a Python list exhausts memory. `lazy='dynamic'` returns a query statement object:

```python
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    posts = db.relationship('Post', lazy='dynamic')

# Filter and paginate directly on the relationship attribute!
user = db.session.get(User, 1)
recent_posts = user.posts.filter(Post.views > 1000).order_by(Post.created_at.desc()).limit(5).all()
```
