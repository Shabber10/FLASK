# Day 08: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from relationship basics up to N+1 query elimination and complex cascade configurations.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is a Database Relationship in simple terms?
**Answer**:
A Database Relationship is a connection established between two tables using Foreign Keys (e.g. linking a `Comment` row to the specific `Post` row it belongs to), allowing related data to be organized and queried efficiently.

---

### Q2: What is a Foreign Key?
**Answer**:
A Foreign Key is a column in a child table (`post_id`) that stores the Primary Key ID (`id`) of a parent row in another table, serving as a direct reference pointer between the two rows.

---

### Q3: What is the difference between a One-to-Many and a Many-to-Many relationship?
**Answer**:
*   **One-to-Many**: A single parent record connects to multiple child records (e.g., 1 Author writes Many Posts).
*   **Many-to-Many**: Multiple records on both sides connect to each other (e.g., 1 Post has Many Tags, and 1 Tag belongs to Many Posts). This requires a 3rd **Junction Table**.

---

### Q4: What is Cascade Delete and why is it useful?
**Answer**:
Cascade Delete is an automatic rule that instructs the database/ORM to delete all child records (e.g. Comments) whenever their parent record (Post) is deleted, preventing orphan records from clogging the database.

---

### Q5: Where do you declare `db.ForeignKey` versus `db.relationship`?
**Answer**:
*   `db.ForeignKey`: Declared on the **child model's column** (the table holding the ID reference).
*   `db.relationship`: Declared on the **parent model** to create a high-level Python attribute for navigating related objects.

---

## 🟡 Level 2: Intermediate Questions

### Q6: What is the N+1 query problem and how do you resolve it in SQLAlchemy?
**Answer**:
The N+1 query problem occurs when an application fetches $N$ parent records in 1 initial query, and then lazily fetches the relationship attribute for each parent inside a loop, triggering $N$ secondary SQL queries ($1 + N$ total queries).

Resolve it using eager loading strategies:
*   Use `selectinload(Model.relationship)` for One-to-Many collections (emits 2 total queries).
*   Use `joinedload(Model.relationship)` for Many-to-One scalar relationships (emits 1 SQL `JOIN` query).

---

### Q7: What is the difference between `backref` and `back_populates` in `db.relationship`?
**Answer**:
*   `backref`: Automatically generates the inverse relationship property on the target model in a single string line (legacy shortcut).
*   `back_populates`: Explicitly requires defining `db.relationship` on **both** models, pointing to each other by attribute name. It is the modern SQLAlchemy 2.0 standard because it provides static type checking support.

---

### Q8: What does `cascade='all, delete-orphan'` mean and how does `delete-orphan` differ from `delete`?
**Answer**:
*   `delete`: Deletes child records from the database when the parent model instance itself is deleted (`db.session.delete(parent)`).
*   `delete-orphan`: Deletes a child record from the database when it is disassociated from the parent's collection list in Python code (e.g. `parent.children.remove(c1)`), even if the parent instance remains alive.

---

### Q9: How do you create a One-to-One relationship in Flask-SQLAlchemy?
**Answer**:
Set `uselist=False` on the parent `db.relationship` declaration, and set `unique=True` on the child model's `db.ForeignKey` column:

```python
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    profile = db.relationship('UserProfile', backref='user', uselist=False)

class UserProfile(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    user_id = db.Column(db.Integer, db.ForeignKey('user.id'), unique=True, nullable=False)
```

---

### Q10: How do `lazy='joined'` and `lazy='selectin'` differ under the hood?
**Answer**:
*   `lazy='joined'`: Emits an SQL `LEFT OUTER JOIN` in the initial `SELECT` query. Ideal for One-to-One or Many-to-One scalar relationships, but can produce duplicate rows or Cartesian products when joining multiple collections.
*   `lazy='selectin'`: Emits a secondary `SELECT` query using `WHERE parent_id IN (1, 2, 3...)`. It avoids Cartesian products and is the recommended eager loader for collections.

---

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: When should you use `lazy='dynamic'` on a relationship?
**Answer**:
Use `lazy='dynamic'` on One-to-Many relationships that contain thousands or millions of items (e.g. `user.followers`). Instead of loading all items into a Python list, `dynamic` returns a SQLAlchemy `Query` object, allowing you to append `.filter()`, `.order_by()`, and `.paginate()` directly on the relationship attribute.

---

### Q12: How do you handle Many-to-Many relationships that require additional payload columns (e.g. `assigned_date`, `role`)?
**Answer**:
When an association requires extra attributes beyond foreign keys, convert the junction table into a full **Association Model** class:

```python
class PostTag(db.Model):
    __tablename__ = 'post_tags'
    post_id = db.Column(db.Integer, db.ForeignKey('posts.id'), primary_key=True)
    tag_id = db.Column(db.Integer, db.ForeignKey('tags.id'), primary_key=True)
    assigned_by = db.Column(db.String(50))  # Extra attribute
    
    post = db.relationship('Post', backref='post_tags')
    tag = db.relationship('Tag', backref='post_tags')
```

---

### Q13: What is the difference between DB-level foreign key CASCADE (`ondelete='CASCADE'`) and ORM-level `cascade='all, delete'`?
**Answer**:
*   DB-level (`ondelete='CASCADE'`): Executed directly by the RDBMS engine when a foreign key row is deleted. It does not require SQLAlchemy to load child objects into memory.
*   ORM-level (`cascade='all, delete'`): Managed in Python by SQLAlchemy. It loads child instances into `db.session` to trigger Python-side event listeners and cascade rules.

Best practice is to specify **both** for maximum data integrity and performance.

---

### Q14: What happens if you access a `lazy='select'` relationship attribute after `db.session.close()`?
**Answer**:
Accessing a lazily loaded relationship on a detached object whose session has been closed raises a `DetachedInstanceError: Parent instance is not bound to a Session; lazy load operation of attribute cannot proceed`.

---

### Q15: How do you write a self-referential relationship (e.g. Category parent/child trees or Manager/Employee hierarchies)?
**Answer**:
Point the `ForeignKey` and `relationship` back to the model's own primary key:

```python
class Category(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(50), nullable=False)
    parent_id = db.Column(db.Integer, db.ForeignKey('category.id'))
    
    subcategories = db.relationship('Category', backref=db.backref('parent', remote_side=[id]))
```
