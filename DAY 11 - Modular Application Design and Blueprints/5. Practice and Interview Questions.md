# Day 11: Practice & Technical Interview Questions

---

### Q1: What is a Flask Blueprint and why is it preferred over declaring all routes in `app.py`?
**Answer**:
A Blueprint is a logical component that records routes, handlers, templates, and static folders to be registered onto a Flask application later. 

Blueprints solve monolithic codebase issues by:
1. Decoupling application features into modular, reusable packages (e.g. `auth`, `admin`, `api`).
2. Preventing circular import dependencies between models, views, and forms.
3. Enabling multiple developers to work on separate application modules without git merge conflicts.
4. Allowing uniform URL prefixing (`url_prefix='/api/v1'`) and blueprint-scoped middleware.

---

### Q2: Is a Flask Blueprint a standalone application instance? Can it be run directly on a WSGI server?
**Answer**:
No. A Blueprint is **not** a Flask application instance. It cannot handle HTTP requests or run independently on a WSGI server. It acts as a set of instructions waiting to be bound to a real `Flask` application instance via `app.register_blueprint()`.

---

### Q3: How does `url_for()` namespacing work when resolving routes registered inside Blueprints?
**Answer**:
Flask prefixes view function names with the blueprint's name: `'blueprint_name.view_function_name'`.

- Calling `url_for('auth.login')` resolves to the `login` function inside the `auth` blueprint.
- Calling `url_for('.login')` uses relative endpoint resolution, resolving to the `login` view function within the **currently executing blueprint**.

### Q4: How do you register Nested Blueprints in Flask 2.0+ and what URL prefix is generated?
**Answer**:
In Flask 2.0+, register a child blueprint onto a parent blueprint using `parent_bp.register_blueprint(child_bp)`. The resulting URL prefix is the concatenation of the parent and child prefixes:

```python
parent_bp = Blueprint('api', __name__, url_prefix='/api')
child_bp = Blueprint('v1', __name__, url_prefix='/v1')

parent_bp.register_blueprint(child_bp)
app.register_blueprint(parent_bp)
# Final Route Prefix: "/api/v1"
```

### Q5: How do `@bp.before_request` and `@bp.app_before_request` differ?
**Answer**:
- `@bp.before_request`: Registers a request hook that executes **ONLY** when a request matches a route registered within that specific blueprint.
- `@bp.app_before_request`: Registers a request hook defined inside a blueprint that executes for **ALL** incoming requests across the entire Flask application.

---

### Q6: How do `@bp.errorhandler(404)` and `@bp.app_errorhandler(404)` differ?
**Answer**:
- `@bp.errorhandler(404)`: Handles 404 errors triggered within that specific blueprint's view functions.
- `@bp.app_errorhandler(404)`: Overrides the global 404 error handler for the entire Flask application instance.

---

### Q7: How do you bind a Blueprint to a specific custom subdomain (e.g. `api.example.com`)?
**Answer**:
Pass `subdomain='api'` to the `Blueprint` constructor and configure `SERVER_NAME` on the Flask application:

```python
app.config['SERVER_NAME'] = 'example.com:5000'
api_bp = Blueprint('api', __name__, subdomain='api')
app.register_blueprint(api_bp)
```

---

### Q8: Can the same Blueprint instance be registered multiple times on a Flask application with different URL prefixes?
**Answer**:
Yes! A single Blueprint instance can be registered multiple times with different configuration options or URL prefixes:

```python
app.register_blueprint(site_bp, url_prefix='/en')
app.register_blueprint(site_bp, url_prefix='/fr', name='site_fr')
```

---

### Q9: How do static and template folders work inside a Blueprint?
**Answer**:
Passing `template_folder='templates'` or `static_folder='static'` to a `Blueprint` adds its folders to Flask's search path:
- **Templates**: Flask searches the app's root `templates/` folder first, followed by blueprint `templates/` folders.
- **Static Files**: Static assets inside a blueprint are accessible via `url_for('blueprint_name.static', filename='style.css')`.

---

### Q10: What is the difference between Feature-Based and Layer-Based project structure?
**Answer**:
- **Layer-Based**: Groups files by technical layer (`views/`, `models/`, `controllers/`). Works well for small apps.
- **Feature-Based**: Groups files by domain feature (`blueprints/auth/`, `blueprints/billing/`, `blueprints/catalog/`). Each feature folder contains its own routes, models, forms, and templates, making large codebases easier to maintain and scale.
