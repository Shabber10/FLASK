# Day 09: Practice & Technical Interview Questions

This question bank is divided into **3 progression levels**, starting from migration fundamentals up to autogeneration limits and zero-downtime schema evolution.

---

## 🟢 Level 1: Absolute Beginner Questions

### Q1: What is a Database Migration in simple terms?
**Answer**:
A Database Migration is like version control (Git) for database tables. It tracks structural changes (like adding columns or creating tables) in code files, allowing you to update live databases safely without deleting existing user data.

---

### Q2: Why should `db.create_all()` NEVER be used in production applications?
**Answer**:
`db.create_all()` only creates tables if they do not exist yet. It cannot add new columns, remove obsolete fields, or modify data types on existing live tables. The only way to force it to add a column is to drop the table—which deletes all real user data permanently!

---

### Q3: What is the difference between Alembic and Flask-Migrate?
**Answer**:
*   **Alembic**: The core database migration engine created for SQLAlchemy. It computes database schema differences and generates migration Python scripts.
*   **Flask-Migrate**: A Flask extension that integrates Alembic into Flask applications and exposes user-friendly `flask db` command-line tools in the terminal.

---

### Q4: What are the 4 main CLI commands used in Flask-Migrate?
**Answer**:
1.  `flask db init`: Initializes the `migrations/` folder (run once).
2.  `flask db migrate -m "message"`: Autogenerates a revision script by comparing models against the database.
3.  `flask db upgrade`: Applies pending migration scripts to the database.
4.  `flask db downgrade`: Rolls back the last applied migration step.

---

### Q5: Where are autogenerated migration scripts stored?
**Answer**:
Inside the `migrations/versions/` directory inside your project root directory.

---

## 🟡 Level 2: Intermediate Questions

### Q6: How does Alembic know which migrations have already been applied to a database?
**Answer**:
Alembic creates a single-column table in your SQL database named **`alembic_version`**. It holds a single string value—the revision hash of the most recently applied migration script. When `flask db upgrade` is executed, Alembic compares `alembic_version` against script files in `migrations/versions/` to determine which pending scripts need to run.

---

### Q7: What are `upgrade()` and `downgrade()` functions inside revision scripts?
**Answer**:
*   `upgrade()`: Contains Alembic operations (such as `op.add_column()`) executed when running `flask db upgrade` to advance the database schema forward.
*   `downgrade()`: Contains inverse Alembic operations (such as `op.drop_column()`) executed when running `flask db downgrade` to revert changes back to the previous version.

---

### Q8: What does `flask db stamp <revision_hash>` do and when would you use it?
**Answer**:
`flask db stamp <hash>` directly updates the `alembic_version` table in the database to point to `<hash>` **without executing any SQL migration scripts**. It is used to repair out-of-sync migration states or when importing an existing database whose tables were created manually.

---

### Q9: What schema changes CANNOT be autogenerated by `flask db migrate`?
**Answer**:
Alembic's autogenerate feature cannot automatically detect:
*   Table name or column name changes (it will misinterpret a rename as dropping the old column and adding a new column, causing data loss!).
*   Changes to table options or custom database constraints.
*   Special column types like ENUMs on certain database engines.

Always inspect autogenerated migration scripts before running `flask db upgrade`!

---

### Q10: How do `flask db current` and `flask db heads` differ?
**Answer**:
*   `flask db current`: Displays the revision hash currently recorded in the active database's `alembic_version` table.
*   `flask db heads`: Displays the latest revision hash script file available in `migrations/versions/`.

If `current` matches `heads`, your database schema is completely up to date!

## 🔴 Level 3: Advanced & Enterprise Questions

### Q11: Why does SQLite fail on standard `ALTER TABLE` statements and how does `render_as_batch=True` solve it?
**Answer**:
SQLite lacks native SQL support for dropping or altering existing table columns directly (`ALTER TABLE DROP COLUMN`). 

Setting `Migrate(app, db, render_as_batch=True)` enables **Batch Mode**. Instead of running invalid `ALTER TABLE` statements, Alembic creates a temporary table (`_alembic_tmp_users`), copies existing rows into the temporary table, drops the old table, and renames the temporary table back to the original name transparently.

---

### Q12: How do you safely add a non-nullable (`NOT NULL`) column to a database table that already contains millions of live rows?
**Answer**:
Adding a `NOT NULL` column directly fails because existing rows cannot have `NULL` values. Solve this using a 3-step **Data Migration** inside `upgrade()`:

```python
def upgrade():
    # 1. Add column as nullable initially
    op.add_column('users', sa.Column('is_verified', sa.Boolean(), nullable=True))
    
    # 2. Populate default data for all existing rows!
    op.execute("UPDATE users SET is_verified = FALSE WHERE is_verified IS NULL")
    
    # 3. Enforce NOT NULL constraint
    op.alter_column('users', 'is_verified', nullable=False)
```

---

### Q13: What strategy should be used to achieve zero-downtime database migrations during production deployments?
**Answer**:
Achieve zero-downtime migrations using **Expand-Contract (Parallel Adoption)** pattern across multiple app deployments:
1.  **Phase 1 (Expand)**: Add new columns/tables as optional (nullable). Deploy new application code that writes to both old and new fields.
2.  **Phase 2 (Migrate Data)**: Run a background script populating historical data into the new fields.
3.  **Phase 3 (Contract)**: Deploy code using only the new fields, then issue a migration dropping old unused fields.

---

### Q14: What is `env.py` inside the `migrations/` directory and why is it important?
**Answer**:
`env.py` is the Python script executed whenever Alembic runs. It loads the Flask application context, retrieves `app.config['SQLALCHEMY_DATABASE_URI']`, and binds `db.metadata` to Alembic so autogenerate can inspect model definitions against live database tables.

---

### Q15: What happens if two developers on a team create separate migrations simultaneously resulting in multiple "heads"?
**Answer**:
Running `flask db upgrade` will fail with an `AmbiguousHeadError`. Resolve it by running `flask db merge heads -m "merge_branch_a_and_b"`, which creates a new merge migration script joining the two branching revision histories back into a single lineage.
