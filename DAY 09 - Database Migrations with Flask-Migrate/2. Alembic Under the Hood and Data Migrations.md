# Day 09 - Module 2: Alembic Under the Hood & Data Migrations

Welcome to **Module 2** of Day 09! Now that we know how to use the `flask db` CLI commands, let's explore **how Alembic works under the hood**, how to write **Data Migrations**, and how to handle **SQLite ALTER TABLE limitations**!

---

## 1. Inside the `migrations/` Directory

Running `flask db init` creates a `migrations/` repository in your project root:

```
migrations/
├── env.py              # Configuration script loading Flask app & SQLAlchemy metadata
├── README              # Environment documentation
├── script.py.mako      # Mako template used for generating new revision scripts
└── versions/           # Folder holding revision scripts (e.g. 1a2b3c4d_add_phone.py)
```

---

## 2. The `alembic_version` Tracking Table

When you run `flask db upgrade`, Alembic creates a hidden single-column table inside your database named **`alembic_version`**:

```
TABLE: alembic_version
┌──────────────────┐
│ version_num      │
├──────────────────┤
│ a1b2c3d4e5f6     │  <-- Current active migration revision hash matching a file in versions/
└──────────────────┘
```

Alembic checks this table to determine which migration scripts have already executed and which pending scripts need to run!

---

## 3. Structure of an Autogenerated Revision Script

Each file in `migrations/versions/` contains two core functions: **`upgrade()`** and **`downgrade()`**:

```python
"""Add phone_number to User

Revision ID: a1b2c3d4e5f6
Revises: 
Create Date: 2026-08-10 11:15:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = 'a1b2c3d4e5f6'
down_revision = None

def upgrade():
    # Executed when running `flask db upgrade`
    op.add_column('users', sa.Column('phone_number', sa.String(length=20), nullable=True))

def downgrade():
    # Executed when running `flask db downgrade`
    op.drop_column('users', 'phone_number')
```

## 4. Manual Data Migrations (Populating Existing Rows)

When adding a non-nullable column (`nullable=False`) to a table that already contains live rows, database engines will reject `op.add_column()` because existing rows cannot have `NULL` values.

To fix this, write a **Data Migration** inside `upgrade()` using `op.execute()`:

```python
def upgrade():
    # Step 1: Add column as nullable initially
    op.add_column('users', sa.Column('is_verified', sa.Boolean(), nullable=True))
    
    # Step 2: Populate default value for all existing database rows!
    op.execute("UPDATE users SET is_verified = FALSE WHERE is_verified IS NULL")
    
    # Step 3: Alter column constraint to NOT NULL
    op.alter_column('users', 'is_verified', nullable=False)
```

## 5. Handling SQLite Constraints (`render_as_batch=True`)

SQLite has strict architectural limitations: it **cannot** perform standard `ALTER TABLE DROP COLUMN` or `ALTER TABLE ALTER COLUMN` statements directly!

To bypass this in SQLite, enable **Batch Mode** in Flask-Migrate:

```python
# Enable Batch Mode for SQLite compatibility
migrate = Migrate(app, db, render_as_batch=True)
```

> **What Batch Mode Does**: Instead of executing invalid SQLite `ALTER TABLE` commands, Alembic creates a temporary table (`_alembic_tmp_users`), copies your old rows into the new table, drops the old table, and renames the new table!
